# 边界缺陷检查清单

> [English](boundary-checklist.md) | **简体中文**

本文档持续收录在本仓库中发现的边界（boundary）/极端情况（edge case）缺陷的*类别*，
以避免同类问题被反复引入。每个条目都是一个可复用的模式：反模式（anti-pattern）、
修复方式，以及实际发现问题的位置。可以从两个角度使用：

- **编写**解析 / 匹配 / 光标 / 缓存 / 序列化 / 生命周期 /
  分类相关的代码时——提交前先核对相关条目。
- **评审**涉及上述领域的变更时——把这份清单当作检查表逐条过一遍。

这类缺陷大多能通过 `typecheck`，甚至能通过正常路径（happy path）的测试。它们只在
特定的边界输入上暴露，因此需要有意识地专门审视，而不能只看测试是否全绿。

---

## 1. `parse` 系列函数会返回 `NaN`，而所有与 `NaN` 的比较结果都是 `false`

`Date.parse(x)`、`parseInt(x)`、`parseFloat(x)`、`Number(x)` 在输入非法时返回 `NaN`。
`NaN >= cutoff`、`NaN < limit`、`NaN === n` **全部**为 `false`，因此写成「较新 → 保留」
的守卫逻辑在遇到无法解析的输入时会悄悄走进 *else* 分支。

- **正确做法：** `const n = Date.parse(x); if (Number.isNaN(n) || n >= cutoff) …` ——
  明确决定「无法解析的值」意味着什么，并显式处理。
- **发现位置：** `packages/core/src/memory/compact.ts` —— 损坏的 `addedAt` 使
  `NaN >= cutoff` 为 false，导致一条年龄未知的记忆事实被悄悄归档。
- **同类问题：** 会话元数据接受带时区偏移的时间戳，却按其原始字符串排序；应先把
  时间解析为 epoch 值，再让 `keepLast` 决定裁剪时保留哪些内容。
- **同类问题：** Loop DAG 与推演摘要曾按字符串排序合法的偏移时间戳，导致新旧次序错误；
  应比较解析后的 epoch，并保留确定性的平局行为。
- **同类问题：** Graph 调度智能把追加次序当作事件次序，导致延迟到达的合法观测可能覆盖
  真正的最新结果。

## 2. 前缀匹配必须带分隔符边界

`subject.startsWith(match)` 会让 `src/foo` 匹配到 `src/foobar.ts`，让
`npm run build` 匹配到 `npm run build-all` —— 一个共享前缀的「兄弟」就这样混过了关卡。

- **正确做法：** 对于**允许 / 授权**类判定，必须要求边界：`subject ===
  match`，或者 match 本身已经以分隔符结尾，或者 `subject[match.length]` 是分隔符
  （命令用 `" "`，路径用 `/` 或 `path.sep`）。对于**拒绝**类判定，则保留宽泛的
  `startsWith` —— 拒绝规则过度匹配属于失败关闭（fail closed），是安全的。
- **发现位置：** `packages/core/src/tools/permissions.ts`（`ruleMatches` /
  `boundaryPrefix`）；同样的道理此前已经体现在 `sessionAllowed` 中。
- **同类问题：** `packages/core/src/hooks/index.ts`（`hookApplies`）—— hook 的
  `pattern: "npm run build"` 匹配到了 `npm run build-all`，`src/foo` 匹配到了
  `src/foobar.ts`。
- **同类问题：** `apps/tui/src/app.tsx`（`/memory edit`）—— 裸的
  `target.startsWith(memoryDir)` 让 `../memory2/project.md` 通过了检查，因为
  `memory2` 与之共享同一个字符串前缀。
- **同类问题：** `packages/core/src/agent/trace.ts` —— 会话 id 被直接拼接进
  读/写/删除路径，依赖每个调用方自行在到达 Core 之前拒绝路径穿越。
- **同类问题：** `packages/core/src/agent/trace.ts` —— rewind 检查点路径使用
  词法包含判断，可以通过父目录中的符号链接逃逸。
- **同类问题：** `packages/core/src/memory/store.ts` —— `@import` 与根记忆文件
  使用词法包含判断，但读取会跟随符号链接跳出工作区。
- **同类问题：** `apps/server/src/files.ts` —— 上传目录本身可能是指向工作区之外
  的符号链接，即便返回的相对路径看起来是安全的。
- **同类问题：** `packages/core/src/skills/manage.ts` —— enable/disable/remove
  直接拼接未经校验的技能 id，可能修改技能根目录之外的目录。
- **同类问题：** `apps/cli/src/authorized-dirs.ts` —— 祖先目录匹配使用了硬编码的
  分隔符，无法正确处理 Windows 路径和文件系统根目录。

## 3. 缓存 / memo 的键必须包含所有影响输出的输入

如果两个不同的请求哈希到同一个键，第二个请求会悄悄拿到第一个请求的答案。

- **正确做法：** 对**所有**影响输出的字段做哈希，而不仅是那些显眼的字段。
- **发现位置：** `packages/core/src/provider/cache.ts` —— 缓存键遗漏了
  `temperature` 和 `maxTokens`，导致后续用更大 `maxTokens` 的调用重放了之前
  被截断的回复。
- **同类问题：** `apps/tui/src/statusline-scheduler.ts` —— 缓存键遗漏了状态栏
  命令本身，替换或重新启用该命令后仍在复用过期输出。
- **同类问题：** 仅按模型/请求做键的 provider 响应缓存可能跨端点或跨租户重放
  数据；应把每一个影响响应的 provider 设置纳入一个不透明的身份标识。
- **同类问题：** 规范化后的 MCP prompt 名称可能冲突（`foo_bar`/`foo-bar`）；
  应分配确定性的唯一命令名，并在查找时使用同一套映射。
- **同类问题：** 子代理（subagent）的派发 id 会在新的 manager/run 中从头计数。
  转写记录只能更新最新的、处于活跃状态的匹配派发，而不是恰好复用了同一个
  局部 id 的某张已完成的旧卡片。
- **同类问题：** 把源码行号编进 Finding id 会导致无关行插入后同一个漏洞被
  重复报告。应优先使用稳定的规则、路径和规范化证据构成身份，行号仅作为位置信息。

## 4. 序列化与反序列化必须严格互逆

如果写入方使用 `JSON.stringify`，而读取方只是剥掉外层引号，那么任何含 `"` 或 `\`
的值在「渲染→重新加载」的往返中都会被破坏。

- **正确做法：** 有意识地配对编码器和解码器；写入方做了 JSON 编码，读取方就必须
  `JSON.parse`。添加一个含引号/反斜杠值的往返（round-trip）测试。
- **发现位置：** `packages/core/src/subagents/frontmatter.ts` 与 `import.ts`。
- **同类问题：** Git 路径可能包含换行符，因此按行分割的 worktree porcelain 输出
  是不可逆的；应使用 `git worktree list --porcelain -z` 并端到端解析
  NUL 分隔的字段。
- **同类问题：** 结构化数字语法中的别名必须在解析出值之后再做规范化，而不是在
  源字符串上做字符替换；cron 中把 DOW 的 `7` 直接替换会破坏 `5-7`、`*/7`
  这类合法的区间和步长写法。

## 5. 光标 / 索引运算必须感知代理对与多字节字符

星光平面字符（emoji、CJK 扩展区）占两个 UTF-16 码元。裸的 `cursor ± 1` 会落在
两半*之间*，下一次编辑时就会破坏文本。

- **正确做法：** 按完整码点（code point）步进（`stepLeft`/`stepRight`/`moveLeft`/`moveRight`），
  对任何被钳制过的位置执行 `snapToBoundary`。用 `"😀"` 做测试。
- **发现位置：** `apps/tui/src/vim.ts`（插入模式 Escape、字符级 `p`）——
  这些辅助函数在 `editor.ts` 里早已存在，只是 vim 绕开了它们。
- **同类问题：** `apps/tui/src/components/MultilineComposer.tsx` —— 光标渲染按
  单个 UTF-16 码元索引，把 emoji 代理对切成了两半。
- **同类问题：** Vim 的 word/end 移动直接用字符串索引，可能停在代理对内部；
  应使用编辑器的码点辅助函数来分类和前进。
- **同类问题：** TUI 垂直移动把 UTF-16 偏移量当作终端列号使用，标签页标题
  按字素中间截断；应计算显示宽度，且只在字素（grapheme）边界处截断。

## 6. 每个 `addEventListener` 都需要一个配对的 `removeEventListener`

`{ once: true }` 只有在监听器*触发*时才会移除它。在正常的完成/清理路径上它永远
不会触发，于是挂在长生命周期 signal 上的监听器每执行一次操作就泄漏一个。

- **正确做法：** 给处理函数命名，并在 `finally` / settle 回调中
  `removeEventListener`（或使用 `AbortSignal.any`）。定时器、流、子进程同理。
- **发现位置：** `packages/core/src/subagents/manager.ts` —— 挂在共享父级
  `AbortSignal` 上的 abort 监听器。
- **同类问题：** `packages/core/src/agent/trace.ts` —— 删除会话前必须关闭缓存的
  追加写文件描述符，否则重建同一个 id 后仍会继续写入已被 unlink 的 inode。

## 7. 在序列化 / 请求边界处强制执行协议不变量

在操作中途持久化的状态（两次写入之间发生取消 / 错误 / 触达上限）可能违反下游
消费者所要求的不变量。只修其中一条写入路径，其他所有路径依然暴露在外。

- **正确做法：** 在数据离开系统的地方集中强制执行不变量，这样无论数据是怎么
  产生的，不变量都成立。对格式良好的输入，这一步应当是空操作（no-op）。
- **发现位置：** `packages/core/src/provider/mapping.ts`（`toWireMessages`）——
  一条没有对应 `tool` 结果的 assistant `tool_calls`（回合在执行途中被取消或
  触达上限）会让 OpenAI 兼容 API 在 `/resume` 时返回 400。现在未应答的
  tool_calls 和孤立的 tool 结果会在构建请求前被丢弃。
- **同类问题：** 流式 EOF 在没有收到必需的 `[DONE]` 终止符时就被视为完成，
  把断开的连接变成了一次「成功」的部分响应。
- **同类问题：** tool-call id 在整个会话范围内不保证唯一。应在每个 assistant
  回合内部配对结果；全局的「已应答 id」集合会在早先回合复用了某个 id 时，
  让一次被中断的调用看起来像已完成。
- **同类问题：** 会话审计导出通过一个全局 id 映射来配对工具结果，导致后续回合
  复用某个 id 时改写了先前调用的证据。审计/报告代码必须保持同样的
  「按 assistant 回合配对」边界。
- **同类问题：** 一个可选的安全字段如果存在但格式非法，必须拒绝该请求。
  此前非法的 WebSocket `selectedHunks` 会把一个部分权限响应放大为对整个
  补丁的批准。
- **同类问题：** 未知的子代理模式此前默认落到可写的 `edit`；枚举型安全设置
  必须拒绝未知值，而不是选择一个宽松的兜底值。

## 8. `JSON.parse` 成功不代表你拿到的是对象

`null`、`42`、`"x"`、`[]` 都是合法的 JSON。随后展开 `...parsed.field` 的代码会
抛出一个难以定位的 `TypeError`。

- **正确做法：** 解析配置类输入后，先断言它是一个非 null、非数组的对象再使用；
  否则返回 `{}` 或抛出描述性错误。
- **发现位置：** `apps/cli/src/config.ts`（`readJson` / `readSettingsFile`）。
- **同类问题：** `apps/cli/src/mcp-config.ts`（`readConfigDoc`）—— JSON 的
  `null` / `[]` / `"x"` 被当作配置文档返回，随后在访问 `doc.mcpServers` 时崩溃。
- **同类问题：** `apps/server/src/routes/settings.ts`（`readConfigDoc` /
  `mutateMcpServers`）—— 非对象形态的项目配置 JSON 会让 `/api/hooks`、
  `/api/mcp` 等设置路由崩溃。
- **同类问题：** `apps/cli/src/commands/run.ts`（`--mcp-config`）、
  `apps/cli/src/commands/config.ts`（`config set`）以及
  `apps/server/src/config.ts`（`setConfigValue`）—— 非对象 JSON 通过了解析步骤，
  却在稍后的 MCP 合并或配置变更中失败。
- **同类问题：** `packages/core/src/runtime/client.ts` —— `null` 之类的合法 JSON
  或伪造的响应形态可能让 readline 回调崩溃，或用非法数据 settle 一个挂起的
  runtime 请求。
- **同类问题：** `packages/core/src/agent/trace.ts` —— 未经校验的会话元数据可能
  让列表功能崩溃，或伪造出一个稍后被裁剪逻辑使用的 id。
- **同类问题：** `packages/core/src/agent/trace.ts` —— `messages.jsonl` 中合法的
  JSON 标量和数组被当作伪造的 `ChatMessage` 值重放。
- **同类问题：** `packages/core/src/mcp/http.ts` —— 纯 JSON 传输接受了 `null`，
  以及属于另一个 JSON-RPC 请求 id 的响应。
- **同类问题：** `packages/core/src/provider/sse.ts` 与 `mapping.ts` —— 合法的
  JSON 非对象值会让流式处理崩溃，而非有限的 token 计数会污染成本与预算核算。
- **同类问题：** `packages/core/src/tools/lsp/client.ts` —— 帧化的 JSON `null`
  到达了 stdout 事件分发器，可能在请求 Promise 之外抛出异常。
- **同类问题：** `packages/core/src/mcp/tools.ts` —— 畸形的 `tools/list` 数据在
  后续的映射循环中逃出了按服务器隔离的失败边界。
- **同类问题：** `apps/server/src/config.ts` 与 CLI doctor —— JSON `null` 尽管
  解析本身成功，仍然进入了对象展开/属性访问。
- **同类问题：** `packages/eval-harness/src/config.ts` 把任意 JSON 强转为
  `EvalConfig`；标量会让 provider 选择崩溃，畸形的嵌套定价数据可能污染成本核算。
  应过滤标量字段并校验每一个价格。
- **同类问题：** `packages/core/src/skills/manage.ts` —— 非对象形态的 `skill.json`
  值会让 enable/disable 崩溃，而不是被修复。
- **同类问题：** `apps/tui/src/config.ts` —— 与 CLI 和 server 不同，合法的 JSON
  标量或数组被直接传入分层合并逻辑，`null` 在第一次属性访问时就让 TUI 启动崩溃。
- **同类问题：** `packages/shared/src/config-layers.ts` —— 一个形态是对象的配置
  仍可能提供非数组的权限规则、非对象的 MCP 映射，或畸形的 MCP 条目/hook，
  导致合并或下游消费者崩溃。应校验每一个结构化字段，并保留低优先级层中的有效值。
- **同类问题：** 只是安全地忽略非对象配置还不够——如果 doctor 仅仅因为
  `JSON.parse` 成功就把它报告为有效，问题依旧。配置诊断也必须校验预期的
  顶层形态。
- **同类问题：** 仓库配置清洗器曾在不校验值类型的情况下复制所谓安全偏好，
  而被选中的 `null` profile 会在清洗前直接导致崩溃。应逐字段校验保留值，
  并且只把对象形态的 profile 条目视为可选择的配置层。

## 9. 「只读 vs 有副作用」分类：核实每个命令的真实效果

无参数 ≠ 列表操作。裸的 `git stash` 等价于 `git stash push`，会修改工作树；
把「无参数 = 只读」的假设写进代码后，它被免确认自动执行了。

- **正确做法：** 按命令的实际副作用逐个子命令分类。拿不准时按有副作用处理
  （要求确认）—— 失败关闭（fail closed）。
- **发现位置：** `packages/core/src/tools/run-command.ts`（`classifyGit`）。
- **同类问题：** `packages/core/src/tools/run-command.ts`（`classifyGh`）——
  `gh api --method=POST` / `-XPOST` 以及 `--field=...` 形式没有被解析为
  有副作用，可能被误判为只读的 GET 请求。
- **同类问题：** 重复出现的 `gh api -X/--method` 标志——只检查第一个会让
  后面的 POST 覆盖一个已被自动批准的 GET 分类。
- **同类问题：** `apps/server/src/routes/git.ts` —— 客户端文件名被直接作为 Git
  pathspec 传入，以 pathspec 魔法字符开头的文件名会改变命令的作用范围。
- **同类问题：** 命中允许列表的前缀并不等于授权一个带未加引号控制操作符的
  shell 程序。在内置、用户、会话或规则级自动批准之前，必须先拒绝复合语法和重定向。

## 10. 钳制参与排序 / 尺寸 / 预算计算的外部数字

来自用户编写文件的无界数值可能压倒一个本该只作平局裁决（tie-breaker）的分数，
或者冲破预算。

- **正确做法：** 在加载边界处钳制到预期区间（`Math.max(lo,
  Math.min(hi, x))`），而不是信任输入。
- **发现位置：** `packages/core/src/skills/load.ts` —— 精心构造的 `priority: 500`
  压过了真实的匹配信号（priority 的设计区间是 `[0,100]`）。

## 11. 解析器要处理空 / 未初始（unborn）/ 零值状态

全新仓库（无提交）、空集合、空字符串、单元素、零次试验——这些都会产生
正常路径从未见过的输出形态。

- **正确做法：** 为每个解析器或统计函数枚举零/一/未初始的情形，并加以测试。
- **发现位置：** `apps/server/src/rest.ts`（`gitStatus`）—— `## No commits yet on main`
  把分支解析成了 `"No"`。（另见 `packages/eval-harness` 各处的空集合防护。）
- **同类问题：** 按行分割的 Git porcelain 解析把普通文件名中的 ` -> ` 当成了
  重命名语法；应使用 NUL 分隔的机器格式。

## 12. 格式化数字的符号要在舍入*之后*决定

`value >= 0 ? "+"+fixed : fixed` 对一个没有变化的差值打印 `+0`，对一个舍入到零的
微小负值打印 `-0.0000` —— 两者都有误导性。

- **正确做法：** 先舍入，如果舍入后的值是 `0`，输出无符号的零。
- **发现位置：** `packages/eval-harness/src/{report,ab}.ts`（`signed`）。

## 13. 注释/文档与测试矛盾时，以测试为准

一条文档注释声称「单方运行的任务 = 平局」，而测试断言它记在实际运行它的
variant 名下。不要为了迎合注释而「修」代码——先确认意图（测试编码了意图），
然后修注释。

- **发现位置：** `packages/eval-harness/src/ab.ts`（`AbSummary` 的文档注释 vs
  `compareVariants` 的实际行为）。

## 14. 解析出的数字元数据必须是有限值，而不仅仅是 number 类型

JSON 可以把 `1e999` 之类的巨大数字字面量解析成 `Infinity`；`typeof` 仍然是
`"number"`，但新鲜度检查和光标/索引运算都会因此出错。

- **正确做法：** 对缓存时间戳、TTL、索引、光标及其他解析出的数字元数据，
  在参与运算前用 `Number.isFinite` 校验。
- **发现位置：** `packages/core/src/provider/cache.ts` —— 非有限的缓存 `ts`
  可能让一条被投毒的缓存条目看起来始终新鲜。
- **同类问题：** `apps/cli/src/version-check.ts` —— 无穷大的 `checkedAt` 时间戳
  让更新检查缓存永远新鲜。
- **同类问题：** `apps/server/src/recents.ts` —— 无穷大的 `lastOpened` 时间戳
  永久霸占最近工作区排序的首位。
- **同类问题：** `apps/cli/src/schedule.ts` —— 持久化的任务预算为无穷大时，
  成本熔断彻底失效，因为没有任何有限花费能达到 `Infinity`。
- **同类问题：** `apps/server/src/ws.ts` —— `selectedHunks` 只校验了外层数组，
  允许负数、非整数和无界索引进入 Core。

## 15. 共享的安全守卫可能需要更窄的、按能力定制的例外

直接复用一个严格的守卫可能悄悄让新能力完全不可用。网页抓取器必须拒绝
loopback 地址，而浏览器验证工具必须能够检查一个经用户确认的本地开发服务器。

- **正确做法：** 保持严格的共享默认值，在能力边界处添加尽可能小的显式例外；
  不要放宽共享守卫本身。
- **发现位置：** `packages/core/src/tools/builtins/browser.ts` —— 复用
  `checkFetchUrl` 使文档中描述的 `http://localhost:5173` 工作流完全无法使用。

## 16. 校验每一跳网络请求，而不仅是初始 URL

一个已批准的公网 URL 可能重定向到私有地址，一个已加载的页面可能请求私有的
子资源。只检查第一个 URL 会让 SSRF 守卫在导航开始后形同虚设。

- **正确做法：** 在浏览器/网络请求边界处对重定向和子资源同样执行 URL 策略，
  而不仅是初始导航。
- **发现位置：** `packages/core/src/tools/builtins/browser.ts` —— 初始 URL 检查了，
  但 Playwright 后续跟随的请求没有重新应用该策略。
- **同类问题：** `web_fetch` 把重定向交给 `fetch(..., redirect: "follow")`，且不检查
  DNS 结果；一个看似公网的 URL 可能在单次词法检查后解析或跳转到环回地址。应拒绝
  每一个非公网解析结果，并在跟随重定向前逐跳手动校验。

## 17. 在最细粒度的可观测边界上执行护栏

只在高层迭代之间检查预算或取消信号，会让单次迭代在停止条件已经可观测之后
继续发起调用。同样，取消父操作却不向其子进程发信号，会让用户干等到超时。

- **正确做法：** 在每次用量更新时检查预算，把取消传播到活跃的子进程树中，
  并在做预检工作之前先检查 signal 是否已经处于 aborted 状态。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` 和
  `packages/core/src/tools/run-command.ts` —— 循环的预算/取消此前只在一次
  完整的 agent 运行或验证超时之后才生效。
- **同类问题：** `packages/core/src/provider/http.ts` —— 调用方的取消被当作
  可重试的网络错误处理，且重试退避（backoff）忽略了 abort signal。
- **同类问题：** `packages/core/src/agent/loop.ts` —— finalize 阶段的自动验证与
  自动 lint 命令漏传了运行 signal，把取消延迟到了命令退出。
- **同类问题：** `apps/tui/src/app.tsx` —— Ctrl+C 中止了运行控制器，却让前端的
  `ask_user` Promise 悬而未决，运行本身始终观测不到取消。
- **同类问题：** agent 循环没有把它的 signal 放进 `ToolContext`，导致一个执行中
  的前台命令在取消后仍然存活，尽管执行器本身支持取消。
- **同类问题：** 一次成功的非流式 provider 响应在收到响应头后就清除了超时，
  留下一个停滞的 JSON body 无法取消；应在 body 消费完成之前保留超时和
  调用方 signal。
- **同类问题：** 响应体的消费发生在重试辅助函数返回之后，导致停滞、截断或
  畸形的 `200` body 既不重试也到不了模型回退；解析必须留在单次尝试的边界之内。
- **同类问题：** 回退（fallback）错误处理在调用方已取消回退尝试的情况下，仍然
  重新抛出主模型的失败；调用方的 abort 必须优先于保留更早的可重试错误。
- **同类问题：** `DOMException.code` 是数字，直接转发任意错误码会把一个执行中
  的 `AbortError` 分类为失败的会话；被中止的运行 signal 必须强制使用稳定的
  字符串错误码 `cancelled`。
- **同类问题：** TUI 的异步 MCP prompt 在 prompt 解析完成之后才预约运行槽位，
  且 Ctrl+C 计数是全局的；应在 await 之前先预约，并把中断状态绑定到发起它的
  标签页/运行身份上。

## 18. 把内部状态排除在收敛判断的输入之外

把编排状态持久化在工作区内部，同时又把它计入工作区指纹，会让每一次迭代
看起来都「有进展」。

- **正确做法：** 把内部 trace、上传文件和循环状态文件排除在内容指纹之外，
  并独立地限制实时输出的事件数量和分块大小。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 持久化的循环更新与
  无上限的验证器输出块可能破坏「无进展检测」，或让客户端无限膨胀。

## 19. 数字选项解析器必须消费整个字符串

`parseInt("2x")` 和 `parseFloat("1.5usd")` 会悄悄接受一个合法前缀。除非单独检查，
它们还会放行非有限值。

- **正确做法：** 先校验完整的数字语法，再做转换，并按需要求结果是安全整数或
  有限浮点数。
- **发现位置：** `apps/cli/src/index.ts` —— 全局的正整数/浮点数选项解析器。
- **同类问题：** `apps/cli/src/schedule.ts` —— cron 片段使用 `parseInt`，接受了
  `1x`、`1-2x`、`*/2x` 之类的值。
- **同类问题：** CLI 的 `serve --port` 和 `sessions prune` 接受了垃圾后缀，
  因为 `parseInt("12junk")` 返回 `12`。
- **同类问题：** CLI 的权限 hunk 选择和 `ask_user` 选择接受了 `1abc` 之类的
  尾随垃圾字符；必须完整校验每一个 token，并对照实际提供的索引范围，
  才能批准或选中。
- **同类问题：** eval 的 `--repeat` 使用 `Number()`，即使该选项表示十进制迭代次数，
  仍会接受十六进制和指数形式。

## 20. 生命周期清理在删除共享状态前必须先证明所有权

一个过期的 worker 可能在其租约（lease）被替换后才完成，然后误删新所有者的锁，
导致同一份持久化状态被并发修改。

- **正确做法：** 用不可猜测的所有权令牌标识租约，只回收确已死亡的所有者，
  并在清理删除锁之前再次比对令牌。
- **发现位置：** `packages/core/src/agent/loop-state.ts` —— 自治循环租约。
- **同类问题：** `apps/cli/src/loop-worktree.ts` —— 清理现在同时要求保留的
  worktree 根目录和 Loop 专用的 `seekforge/loop-*` 分支前缀，因此不会误删
  其他 SeekForge 工作流的检出目录。
- **同类问题：** 并发的首次 LSP 调用复用了一个在 initialize 握手完成之前就被
  插入注册表的会话；应共享启动 Promise。
- **同类问题：** LSP 注册表只按语言做键，导致并发的工作区互相销毁对方的
  服务器；键中必须包含工作区身份。
- **同类问题：** 缓存的 LSP 文档在定义/引用请求前没有刷新；应跟踪最近的文本，
  并在磁盘编辑后发送 `didChange`。
- **同类问题：** 同一 URI 的并发诊断请求覆盖了单一等待者；应合并进行中的请求，
  或为该身份保留所有等待者。
- **同类问题：** 顶层 agent 清理会全局销毁共享的 LSP 和浏览器进程，而并发的
  运行仍在使用它们；应为每次运行保留一个令牌，只在最后一个匹配的所有者
  释放后才拆除。
- **同类问题：** LSP 服务器退出/销毁时把挂起的诊断请求 resolve 成一个空的
  成功结果；生命周期失败必须 reject 所有受影响的等待者。
- **同类问题：** 两个连接可以同时 resume 同一个持久化会话，交错写入 JSONL、
  元数据和检查点；应获取一个运行作用域的会话租约。
- **同类问题：** 服务器关闭时只关了 HTTP 监听器，没有中止活跃的触发器运行；
  应跟踪受管的运行句柄，并在 close 之前 await 它们的清理。
- **同类问题：** webhook 投递 ID 在负载校验之前就被占用，一次畸形请求就永久
  消耗掉了一个合法的重试标识符。
- **同类问题：** 前台 shell 可能退出而某个后台后代进程仍持有输出管道，导致
  读取端的 join 绕过命令超时；应在 join 管道读取器之前先清理自己拥有的进程组。
- **同类问题：** 后代进程可以调用 `setsid()` 逃出该进程组，同时仍持有
  stdout/stderr；输出排空本身也需要截止时间，绝不能无条件地 join 一个可能
  永远看不到 EOF 的读取器。
- **同类问题：** 只在 provider 边界添加取消支持是不够的，除非 agent 循环把它的
  运行 signal 传入每一个活跃的模型请求，包括流式读取和非流式 body 消费。
- **同类问题：** 过期锁的恢复本身也需要一个独占的恢复租约；否则两个恢复者
  可能竞速，第二个在验证旧所有者后可能把第一个刚获得的新锁重命名掉。
- **同类问题：** JSON-RPC 的请求顺序不等于响应顺序。串行化所有 MCP 请求会让
  一个耗时的工具调用阻塞 ping/list/取消，尽管请求 ID 本身允许独立的
  并行处理。
- **同类问题：** 取消必须在客户端移除匹配的挂起请求、定时器和监听器，发送
  `notifications/cancelled`，并且只 abort 服务器端具有相同请求 ID 的工具上下文。
- **同类问题：** 子进程 runtime 的 stdin 循环在阻塞执行单个请求时无法观测取消；
  应通过有界的 worker 池分发，让请求 ID 在输出排空期间保持活跃，并让
  取消/EOF 设置对应命令的终止标志。
- **同类问题：** 客户端侧的 JSON-RPC 超时也是一种取消；应在 reject 之前带上
  原始请求 ID 发送 `notifications/cancelled`，避免服务器继续做已被放弃的工作。
- **同类问题：** HTTP 取消通知不能 await 到完成；否则一个无响应的服务器会在
  原始的取消或超时到达调用方之前再叠加一个完整的超时时长。
- **同类问题：** LSP 请求取消必须移除挂起的请求、定时器和 abort 监听器，
  然后带上原始 ID 发送 `$/cancelRequest`。
- **同类问题：** SSE 对端可以永远流式发送一个不终止的事件；应同时限制完整
  事件的大小和未完成缓冲区的大小，并在溢出时取消读取器，让内存占用和
  传输生命周期都有界。
- **同类问题：** 在文件系统清理成功之前就把租约标记为已释放，会把一次瞬时的
  清理失败变成一个活着的孤儿。应保持本地所有权，并让 `release()` 可重试，
  直到令牌所拥有的目录确实被删除。
- **同类问题：** 服务器关闭时中止了 socket，却没有 await 游离的 WebSocket/REST
  操作；应跟踪每一个已启动的操作并排空整个集合。
- **同类问题：** 一个共享的可变重试回调把并发的 AgentCore 运行全部路由到
  最后注册的那个队列。应把重试投递绑定到发起它的异步运行上下文。
- **同类问题：** runtime 销毁时在新派生的子进程来得及消费排队的取消消息之前
  就强制关闭了它（并行负载下）。关闭要有界，但应为有序的 stdin 消息排空
  留出一个现实的宽限窗口。

## 21. 在成本或所有权变得可观测的事件点建立检查点

只在整个 agent 运行结束后才持久化，一旦进程在 provider 事件与最终报告之间
退出，会话 id 和已计费的用量就丢了。

- **正确做法：** 立即为会话身份建立检查点，并以幂等方式持久化累计用量更新；
  最终写入应重复相同的绝对总量。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 崩溃恢复可能打开一个
  新会话并少算 Loop 预算。

## 22. 一旦声明请求已中断，就绝不能再重放它

重连队列的生命周期可能超过创建它的 UI 操作。事后重放该请求会启动不可见的
工作，并让控件与服务器状态脱节。

- **正确做法：** 当某个连接失败时，清空绑定在该连接上的排队请求；用户在断连
  期间有意提交的请求属于下一次连接尝试。
- **发现位置：** `apps/desktop/src/lib/ws.ts` —— 一个排队的 Loop 可能在 store
  已经清除其运行状态之后才启动。
- **同类问题：** `apps/desktop/src/store.ts` —— 在 socket 运行仍活跃时重置会话，
  让迟到的事件填充了刚被清空的转写记录。
- **同类问题：** Desktop 的 backtrack 和 continue 回调解析到的是 await 之后
  「当时活跃」的标签页/工作区，而不是 await 之前捕获的身份。
- **同类问题：** 工作区作用域的视图请求可能重绘一个新选中的工作区；应按
  工作区重新挂载视图，并使聊天作用域的回调失效。
- **同类问题：** 一次延迟的图片上传从共享组件实例读到了下一个标签页的草稿；
  异步 composer 状态必须按标签页身份做键。
- **同类问题：** 绑定标签页的主页视图接受了 workspace prop，但它的最近会话/
  技能/代理请求仍然回退到全局活跃工作区；捕获到的标签页工作区必须传入
  每一个作用域请求。
- **同类问题：** 会话、代理和技能的详情请求在选中项变化后才提交；应把每个
  响应绑定到一个 generation 和选中 id 上。
- **同类问题：** Git 状态和 hooks 加载在工作区切换后才提交，随后破坏性操作或
  保存操作作用到了新激活的工作区。应捕获工作区身份，同时守卫响应提交和变更。
- **同类问题：** TUI 的草稿和运行设置跨越了标签页边界，因为编辑器状态是全局的，
  而模型/审批模式是在 await 一次 MCP 加载之后才读取的；草稿要按标签页做键，
  所有运行输入要在第一个 await 之前快照。

## 23. PID 不是持久的进程身份

操作系统会复用 PID。一个含有「活着但被复用的 PID」的过期锁可能永久保持活跃，
而一个只写了一半的锁可能被误判为已死的所有者而被抢走。

- **正确做法：** 随 PID 一起持久化进程启动身份，恢复时两者一起比对，并在
  有限的宽限期内把新出现的畸形锁视为活跃。
- **发现位置：** `packages/core/src/agent/loop-state.ts` —— 持久化的 Loop 租约。
- **同类问题：** `apps/cli/src/schedule.ts` 在调度器租约上重复了只查 PID 的检查；
  那里同样要持久化并比对进程启动身份。
- **同类问题：** 恢复锁本身也可能因所有者崩溃而被遗弃；应给畸形的恢复状态
  一个宽限期，过期后再回收。

## 24. 统计「已完成」的单元，而不是「已开始」的单元

在 `iteration.start` 时就为迭代号建检查点，意味着进程在该迭代产出结果之前
崩溃时，这个名额已经被消耗掉了。

- **正确做法：** 可恢复的会话与成本事件应立即建检查点，但单元计数器只在
  证明完成的事件点推进。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 被中断的 Loop 迭代。

## 25. 追加式日志只能恢复到最长有效前缀

跳过一条畸形的 JSONL 记录并接受后续记录，可能把本来并不相邻的事件拼在一起，
在一次部分写入之后破坏协议顺序。

- **正确做法：** 在第一条畸形记录处停止，只重放最长的有效前缀；元数据替换
  要用「临时文件 + rename」保证原子性。
- **发现位置：** `packages/core/src/agent/trace.ts` —— 会话恢复 trace。
- **同类问题：** 检查点恢复跳过了畸形行并接受了后面的快照，使 rewind 信任了
  因果前缀缺失的状态。

## 26. 逻辑路径相等不等于物理工作区相等

符号链接别名以及 `/var` 与 `/private/var` 这类平台别名可以指向同一个目录，
却通不过字符串相等检查。

- **正确做法：** 在持久化、给租约做键或校验加载状态之前，先用 `realpath`
  规范化已存在的工作区根目录。
- **发现位置：** `packages/core/src/agent/loop-state.ts` —— 非 Git 的 Loop 管理。

## 27. 有界的文件前缀不是内容指纹

只哈希第一个分块加文件大小，会漏掉大文件后部的等长修改，从而触发错误的
「无进展」停止。

- **正确做法：** 以有界内存的分块方式，让完整文件流过哈希。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— Loop 收敛检测。

## 28. 不仅要校验操作数，还要校验运算结果

两个有限的正数相加/相乘可以溢出为 `Infinity`。如果后续某一层把非有限值当作
「未设置」处理，一次溢出就会悄悄拆掉一道护栏。

- **正确做法：** 对产生预算、上限、时间戳或尺寸的加法和乘法，校验其结果。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 累加型 resume 预算。
- **同类问题：** 调度间隔的计数是有限的，但换算成毫秒后可能超出安全整数范围；
  乘积也要校验。

## 29. 元数据调用可能跟随符号链接跨越沙箱边界

`stat` 会跟随符号链接，因此本意是给工作区条目做指纹的代码，可能意外读取了
工作区之外的目标。而完全忽略符号链接又会漏掉链接本身的变化。

- **正确做法：** 用 `lstat` 分类条目，对符号链接哈希其 `readlink` 输出；
  绝不把链接目标当作工作区内容打开。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 收敛指纹计算。
- **同类问题：** 缓存的服务器搜索结果和项目配置/触发器路径在重新打开时没有
  做物理路径复验，后续的符号链接替换可以逃出工作区；应拒绝符号链接并用
  `O_NOFOLLOW` 打开。
- **同类问题：** 内部状态根目录需要比普通工作区解析更严格的语义。会话 trace
  和 Git worktree 根目录必须拒绝任何含符号链接的目录组件，复验物理包含关系，
  并在读写之前使用 no-follow 的叶节点打开或原子替换。
- **同类问题：** 共享临时目录下的可预测根目录本身就是一道安全边界。创建每一级
  组件时都不跟随符号链接，并要求当前操作系统用户所有加私有（`0700`）目录权限。
- **同类问题：** 「先校验路径、稍后再重新打开」会留下替换窗口。应以 no-follow
  标志打开叶节点和父目录，比对描述符/路径身份，并把截断推迟到打开的文件
  通过物理复验之后。
- **同类问题：** 任务的 `@path` 展开在 `stat` 和 `readFile` 之前只做了词法包含
  判断，允许工作区或额外只读目录内的符号链接注入该根之外的文件。应对两个
  根目录和被引用文件都做物理解析，读取前再次检查包含关系。
- **同类问题：** 无认证的静态文件服务在其根目录内部跟随了符号链接。应规范化
  静态根目录，并对每一个被请求的资源使用 no-follow 描述符读取加
  路径/描述符身份检查。
- **同类问题：** 服务器的原始上传边界把符号链接化的上传目录的物理目标当作
  可信目录，且目录列举后重新打开一个已验证的路径时没有再检查身份。
- **同类问题：** 项目 Skill 发现打开了指向工作区之外的符号链接 `SKILL.md`；
  应对照其所属根目录校验物理内容文件。

## 30. 相关的变更必须共享同一个串行化域

对变更同一底层资源的操作使用各自独立的锁，并不能防止竞态。Git worktree 的
create 与 merge、remove 修改的是同一份基础仓库元数据，尽管它们的 API 路由和
目标 id 各不相同。

- **正确做法：** 找出被变更的物理资源，按该身份建一把锁，并让这一族的每个
  操作都获取同一个工作区/会话守卫。
- **发现位置：** `apps/server/src/worktrees.ts` —— create、merge、remove 现在共享
  基础仓库锁；create 还会持有基础工作区守卫。
- **同类问题：** REST 的 stage/unstage/discard/commit 在该锁之外变更同一份
  index 和 refs；Git 路由与 worktree 操作必须使用按物理公共 Git 目录做键的
  同一个协调器。
- **同类问题：** `PUT /api/file` 在没有活跃会话守卫的情况下写入工作区文件，
  允许编辑器覆盖 Agent 的并发修改。每一个独立的工作区变更入口都必须获取
  同一个守卫。
- **同类问题：** Desktop 的 Git stage/unstage/discard 与 commit 使用了各自独立的
  pending 标志，允许并发发起相互冲突的写操作。
- **同类问题：** backtrack 把恢复文件和截断 trace 作为两次独立变更执行，
  记忆压缩在归档持久化之前就删除了事实。应先执行可能失败的前置步骤，
  再在持有共享守卫的情况下提交破坏性更新。
- **同类问题：** TUI 的 `/rewind` 缺少相邻历史命令都有的活跃运行守卫，
  允许检查点恢复与 Agent 的写入竞速。

## 31. 语法的派生语义应基于解析后的值

文本写法不等于语义限制。`*` 和 `*/1` 覆盖的 cron 域相同，尽管源字符串不同。

- **正确做法：** 从规范化后的值集合推导「无限制/有限制」标志。
- **发现位置：** `apps/cli/src/schedule.ts` —— DOM/DOW 的 OR 语义让 `*/1` 使一个
  指定星期几的自治任务每天都运行。

## 32. 可变的序号不是持久身份

索引会在插入/删除后变化。按显示索引排队两个变更操作，重新编号后第二个操作
可能作用到另一个条目上。

- **正确做法：** 使用稳定 id/内容指纹，串行化变更，身份存疑时失败关闭
  （fail closed）。
- **发现位置：** `apps/desktop/src/views/MemoryView.tsx` —— 并发删除记忆事实。

## 33. 不可信数据中不能包含它自己的围栏分隔符

把某个提示词区段标注为「不可信」毫无意义——只要负载文本能闭合该区段，
就能在区段之外接续指令式文本。

- **正确做法：** 对每一个被插值的键和值，按分隔符语法进行编码。
- **发现位置：** `apps/server/src/triggers.ts` —— webhook 标题可以向 headless
  编辑任务注入 `</untrusted-event-data>`。

## 34. 在每次可观测的用量更新时聚合成本

只在完成时记账，会在后台子任务被中止或比父任务活得更久时丢失已经计费的工作。

- **正确做法：** 立即合并单调递增的累计增量，完成时绝不把同一个子任务的
  总量再加一遍。
- **发现位置：** `packages/core/src/agent/loop.ts` —— 后台子代理用量。

## 35. 同步调用无法执行外部的墙钟预算

在一个可能灾难性回溯的正则或阻塞式子进程等待外面检查 `Date.now()`，
无法在调用占有线程期间打断它。

- **正确做法：** 执行前先拒绝不安全的正则语法；子进程方法要运行在自有的
  进程组中，配备有界的输出排空、取消轮询和内部截止时间。
- **发现位置：** `apps/server/src/files.ts` 的正则搜索和 Rust runtime 的 Git 调用。
- **同类问题：** Core 的 `search_text` 在 Node 主线程上执行任意正则表达式；
  应在构造表达式之前拒绝反向引用和有歧义的嵌套量词。
- **同类问题：** 自定义命令的超时只杀掉了 shell，并把已捕获的 stdout 当作成功。
  应拥有整个进程组、限制输出、终止后代进程，并拒绝任何超时或非零退出。

## 36. 持久化缓存命中需要完整的契约校验

时间戳有效不代表缓存的负载有效。不完整的对象、非有限或不可能的计数器都可能
让消费者崩溃或污染预算。

- **正确做法：** 校验完整的响应形态和数字不变量；任何不匹配都当作缓存未命中。
- **发现位置：** `packages/core/src/provider/cache.ts` —— 缓存的 `ChatResponse` 数据。

## 37. 传输成功不等于验证成功

一个合法的工具结果信封，描述的可能是一个失败的或仍在运行的进程。

- **正确做法：** 在记录验证或 lint 成功之前，要求满足操作特定的成功条件，
  包括前台完成和退出码为零。
- **发现位置：** `packages/core/src/agent/loop.ts` —— 非零退出和后台命令曾经
  满足了 verify/lint 完成门槛。
- **同类问题：** 数字选项解析器必须对非法输入抛出异常，而不是返回
  `undefined`，Commander 会把后者当作选项未提供。

## 38. 环境变量中的命令字符串需要 argv 解析器

`EDITOR="code --wait"` 是「命令加参数」，不是一个可执行文件名。按空白分割
还会破坏带引号的路径和参数。

- **正确做法：** 在不调用 shell 的前提下把引号与转义解析成 argv；拒绝畸形的
  引号写法，并用解析出的参数启动可执行文件。
- **发现位置：** `apps/tui/src/app.tsx` —— `/memory edit` 和 `/config edit` 把
  完整的 `$EDITOR` 值当作可执行文件传了进去。

## 39. 内部错误必须在公共边界处完成转换

重构一个门面（facade）可以保持返回值不变，却意外暴露一种新的异常类型。
把领域错误映射为 HTTP 状态码或 CLI 输出的调用方，随即把一个已处理的
客户端错误变成了未知的服务器故障。

- **正确做法：** 在拥有该服务的边界处捕获底层的策略、文件系统和传输错误，
  转换为既定的领域错误；用契约测试覆盖状态码、错误码和消息语义。
- **发现位置：** `apps/server/src/file-upload-raw.ts` —— 共享路径守卫的
  `ToolError` 从 `saveUpload` 中逃逸，而不是抛出文档规定的 `UploadError(400)`。

## 40. 便利型解码器可能接受畸形编码

许多标准库解码器有意设计得宽容。解码成功并不能证明不可信输入遵守了
声明的线上格式（wire format）。

- **正确做法：** 校验语法，并与规范化的往返（round trip）结果比对，
  再接受编码输入。
- **发现位置：** `apps/server/src/file-upload-raw.ts` —— `Buffer.from(..., "base64")`
  忽略非法字符，接受了畸形的图片上传。

## 41. Effect 清理在依赖变化时也会运行，而不仅是卸载时

把进程级的清理放在一个依赖可变状态的 effect 里，意味着每次重新运行之前
都会先执行这段清理。而兄弟 effect 未必会重新运行来恢复被清掉的东西。

- **正确做法：** 依赖变化触发的清理只作用于该 effect 自己的资源，组件级的
  清理放在单独的卸载 effect 中。
- **发现位置：** `apps/tui/src/use-terminal-lifecycle.ts` —— 切换鼠标捕获会清掉
  终端标题，直到另一个标题依赖发生变化才恢复。

## 42. 渲染过程中不得修改已有的异步协调器

React 的并发渲染可能被放弃。在渲染期间修改一个长生命周期的协调器，
会让一次未提交的渲染使屏幕上仍在显示的状态失效。

- **正确做法：** 用 `useMemo` 创建与身份绑定的协调器，通过 ref 更新回调而
  不改变所有权，并在 effect 清理中使旧实例失效。
- **发现位置：** `apps/desktop/src/views/use-workspace-async.ts` —— 工作区切换
  在渲染提交之前就修改了上一个协调器。
- **同类问题：** 工作区打开、记忆变更/统计和余额请求在其所属工作区已切换后
  才提交；每一次完成和回滚都必须绑定到 generation 或工作区身份。
- **同类问题：** 安全、设置/MCP、代理、会话、诊断、演进、技能、文件、diff、
  待办以及嵌套的记忆控件，都允许迟到的成功、错误、清理或定时器回调去修改
  新激活工作区的 UI。要给每一次完成加作用域，而不只是请求 URL，还要包括
  报告下载这类浏览器侧副作用。

## 43. 回退分支必须保留请求的全部谓词

慢路径或绕过缓存的路径实现的仍是同一个请求。直接返回其原始中间结果会
悄悄丢掉过滤、排序或分页。

- **正确做法：** 让缓存分支和非缓存分支共享后处理逻辑，或显式重复每一个
  谓词并配以边界测试。
- **发现位置：** `apps/server/src/file-scan-search.ts` —— 一次扩大范围的
  非缓存遍历忽略了调用方的 `q` 过滤条件。

## 44. 先认证，再暴露资源状态

在认证之前就查找资源或检查其是否启用，会让状态码变成一个枚举探测器
（enumeration oracle），即便受保护的操作本身从未执行。

- **正确做法：** 先对着一个不泄露信息的兜底对象校验凭据，并对缺失、禁用、
  启用三种资源返回同样的认证失败。
- **发现位置：** `apps/server/src/routes/triggers.ts` —— 伪造的 GitHub webhook
  请求头在 HMAC 校验之前就能区分未知、禁用和启用的触发器 id。

## 45. 备选执行后端必须保持安全策略

更快的后端如果其协议无法表达当前生效的沙箱、权限、取消或资源策略，
就不能互换使用。

- **正确做法：** 路由到具备策略能力的后端，或者直接拒绝；绝不悄悄丢弃
  不受支持的约束。
- **发现位置：** `packages/core/src/tools/builtins/command.ts` —— Rust Runtime
  路径绕过了处于激活状态的操作系统命令沙箱。

## 46. 不透明分页需要进度守卫

忽略 `nextCursor` 会悄悄隐藏数据；无限信任它则会让一个畸形的服务器制造
死循环。

- **正确做法：** 消费每一个不透明游标，包括合法的空字符串；只有游标缺席才
  意味着分页结束。拒绝重复的游标，并施加一个有文档说明的页数/条目上限。
- **发现位置：** `packages/core/src/mcp/client.ts` —— 工具、资源和 prompt 的
  发现只返回了第一页。

## 47. 声明的能力是必须兑现的承诺

声明一项协议能力（capability）会导致对端发送请求并等待答复。声明一个
只实现了一半的特性比不声明更糟。

- **正确做法：** 只声明当前传输确实能服务的能力；保留协商出的版本/能力状态
  供后续请求使用。
- **发现位置：** `packages/core/src/mcp/http.ts` —— HTTP 声明了 roots 能力，
  却可能丢弃一个请求作用域的 `roots/list`，让一个遵循协议的服务器死锁。

## 48. 记忆化的启动 Promise 必须在每条失败路径上重置

`promise.then(success, failure)` 的双回调形式不会把 `success` 中抛出的异常
送进那个 `failure` 回调。即便传输层的本意是让下一次调用重试初始化，
被 reject 的 Promise 也可能永远留在缓存里。

- **正确做法：** 在握手校验之后追加一个最终的 `.catch(...)`，并清除所有
  部分生命周期状态（会话 id、协商版本、缓存的 Promise）。
- **发现位置：** `packages/core/src/mcp/http.ts` —— 一次畸形的 initialize 结果
  永久毒化了客户端，并保留了服务器的部分会话 id。

## 49. 宽泛的可写父目录会覆盖受保护的嵌套根目录

允许临时目录保持可写，也就允许了其下的每一个工作区可写——除非嵌套的
工作区被再次显式保护。

- **正确做法：** 调整挂载/profile 规则的顺序，让更窄的工作区策略胜过宽泛的
  临时目录许可，并直接测试「工作区位于临时目录内」这一情形。
- **发现位置：** `packages/core/src/tools/os-sandbox.ts` —— 位于 `/tmp` 或
  `TMPDIR` 之下的 `read-only` 工作区继承了父目录的写权限。

## 50. 除非 UI 做了排队，交互式提示就是一个串行化资源

并发启动多个各自等待确认的操作，可能覆盖唯一的「待确认提示」槽位，
让被顶掉的 Promise 永远得不到 resolve。

- **正确做法：** 串行化交互式授权，然后按请求的并发度运行已批准的工作；
  使用完成驱动的调度器，避免一个慢的兄弟任务用批处理屏障卡住无关的
  就绪分支。
- **发现位置：** `packages/core/src/agent/loop.ts` —— 并发的编辑团队成员竞争
  单槽位的权限 UI，且 `Promise.all` 卡住了新就绪的分支。

## 51. 异步结果需要完整的可变目标身份

当结果要写入某个标签页时，只检查工作区 id 是不够的：用户可以在同一工作区内
切换标签页，也可以在完成之前 A→B→A 地切换。

- **正确做法：** 同时捕获工作区和标签页身份，支持取消，省略为空的可选参数，
  并在请求失败时保留重试状态。
- **发现位置：** `apps/desktop/src/views/SettingsView.tsx` —— 一个缓慢的 MCP
  Prompt 可能覆盖另一个标签页的草稿，并把空的可选参数当作有效值。

## 52. 外部上下文在模型边界处必须始终以「数据」的形态可见

把第三方文本直接拼到用户任务后面，会让其中嵌入的指令获得与用户请求相同的
视觉权威，即便工具权限仍然受控。

- **正确做法：** 把外部内容序列化进一个显式的不可信数据信封中，提示词中
  省略不可信的传输错误信息，并强化系统规则。
- **发现位置：** `apps/server/src/agent.ts` 和 `apps/tui/src/app.tsx` —— MCP
  Resource 内容被直接拼接到任务消息上。
- **还发现于：** `packages/core/src/agent/auto-loop.ts` —— 验证器输出在没有显式
  不可信数据信封的情况下被拼进 Loop 后续提示词，使仓库可控的诊断文本看起来像
  用户指令。

## 53. 启动阶段的取消与清理先于主操作开始

只挂在最终运行上的取消，无法阻止组装该运行期间发生的 provider/工具发现。
后续的构建失败还可能泄漏此前已获取的资源。

- **正确做法：** 把运行 signal 贯穿到发现阶段，在每一次抛出时销毁部分构建的
  客户端，并在构建客户端之前隔离畸形条目。
- **发现位置：** `packages/core/src/mcp/tools.ts` 和 `apps/server/src/agent.ts` ——
  MCP 发现忽略了取消，且部分完成的 Agent 组装可能泄漏客户端。

## 54. 取消的可观测性从请求派发之后才开始

初始化期间的 abort 可以正确地阻止真正的请求被发出。此时使用固定定时器的
测试可能会去期待一个服务器从未见过的请求 id 的取消通知。

- **正确做法：** 断言传输层取消的副作用时，先同步等到服务器收到目标请求
  再 abort；延迟应从 abort 时刻起算，而不是从客户端构建或握手启动起算。
- **发现位置：** `packages/core/tests/mcp/http.test.ts` —— 一个 25 ms 的定时器
  与 initialize 握手竞速，使通知断言变得不确定。

## 55. 预算要覆盖完整的线上请求，而不仅是显眼的负载

消息并不是模型请求的全部：工具定义及其 JSON schema 每一轮都会被序列化，
可能占据上下文窗口的大头。

- **正确做法：** 在 provider 边界同时估算消息和已声明的工具；为两者都预留
  空间，并对过大的工具目录做确定性的收窄。
- **发现位置：** `packages/core/src/agent/loop.ts` —— 上下文压缩（compaction）
  只考虑了消息，因此一个巨大的 MCP 目录可能在 UI 报告空间充裕之后
  仍然超出窗口。

## 56. 每一次模型调用都应纳入用量与预算核算

辅助性的摘要、抽取、排序或评审调用同样消耗 token 和金钱，即便它们不是
主 agent 回合。

- **正确做法：** 从每一个成功的 provider 响应中返回用量，包括语义上畸形的
  响应，并在最终报告之前完成聚合。
- **发现位置：** `packages/core/src/agent/context.ts` 与 `memory/extract.ts` ——
  LLM 压缩和记忆抽取丢弃了用量，低估了 Loop 成本。

## 57. 出现在提示词中不等于被使用

把一条记录放进提示词，并不能证明它影响了模型的工作。把「曝光」当作「使用」
会让留存和质量指标自我实现。

- **正确做法：** 把被动曝光、显式检索和确证使用记录为三个独立的计数器；
  按真正想要的信号来做裁剪和评估。
- **发现位置：** `packages/core/src/agent/loop.ts` —— 每一条注入的记忆事实都被
  标记为已使用，即便它与任务毫不相关。

## 58. 追加式日志只能恢复其最长有效前缀

跳过一条畸形 JSONL 记录并接受后续行，会让「撕裂或损坏写入之后的状态」
覆盖最后的持久化状态。合法的 JSON 标量和不符合 schema 的对象同样是损坏，
不是可以无害忽略的记录。

- **正确做法：** 按顺序解析并校验每一条记录，在第一个 JSON 或 schema 失败处
  停止，并在接受下一个事件之前强制单调的序号/时间戳不变量。在后续追加之前，
  先原子地截断无效后缀；否则之后所有的有效记录都将永远不可达。
- **发现位置：** `apps/server/src/run-ledger.ts` —— 运行快照和 WS 重放事件原本
  会跳过中间的畸形记录，继续读取后面的状态。

## 59. 终态生命周期必须拒绝迟到的异步状态迁移

取消可能与 provider、子进程或游离的完成事件竞速。迟到的回调仍会执行，
但它已经无权决定生命周期。

- **正确做法：** 在中央 store 中强制执行允许的状态迁移；一旦运行已 succeeded、
  failed 或 cancelled，忽略与之冲突的终态更新。
- **发现位置：** `apps/server/src/run-ledger.ts` —— 一个后台运行可能先被标记为
  cancelled，随后又被一个迟到的完成事件改写为 succeeded。

## 60. 自主变更入口必须要求有限的显式预算

后台或 UI 触发的编辑路径即使最终调用同一个 Agent 实现，也可能绕过 CLI 的
成本护栏。

- **正确做法：** 在每一个自主变更边界校验有限的正预算，监听累计用量事件，
  并把取消传播进活跃的 provider/工具图。
- **发现位置：** Desktop 安全中心的自动修复最初接受验证命令却没有
  `maxCostUsd`，使编辑 Agent 不受任何限制。

## 61. 感知失败的 UI 完成回调不得执行成功清理

一个捕获错误后正常 resolve 的异步辅助函数，会让下游的 `.then(...)` 处理器
无法区分成功与失败。

- **正确做法：** 返回显式的成功结果（或重新抛出），并且只在确认成功之后
  才关闭对话框或清除用户输入。
- **发现位置：** 失败的 Finding 生命周期/修复请求关闭了对应的 Desktop 对话框，
  丢弃了用户的输入，错误却只显示在模态框背后。

## 62. 聚合结论必须从已校验明细推导，不能信任模型自报

结构化模型响应可能声称 `complete: true`，但自身标准记录仍是未满足、缺失、
重复或未知。

- **正确做法：** 校验标识符精确覆盖，并从必需明细记录推导聚合结果。
  聚合值不一致时拒绝；结构化证据无法解析时按关闭失败处理。
- **发现位置：** `packages/core/src/agent/loop-requirements.ts` —— 验收完成状态必须
  从冻结的必需标准计算，不能信任模型提供的布尔值。

## 63. 中间输出不等于阶段已经成功完成

模型可能先输出看似合法的文本，随后在工具调用或下一次 provider 回合失败。
如果不检查终态就保留前面的文本，会把未完成阶段误判成成功。

- **正确做法：** 只有同一次运行发出成功终态事件后，才接受分析/评审输出；
  取消、预算中止和 `session.failed` 都必须让该阶段保持未完成。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 失败的需求验收仍可能从
  较早的 `model.message` 判定通过；取消的分析也可能持久化 fallback，导致恢复后
  永远不再真正分析。

## 64. 批准只能作用于调用方已经观察到的产物

产物尚不存在时发送的批准参数，不能证明调用方看过最终要批准的准确内容。

- **正确做法：** 把批准绑定到从持久化状态加载的标识/版本；新生成的产物必须
  先返回，再由后续调用批准。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— confirm 模式的需求可以
  在同一次调用中生成并批准。

## 65. 进度指纹必须包含干净的已提交变更

一次运行如果修改并提交了文件，运行前后的工作树状态都可能是干净的。只看脏路径
会把真实进展误判成没有变化。

- **正确做法：** 除脏文件和未跟踪内容外，还要纳入仓库 `HEAD`/tree 身份；
  非 Git 工作区保留内容指纹 fallback。
- **发现位置：** `packages/core/src/agent/auto-loop.ts` —— 已提交的修复在验证诊断
  不变时可能错误触发 `no_progress`。

## 66. 有界事件流不是持久 UI 状态

淘汰旧进度事件不能顺带擦除后续操作所需的当前规格、结果或会话身份。

- **正确做法：** 把持久工作流字段独立于有上限的展示事件流进行归约，并从终态
  快照重新补齐。
- **发现位置：** `apps/desktop/src/lib/loop.ts` 与 `tabs.ts` —— 大量 Loop 输出可能
  淘汰需求，并让后续聊天脱离 Loop 会话。

## 67. 数值等价不代表输入语法等价

`Number()` 会接受十六进制等语法，而 CLI 文档约定的十进制解析器会拒绝，造成
不同界面行为漂移。

- **正确做法：** 先校验完整文本语法，再做数值转换和有限值/范围校验。
- **发现位置：** TUI 与 Desktop 的 Loop 控件会接受 `0x10` 迭代数，而 CLI 拒绝。

## 68. 陈旧锁恢复本身也是协调操作

比较锁内容与删除路径是两个独立的文件系统动作。两个恢复者可能都确认旧 owner
已经失效，随后其中一个却删除另一个刚创建的新锁。

- **正确做法：** 用排他的恢复标记串行化陈旧锁恢复；持有恢复权后重新读取，
  并让新候选在恢复期间主动让出。
- **发现位置：** `packages/core/src/agent/loop-state.ts` —— 并发恢复死亡的 Loop
  lease 时可能同时放进两个 owner。

## 69. 路径权限规则匹配前必须先规范化别名

`src/../secrets/key` 之类的词法别名可以跨越允许/拒绝边界，同时保留误导性的前缀。

- **正确做法：** 在精确或子路径匹配前，同时规范化分类得到的路径和配置规则路径。
- **发现位置：** `packages/core/src/tools/permissions.ts` —— 允许的 `src` 前缀可能
  放行 `src` 外的别名路径，或掩盖被拒绝的目录。

## 70. 必须在文件系统变更边界重新校验目标

路径校验与文件变更是两个操作。目标可以在校验后、按路径写入前被替换为外部符号链接。

- **正确做法：** 使用禁止跟随符号链接的方式打开，在最终检查点前后比较父目录和
  文件身份，并通过已校验的文件描述符执行变更。
- **发现位置：** `write_file` 和 `apply_patch` 可能跟随工作区校验后被换入的叶节点
  符号链接。

## 71. 内部持久化必须与工具写入采用相同的物理边界

当中间状态目录是符号链接时，工作区内的状态路径并不一定真的位于工作区内。

- **正确做法：** 所有持久化写入都通过物理写目标守卫解析，包括追加和原子重写。
- **发现位置：** memory 和 evolution store 可能通过符号链接的
  `.seekforge/memory` 或 `.seekforge/evolution` 目录写到工作区外。

## 72. 工具审批不能授权更早发生的插件启动

插件发现本身就可能启动进程或访问远程端点。之后围绕工具调用出现的权限提示，
不能反向授权此前的启动。

- **正确做法：** 自动发现前先要求连接信任；显式管理探测应独立，并由用户主动发起。
- **发现位置：** 未信任的 MCP stdio 服务器会在组装 Agent 时、任何工具级确认出现前启动。
- **另一个发现位置：** Server prompt 解析没有要求 prompt/resource 发现使用的 trust 标志，
  就会启动已配置的 MCP server。

## 73. 同一个终止原因必须映射到同一个协议状态

持久状态记录为取消、实时通道却发送通用失败，会让在线客户端和重连客户端看到不同结果。

- **正确做法：** 从同一个终止原因推导账本状态和发出的错误码。
- **发现位置：** 已中止的 WS Agent 抛出异常时，账本记为 `cancelled`，但在线客户端
  收到 `agent_error`。

## 74. 包装器选项不能隐藏需要分类的子命令

只检查第一个位置参数的命令分类器，会漏掉全局选项之后的危险子命令，尤其是值与选项
分开的写法。

- **正确做法：** 匹配有效子命令前，完整消费包装器的全局选项语法。
- **发现位置：** `git -C . push` 和 `git -c core.pager=cat push --force` 能绕过
  push/force-push 分类。

## 75. 进程内计数器不能生成持久标识符

时间戳加内存计数在多个进程于同一时钟刻度写入同一持久存储时可能冲突。

- **正确做法：** 为持久记录使用跨进程、抗冲突的标识符。
- **发现位置：** 多个 CLI 进程手动添加的 memory fact 可能获得相同 id。

## 76. 独立变更入口必须加入同一个仓库协调器

每连接 busy 标记只能防止该连接内部重叠；WS Agent、后台 Loop、webhook 与安全修复
仍可能同时指向同一个 checkout。

- **正确做法：** 所有 Server 管理的变更操作都通过同一个物理仓库协调器调度，
  并在排队前注册取消控制器。
- **发现位置：** 不同 WS 连接和后台 REST 运行可能与安全/Git 操作并发修改同一工作区。

## 77. 持久化去重仍需要原子 claim

read-check-write JSON 文件可以跨重启保留，但两个进程都可能在任一原子 rename 可见前
读到键不存在。

- **正确做法：** 使用可恢复陈旧状态的跨进程 lease 保护整个 claim/rollback 事务。
- **发现位置：** 两个 Server 实例可能同时接受同一个 GitHub delivery id。

## 78. 可重连客户端必须保留服务器回放游标

仅自动重连 socket 无法找回运行接受后丢失的帧；客户端还需要持久运行身份和最后应用序号。

- **正确做法：** 在工作流状态中保存 `runId + seq`，重连时使用 `afterSeq` 订阅，
  并忽略陈旧或重复运行帧。
- **发现位置：** Desktop 断连时可能丢失 Agent/Loop 终态，导致结果或会话身份不完整。

## 79. 分离任务仍然拥有结果目的地

把执行从前台控制中分离，并不会让其终态输出脱离接收它的标签页或文档。

- **正确做法：** 在分离任务完成前保持目的地存在，或在允许关闭前显式迁移所有权。
- **发现位置：** TUI 在分离 Loop 后允许关闭原标签页，最终结果会被静默丢弃。

## 80. 完整缓冲后的大小检查不构成内存上限

先读取 `arrayBuffer()` 或 `text()`，再检查长度，会让不受信任的对端在守卫执行前
消耗任意内存。

- **正确做法：** 增量消费流，在保留每个 chunk 前统计字节，溢出时取消读取，
  并让超时一直覆盖到响应体读取完成。
- **发现位置：** `web_fetch`、`web_search` 和 MCP HTTP 的普通 JSON/OAuth 响应
  要么在完整缓冲后才检查上限，要么完全没有上限。

## 81. 分隔协议必须在寻找分隔符期间保持有界

只有找到分隔符后才执行的行/帧上限，无法阻止未终止输入无限扩张解析缓冲区。

- **正确做法：** 在读取过程中限制累积；溢出后使用固定大小块丢弃到分隔符，
  使后续帧仍可继续处理。
- **发现位置：** Rust runtime 对 JSONL 请求使用无界 `read_until('\n')`，
  单个超大行即可耗尽子进程内存。

## 82. 传输层终止原因是载荷有效性的一部分

当 provider 表明生成因输出 token 上限而停止时，仅有文本内容不能证明响应完整。

- **正确做法：** 将长度受限响应视为未完成，请求一份可独立使用的完整答案；若已无剩余
  轮次，则明确失败。
- **发现位置：** Agent 曾把 `finishReason: "length"` 响应当作最终报告，静默持久化
  被截断的输出。

## 83. 取消必须覆盖人工交互等待

如果面向用户的 Promise 可能无限等待，只在进入审批或提问前检查 abort signal 并不充分。

- **正确做法：** 让每个权限确认和提问等待都与运行的 abort signal 竞争，并在任一侧
  完成时移除监听器。
- **发现位置：** Agent 等待权限或 `ask_user` 时取消，会让运行及其工作区 lease 卡住。

## 84. 缺失与显式为空的安全策略是不同状态

当字段缺失表示“使用无限制默认值”时，把空白名单归一化为缺失会扩大权限。

- **正确做法：** 在解析、合并和序列化过程中保留显式空集合；只有字段真正缺失时才
  应用默认值。
- **发现位置：** subagent 的 `tools: []` 白名单会变成 `undefined`，从无工具权限扩大为
  全部工具权限。

## 85. 关闭迭代器属于终止生命周期路径

async generator 可能被消费者关闭，而不抛错，也不进入生产者的正常完成分支。

- **正确做法：** 在 `finally` 中落定持久状态并释放资源，同时保留正常终止路径已写入的状态。
- **发现位置：** 提前关闭 Agent 事件迭代器后，执行虽已停止，会话仍持久化为 `running`。

## 86. 结构化数据必须先脱敏再序列化

文本脱敏器作用于已序列化记录时，可能插入换行，或吞掉 JSON 引号等语法。

- **正确做法：** 先递归脱敏字符串叶节点，再对结果结构执行且只执行一次序列化。
- **发现位置：** run-event 在 `JSON.stringify` 后脱敏会破坏 JSONL，也无法可靠移除
  多行 PEM 内容。

## 87. 敏感路径策略必须覆盖所有模型读取入口

只保护文件工具，会让其它上下文构建器和自动放行的搜索命令读取同一个秘密。

- **正确做法：** 对文件工具、`@path` 展开、工作区目录展开和命令自动审批统一应用
  basename 与相对路径策略。
- **发现位置：** `.seekforge/config.json` 和 `triggers.json` 可通过任务引用或显式指定的
  `rg` 命令进入模型。

## 88. 凭据名称匹配需要语义边界

`TOKEN` 这类无边界子串既会漏掉其它凭据名称，也会删除仅仅包含该单词的普通构建设置。

- **正确做法：** 环境清理和输出脱敏共享凭据类别，按分隔符/驼峰边界匹配，并测试非秘密名称。
- **发现位置：** `GITHUB_PAT` 会泄漏，而 `MAX_TOKENS`、`TOKENIZERS_PARALLELISM`
  会被静默删除。

## 89. 删除必须校验每一个物理父目录

当 `subdir` 能成为指向外部目录的符号链接时，安全文件名并不能保证
`root/subdir/file` 安全。

- **正确做法：** 删除与读写采用同一个物理项目路径守卫，并拒绝符号链接父目录和叶节点。
- **发现位置：** run-ledger 压缩可通过 `.seekforge/run-events` 删除外部
  `run-*.jsonl`。

## 90. 进程级 teardown 注册必须可注销

如果正常销毁不移除监听器，每实例 signal listener 会活得比短生命周期客户端更久。

- **正确做法：** teardown 注册返回幂等 disposer，并在所属客户端永久销毁时调用。
- **发现位置：** 每个 RuntimeClient 关闭后仍遗留四个进程监听器及其闭包。

## 91. 选项解析器必须消费选项的完整参数个数

跳过 flag 却未跳过其独立值，会把该值提升为子命令，从而向策略分类隐藏真正操作。

- **正确做法：** 编码哪些全局选项需要下一个参数，包括短/长拼写，并用 TS/Rust parity
  fixture 完整覆盖。
- **发现位置：** Rust 把 `git --git-dir PATH` 后的路径当成子命令，使后续破坏性 Git
  操作通过。

## 92. 原子替换仍要求完整写入

原子 rename 只保证哪个文件可见，不能保证一次 `write` 系统调用消费了整个 buffer。

- **正确做法：** 循环写到所有字节完成，按返回字节数推进，并在 writer 无进展时于
  fsync/rename 前失败。
- **发现位置：** `writeFileAtomic` 遇到短写时可能用截断临时文件替换持久状态。

## 93. 复合命令的 flag 只属于一个 invocation

在整条 shell 行中搜索危险 flag，可能把前一命令参数归给后一命令，并导致独立分类器分歧。

- **正确做法：** 识别命令边界，只在所属 invocation 内分类 flag，并用复合 fixture 固定
  跨语言行为。
- **发现位置：** Rust 把 `echo --force && git push` 中的 `--force` 归给 Git push，
  TypeScript 则没有。

## 94. 策略规范化必须符合 Shell 续行语义

单引号外的反斜杠换行会在 Shell 分词前被移除；把它当成空白会让拆成两行的危险命令隐藏起来。

- **正确做法：** 在策略匹配和单词解析前移除 Shell 续行，保留单引号内的原文，并固定
  跨运行时一致性。
- **发现位置：** `r\\<换行>m -rf` 和 `git pu\\<换行>sh --force` 实际执行为被拒命令，
  却绕过了 TypeScript 与 Rust 分类器。

## 95. 父级取消必须覆盖每一个网络阶段

操作自身的超时不能让工具响应所属 Agent 运行的取消，尤其是在 DNS 尚未解析完成时。

- **正确做法：** 把父级信号连接到请求控制器，并让 DNS、请求和响应体消费都可被中止；
  操作结束时移除监听器。
- **发现位置：** 已取消的 `web_fetch`、`web_search`、`image_analyze` 和 Browser 操作
  仍会继续运行，直到各自独立的超时；Vision 还会在收到响应头后清除超时，使响应体解析
  失去时间上限。

## 96. 仓库配置不得触发启动时执行

配置优先级不代表每一层具有相同信任级别；在用户批准任何动作前，刚检出的仓库仍不可信。

- **正确做法：** 启动时 shell 命令只能来自用户拥有的配置，并使用最小化白名单环境启动。
- **发现位置：** 项目 `.seekforge/config.json` 可在 TUI 打开时立即运行 `statusLine`，
  并从 `process.env` 继承 provider API 密钥。

## 97. 分隔流必须在分隔符前限制 frame

只在找到换行后检查大小的解析器，即使之后会校验每条记录，也会无界缓存未终止记录。

- **正确做法：** 等待分隔符前先限制待处理缓冲区，同时拒绝已终止的超大 frame，
  并立即失败或终止生产者。
- **发现位置：** CLI stream-json 输入和 Runtime stdout JSONL 都可被一条永不结束的行
  耗尽宿主内存；普通 CLI 管道文本也会在没有总量上限的情况下累积全部 chunk。

## 98. 异步 UI 结果必须持续绑定请求身份

props 变化不会取消早期 render 启动的 Promise；迟到结果可能覆盖已属于另一资源的状态。

- **正确做法：** 捕获 generation 或资源身份，在 effect cleanup 中使其失效，并守卫成功、
  错误和 finally 回调。同一资源内还要捕获编辑修订号，防止保存响应隐藏更新的输入。
- **发现位置：** 迟到的文件 A 读取可进入文件 B 编辑器，后续保存会把 A 内容写到 B；
  文件索引加载也存在同类工作区切换竞态；保存完成也可能在用户输入更新、尚未保存的修订后
  关闭编辑器。

## 99. 在通用 JSON 解析之前执行响应大小限制

`Response.json()` 会缓冲完整响应体，无法在字节到达时执行应用层上限。

- **正确做法：** 不受信任的 API 响应先通过共享的有界增量读取器，再解析已受限的缓冲区。
- **发现位置：** Vision API 响应绕过 Web 响应上限，可在 JSON 解析完成前无界消耗内存。

## 100. 快照替换与追加必须共享同一个跨进程租约

原子 rename 只能避免文件撕裂，不能阻止压缩器在另一进程向旧文件追加后用快照覆盖它；
对端追加或替换文件后，本进程缓存的行数也会失效。

- **正确做法：** 让所有追加与压缩共享同一个跨进程租约；在租约内比较低成本文件身份，
  发现对端写入后重新计数。
- **发现位置：** Server run-ledger 并发压缩可能永久丢弃另一进程的运行记录。

## 101. 后台轮询必须负责异常与终态清理

定时器回调抛出的异常会逃逸请求 Promise；资源结束后仍不注销的轮询会持续保留连接状态。

- **正确做法：** 捕获每次轮询，在失败、socket 关闭和观察到终态帧时注销，且只暴露通用传输错误。
- **发现位置：** WS 运行订阅可能因回放读取异常而使进程崩溃，或在交付终态后永久轮询。

## 102. 轮询游标必须让空闲与增量工作保持低成本

每次定时器触发都从零开始扫描持续增长的追加日志，空闲时仍是 O(N)，长运行累计为 O(N^2)，
即使响应分页有上限也无法避免。

- **正确做法：** 同进程追加使用直接通知；低频跨进程兜底先做 O(1) 文件身份比较，
  仅在发生变化后读取有界页面。
- **发现位置：** 实时 WS 订阅每 25 ms 重新解析完整 run-event JSONL，没有新事件时也一样。

## 102. 取消必须持续拥有所有子操作，直到清理完成

只在 turn 开始时检查 abort，无法覆盖 hook、响应后的处理，也无法覆盖 async iterator
关闭后仍在运行的工具。

- **正确做法：** 将调用方取消桥接到 run 自有 signal，并传给所有子操作；在外部可观察的
  usage 事件后重新检查；对可能忽略信号的 provider Promise 主动竞速；释放 session lease
  前等待活动工具和 subagent 完成清理。即使进入“信号已取消”分支，也必须观察生产者
  Promise，避免同步拒绝逃逸为全局未处理错误。
- **发现位置：** 预算取消后仍可能提取 memory 并完成 session；`iterator.return()` 也可能
  在工具退出前释放 lease；工具级 pre/post hook 也会忽略运行信号；后台 dispatch 还会
  错误地跟踪短暂的启动 Promise，而不是底层子运行。

## 103. Agent 生成态不属于工作区进展

如果进展指纹包含 Agent 自己的日志、memory candidate 或 session 状态，即使产品源码和
verifier 结果完全没变，指纹也会变化。

- **正确做法：** Git 路径和 fallback 路径都要排除所有生成态目录。
- **发现位置：** memory extraction 每轮修改 `.seekforge/memory/candidates.jsonl`，导致
  Loop 的 `no_progress` 守卫无法触发。

## 104. 并发写入者需要工作区隔离或串行化

两个 Agent 可以基于同一个旧快照成功写入，后写结果会静默覆盖先写结果。

- **正确做法：** 使用隔离 worktree 或内容版本 CAS；若项目尚无这类机制，应保守地
  串行执行共享工作区的 edit-mode Agent，同时保留只读 Agent 的并发能力。
- **发现位置：** 独立的 `dispatch_team` edit 成员可能互相覆盖修改，却都报告成功。

## 105. 配置型子进程只能获得最小权限环境

命令由用户配置，并不表示父进程中的所有 provider token 和主机凭据都与该命令相关。

- **正确做法：** 通过共享 secret scrubber 构造子进程环境，再只添加子协议明确需要的
  元数据变量。
- **发现位置：** hook 继承完整 `process.env`，在任何工具权限边界之前就能读取 provider
  API key。

## 106. 授权必须固定到物理资源身份

批准一个逻辑路径，并不等于批准该路径上的符号链接之后可以指向的任意目标。

- **正确做法：** 授权目录时只规范化一次，并保存该物理路径供后续读取；不要再次解析
  原来的逻辑别名。
- **发现位置：** `/add-dir` 的符号链接在批准后可以被重新绑定，使 `@` 引用读取另一个
  外部目录。

## 107. 辅助工作区状态同样需要路径约束与协调

便捷小文件仍是写入面：普通的读取-修改-写回会跟随仓库符号链接、暴露外部内容，或与
正在运行的 Agent 竞争。

- **正确做法：** 拒绝符号链接状态父目录和叶文件，通过 no-follow 文件描述符读取，
  原子替换完整文件，并让每个 UI/API 写入口获取共享 workspace/repository guard。
- **发现位置：** TUI 和 Server 的 todo 操作可能读取或覆盖外部
  `.seekforge/todos.md`，并且写入时没有 Agent 工作区 guard；TUI 还会把失败的写入
  报告成成功修改。

## 108. 配置型子进程需要有界的进程树所有权

只给直接 shell 设置超时并不完整：后代仍可持有管道；`error` 事件也不等于成功 EOF。

- **正确做法：** 异步运行受控进程组，限制捕获字节，失败时销毁管道，先终止再升级杀死
  整个进程组，并且只在确认整个进程组都已退出后取消延迟强杀定时器。
- **发现位置：** REPL shell 展开和 TUI 状态栏会因后代管道挂起或无界收集输出；stdin
  错误会返回部分 prompt，状态栏命令还会阻塞渲染；CLI/TUI shell 父进程成功退出后，
  关闭了输出的后代也可能继续运行。Hook shell 和 Server 命令展开在成功或失败退出后同样
  会泄漏后台后代；Windows 清理还只会终止直接子进程，而不是整棵进程树。

## 109. 在破坏客户端状态前执行传输上限

只在服务器限制 frame，会让客户端先清空或追加本地状态，再发现请求根本无法通过传输层。

- **正确做法：** 共享协议常量，按实际序列化 frame 计量，在发送或清空草稿前拒绝，并在
  编码二进制前预检大小。
- **发现位置：** 超大的 Desktop task/Loop frame 会先清空草稿再被 WebSocket 拒绝，
  超大图片也会先做 base64 膨胀。

## 110. 异步 UI 结果必须绑定编辑版本

标签页身份相同，并不能证明延迟返回的转换文本仍属于当前草稿。

- **正确做法：** 异步工作前记录资源级 revision，仅在身份和 revision 都未变化时应用结果。
- **发现位置：** 延迟的自定义命令展开会覆盖同一 Desktop 标签页中稍后输入的文本。

## 111. 子进程从 spawn 成功的一刻起就必须被持有

进程在 readiness 成功前已经存活；若只在启动完成后登记，Exit/清理会有一段时间找不到它。

- **正确做法：** spawn 后立即在生命周期锁内登记 starting 状态，再把同一个受控子进程
  转为 running，或终止它。
- **发现位置：** Desktop 的 Exit 与 readiness 竞争时可能泄漏 sidecar。

## 112. 终态事件必须兼容迭代器安全关闭

在异步生成器 `finally` 中继续 `yield`，会让 `return()` 以 `done:false` 返回，并把释放流程
无限期挂起。

- **正确做法：** `finally` 只等待清理、不产出；在成功/失败事件前显式排空子任务事件，
  保证 session 终态事件最后出现。
- **发现位置：** 后台 dispatch 的用量/文件可能漏出最终报告或出现在完成事件之后；提前
  停止消费还可能卡住 lease 与 hook 释放。

## 113. 重写后的工具输入才是有效安全主体

只验证、授权原始参数，会使 hook 重写后的路径/命令与执行、审计和验证不一致。

- **正确做法：** 对替换输入统一执行 schema 校验、重新分类、重新授权、执行、报告和审计；
  无效替换直接拒绝。
- **发现位置：** `preToolUse.updatedInput` 仍保留原权限元数据与验证命令，格式错误的替换
  还会静默执行原参数。

## 114. 结构化状态需要校验、串行化和物理写入

JSON 能解析不代表值有限且有界；逻辑路径检查也无法抵抗并发写入或符号链接换绑。

- **正确做法：** 校验每个持久化字段，让计数饱和，跨进程序列化读改写事务，通过验证过的
  no-follow 描述符读取，并经重新验证的父目录原子替换。
- **发现位置：** memory 元数据接受非有限值，并发更新会丢失，memory/candidate/archive/
  summary 写入还保留符号链接 TOCTOU 窗口；把超限或损坏的持久状态当作缺失还可能覆盖原文件。

## 115. 流协议需要累计预算和时间预算

逐行上限无法限制持续推进的响应，JSON 数字字段也可能带来不安全整数或非有限运算。

- **正确做法：** 限制原始字节、每个累计字段和项目数量，同时设置 idle 与总时限，失败时
  取消 reader，并在成本计算前验证 usage。
- **发现位置：** provider SSE 可跨合法行无限增长或持续推进而永不结束；非流式/错误
  body 会无字节上限地缓冲，异常 token usage 还会生成不安全成本。

## 116. 规范路径必须持续绑定到已打开文件

先物理解析路径、再按路径名调用 `stat`/`readFile`，仍会留下换绑窗口；完整读取后再截断
也不构成内存上限。

- **正确做法：** 用 no-follow 标志打开规范父目录和叶文件，比较路径与描述符身份，并且
  只从 fd 读取有界字节前缀。
- **发现位置：** workspace 和额外目录的共享 `@path` 展开可能跟随校验后被替换的文件，
  还会在 30k 上限生效前缓冲完整文件；Rust runtime 读取/列表会重新打开已校验路径，
  `apply_patch` 也会无界缓冲目标文件。Skill/agent 导入、security evidence、Loop 与 session
  lease、工具 checkpoint/search 和 vision 输入也重复了读取前 `stat` 或读取后才限长的模式。

## 117. 被拒绝的请求 body 仍然拥有 drain 生命周期

拒绝 body Promise 不会阻止 socket 继续发出数据或错误。丢弃中的 body 关闭前移除所有
错误监听，会让迟到传输错误崩溃；正常监听一直保留则会逐请求泄漏。

- **正确做法：** body reader 只 settle 一次，在每个终态移除正常监听，保留 drain 专用
  error sink 直到 `close`，并预检 Content-Length。
- **发现位置：** Server REST body 读取在请求中止时可能挂起，settle 后仍保留监听；route
  提前拒绝会留下未读 body，第一版超限修复还留下了迟到错误窗口。

## 118. 持久化协议上限必须放在写入端

重放读取器的行上限无法修复已经追加的超大记录；第一条不可读行会隐藏后续全部合法事件。

- **正确做法：** 追加前序列化并按字节计算准确持久化 envelope，仅在成功后推进序号状态，
  追赶重放时不要再维护一份重复队列。
- **发现位置：** Server run event 可能破坏持久重放，WS 追赶阶段还会无界保留本地追加事件
  的第二份副本。

## 119. 设置属于安全敏感的修改面

Hook、sandbox 策略和 MCP 启动配置即使不是产品源码，也会影响后续执行。独立读改写入口
可能丢失更新，或在 Agent 持有 workspace 时改变策略。

- **正确做法：** project 层完整事务持有 repository/workspace guard，global 层完整事务持有
  共享跨进程 lease。
- **发现位置：** Server hooks、config 和 MCP 写入绕过 session 协调；masked secret 保留逻辑
  还会在加锁前读取旧 MCP 项。

## 120. 传输类型和方法语义也是协议数据

包含 JSON 的字节不一定是 WebSocket 文本 frame；接受 `HEAD` 也不代表可以发送 GET body。

- **正确做法：** 显式拒绝二进制 frame；HEAD 在成功和错误路径都发送与 GET 等价的 header
  （包括 Content-Length），但抑制 body。
- **发现位置：** Server WS 接受二进制 JSON，静态 HEAD 也走与 GET 相同的 body 路径，且
  没有稳定长度。

## 121. 会进入提示词的配置必须同时具备物理边界与字节边界

会成为系统提示或工具元数据的文件都属于不可信输入。词法 join、读取前 `stat`，或之后的
提示预算裁剪，都不能限制实际读取量。

- **正确做法：** 校验名称，拒绝链接化配置根和叶文件，把读取绑定到已验证的 no-follow
  描述符，执行单文件与累计字节上限；结构化文件超限时整体跳过，不解析截断内容。
- **发现位置：** output-style 路径穿越；commands/rules/subagent 链接根；无界 AGENTS/AGENT
  文件；以及 package/repo-map 在过期尺寸检查后继续增长并进入提示构建的读取。

## 122. 授权结果和执行上下文必须属于单次操作

结构化拒绝对象本身为 truthy；共享工具上下文上的可变字段也可能被另一个并发执行覆盖。

- **正确做法：** 所有权限结果都通过显式 `allow` 字段归一化，并把审批产生的状态复制到
  每次调用独立的新上下文。
- **发现位置：** sandbox fallback 在 `{allow:false}` 后仍可能无沙箱运行；并发编辑审批还
  可能交换 `selectedHunks` 选择。

## 123. Schema 与关联边界必须表达精确值域

数字强制转换和全局键关联会静默接受消费者未预期的值，或把不属于同一轮的记录配对。

- **正确做法：** 在 schema 中要求整数及明确上下限，并把这些约束保留到向模型声明的
  JSON Schema 中；同时校验反序列化字段形状，并把工具 call/result 关联限制在同一个
  assistant turn 内。
- **发现位置：** 负数/小数 timeout、tail、depth、range、limit；schema 转换器丢失
  数值与集合边界；异常 package 元数据；复用 tool-call id 时清除了错误轮次；以及正则 predicate
  把非字符串 Loop DAG id 强制转换成了看似合法的字符串。

## 124. 评测工作区属于对抗性输入

Agent 可以塑造其检查项最终读取的文件和进程。词法安全的检查路径或只给直接 shell
设置超时，都不能保证评分可靠。

- **正确做法：** 拒绝链接化断言文件和命令目录，把文件读取绑定到已验证描述符，限制
  断言字节与输出，持有完整检查进程组，并在清理失败时判定样本失败。
- **发现位置：** Eval 的 `file_not_contains` 可通过符号链接假通过，命令 `cwd` 可逃出
  fixture，超时检查会泄漏后代，disposer 异常还会让 harness 拒绝而不是产生失败结果。

## 125. CI 值只能作为数据，不能成为 shell 源码

手动 workflow 输入和 action 输出都可能包含 shell 元字符，即使操作者只是想传 tag 或版本。

- **正确做法：** 通过环境变量传递 expression，生成输出前校验完整值域，并在每处使用时
  引用变量。
- **发现位置：** npm 发布 workflow 把 dispatch tag 直接插入 shell，使其可在后续带凭据
  发布之前修改工作目录。

## 126. `file:` URL 的 pathname 不是文件系统路径

URL pathname 会保留百分号编码，并带有平台相关的前导符/路径规则，因此在空格、Unicode
和 Windows 路径上会失败。

- **正确做法：** 使用 `fileURLToPath` 转换 file URL，再调用路径工具。
- **发现位置：** package smoke 和实时 server E2E 脚本从 `import.meta.url.pathname`
  推导仓库路径。

## 127. 行 framing 上限必须早于行缓冲

在 `readline` 回调中检查行长度已经太迟：peer 可以持续发送不带换行的数据，此时 framing
层早已把它们全部保存在内存中。

- **正确做法：** 消费 chunk 时按原始字节计数；frame 一旦越界就进入丢弃状态，持续丢弃
  到该 frame 的换行符，然后恢复处理下一帧。客户端无法关联被拒绝 frame 时，必须确定性地
  失败所有 pending request 并重启 transport。
- **发现位置：** MCP stdio server 输入以及 client stdout/stderr 使用无界 `readline`
  framing；恶意 peer 无需完成 JSON-RPC 消息就能持续增加内存占用。

## 128. 文件上限必须覆盖读取期间增长，并保护超限持久状态

先检查尺寸再整文件读取，仍会受到文件继续增长的影响；把超限状态当成“缺失”，还可能在
下一次写入时销毁原文件。

- **正确做法：** 通过描述符增量读取并检测越界；响应只在已验证的固定区间内流式发送；
修改超限状态前失败关闭；报告通过原子替换发布。
- **发现位置：** Server 静态资源/settings/recents、shared config/todos，以及 Eval 的
suite/task/baseline/trend/metadata 存在无界读取；状态修改可能覆盖超限文件，报告读取方也
可能看到部分输出。

## 129. run 一旦预留，必须在调度执行前就拥有终态责任

在进入调度器前先持久化 `running` 会留下空窗：取消或协调器失败可能在操作自身的
`try/finally` 运行前就拒绝 Promise。

- **正确做法：** 在调度 Promise 本身挂接 ledger 终态、事件和连接清理；任何执行前拒绝
都必须表现为 failed 或 cancelled。
- **发现位置：** REST 后台 Loop 和 WebSocket Agent/Loop 在仓库协调执行前拒绝时，可能
永久停留在 `running`。

## 130. 校验特殊文件时，不能先阻塞在 open

如果打开 FIFO 会先无限等待 writer，那么尺寸检查或打开后的普通文件校验都无法保护读取方。

- **正确做法：** 对不可信读取路径同时使用 `O_NONBLOCK` 和 `O_NOFOLLOW`，随后在读取前
  校验描述符确实指向普通文件。状态修改必须把 `ENOENT` 之外的所有读取失败视为不可覆盖状态。
- **发现位置：** config、state、trace、静态资源、dataset 和 todo 的有界读取都可能阻塞在
  FIFO；todo 修改还可能把非“文件不存在”的读取错误当成空列表后尝试替换。

## 131. 游标不仅要携带逻辑 id，还必须绑定已校验的物理位置

每次读取第 N 页都从字节零开始扫描到逻辑序号 N，会让完整遍历退化为平方复杂度，即使
单页大小本身有界。

- **正确做法：** 缓存最后一条已校验记录之后的字节偏移，并把它绑定到所有影响解析结果的
  输入（workspace、run id、sequence 和文件 identity）；identity 一旦改变就回退到字节零。
  游标缓存也必须像返回页一样设定容量上限。
- **发现位置：** Server 的 run-event REST/WS 回放会为每个 `afterSeq` 页重新读取完整
  JSONL 前缀。

## 132. 高信任级别的密钥不能继承低信任配置层提供的目标地址

标量优先级可能把各自看似安全的值组合成不安全的凭据路由：用户持有的密钥加上仓库控制的
endpoint。

- **正确做法：** 配置合并时保留目标来源信息，或把凭据校验等携带密钥的启动请求固定到
  用户控制/官方 endpoint；绝不能让项目配置重定向用户刚提交的密钥。
- **发现位置：** Server onboarding 在校验 DeepSeek Key 前读取项目 `baseUrl`，使检出的
  仓库可以通过 Bearer 认证接收该密钥。

## 133. 安全身份必须来自注册记录，而不是命名约定

前缀和“看起来像生成值”的字符串只是分类，不是来源证明；普通哈希和攻击者选择的输入都
可能满足这些形式。

- **正确做法：** 当行为依赖对象身份时查询权威 registry/owner map；名称和前缀只能作为
  展示或序列化细节。
- **发现位置：** 后台隔离把所有以 `wt-` 开头的 workspace id 当作受管 worktree，而普通
  工作区的哈希 id 也可能命中此前缀。
- **同类问题：** workspace 删除接口拒绝所有 `wt-*` id，而没有向 worktree manager
  查询该 workspace 是否真的登记为 worktree。

## 134. 失败后放宽策略只能匹配一个明确且良性的失败原因

在安全边界捕获一整类错误，会把运行故障转化为权限或隔离范围扩大。

- **正确做法：** 检查类型化错误码，只对文档约定的良性场景降级；busy、conflict、基础
  设施错误和未知错误都必须继续抛出。
- **发现位置：** 自动 run 隔离会对所有 `WorktreeError` 回退到基础工作区，而不只是
  `not_a_git_repo`。

## 135. 跨系统关联 id 解析失败时不能用默认值代替

只有调用方有意省略标识符时，兼容默认值才安全；如果客户端尝试解析外部资源但失败，默认值
会把操作绑定到另一个对象。

- **正确做法：** 区分主动省略与查找失败，把异步后续状态绑定到已选择资源，并在发送可变更
  请求前失败关闭。
- **发现位置：** VS Code 客户端在 workspace 路径不匹配时省略 `ws`，Server 随后选择了
  无关的默认工作区。

## 136. 长连接上的每个请求仍然需要自己的截止时间

SSE/WebSocket 会话的生命周期不能充当嵌套 HTTP 请求的超时；等待该请求可能永久阻塞整个
stream dispatcher。

- **正确做法：** 为每个嵌套请求创建独立 controller 和 timer，关联 transport 的父 signal，
  并在完成时同时移除计时器与监听器。
- **发现位置：** Streamable HTTP MCP 的 `roots/list` 响应复用了独立 GET stream 的 signal，
  可能永久等待并阻塞后续所有 SSE 消息。

## 137. 授权不是普通的可合并配置数据

分层优先级只描述值如何选择，并不表示哪个来源有权授予信任。否则低信任仓库层
可与用户密钥或策略默认值组合，获得任何单个字段都未直接表达的能力。

- **正确做法：** 合并前按来源对每一层降权。仓库层可保留安全偏好和限制性规则；密钥
  目的地、执行 hook/runtime 命令、allow 规则/放行清单、sandbox 策略、预算、
  保留策略与信任标志必须来自用户级配置。
- **发现位置：** 项目/local 配置及 profile 可以把用户 API key 路由到仓库端点，
  启动 hook/runtime/MCP、自动放行命令、削弱 sandbox，或把自身 MCP 标记为可信。

## 138. 双向 HTTP 协议消息需要对称的传输检查

客户端回答服务器发起的请求时，仍然在发送一个需认证的 HTTP 请求。若把响应 POST
当作 fire-and-forget，令牌过期或响应被拒时，服务器请求会被静默丢失。

- **正确做法：** 协议响应 POST 与普通请求 POST 使用相同的 OAuth 刷新、非 2xx 拒绝、
  取消和超时行为。
- **发现位置：** Streamable HTTP MCP 会为客户端请求和独立 GET stream 刷新 OAuth，
  却不会为发回服务器的 `roots/list` 响应刷新。

## 139. 改写 transport URL 的 scheme 或 path 之前必须先校验

修改 URL 并不能证明输入原本就指向预期 transport。否则 `file:`、`ftp:` 或携带凭据的
URL 可能被改写成看似合理的 WebSocket 字符串，直到很晚才失败，甚至带着意外权限连接。

- **正确做法：** 只解析一次，先对白名单中的原始 scheme 做校验，丢弃无关 query 与
  fragment，再从已校验值推导 HTTP/WebSocket endpoint。打开连接前拒绝不支持的协议。
- **发现位置：** VS Code bridge 会把任意配置的服务器 scheme 改写成 `ws:`/`wss:`，
  却没有先要求它是 HTTP(S) 服务器 URL。

## 140. 尽力而为的后台整理不能决定前台操作结果

后台整理发生在用户可见的变更已经成功之后。如果配置、状态、租约或写入失败仍向外
抛错，就会把原本已经持久化成功的操作报告为失败；覆盖损坏的整理状态还会销毁唯一的
诊断证据。

- **正确做法：** 在信任边界校验整理策略，使用该领域共享的事务租约，保留损坏状态，
  返回有类型的整理结果，并让前台成功与该结果相互独立。只有整理本身成功后才持久化
  节流时间戳。
- **发现位置：** `packages/core/src/memory/maintenance.ts` 及其 CLI/TUI/Server/Agent
  调用方需要自动压缩，同时不能让已批准记忆写入失败，也不能让仓库配置启用过期事实归档。

## 141. 空闲任务需要非阻塞锁顺序与明确的生命周期所有权

如果后台任务排队等待前台锁，它就不再是空闲任务；如果先取得宽泛的 workspace guard，
而整理过程随后申请一个会被该 guard 自身阻止的领域租约，还会造成死锁。周期计时器也不能
活得比拥有其工作区/配置身份的 Server 或 UI 更久。

- **正确做法：** 非阻塞地取得较窄的领域租约，凭该已持有租约申请更宽的空闲 guard，
  再次检查进程本地空闲状态，任何冲突都跳过；所有者退出时取消下一次计时。每轮重新读取
  动态目标和配置，并禁止多个 tick 重叠。
- **发现位置：** 第一版空闲记忆调度器先取得 workspace guard，再申请记忆租约，导致自己的
  记忆事务等待 30 秒后失败；Server/TUI/REPL 计时器也需要显式释放和当前目标查询。

## 142. allowlist 必须约束最终的运行时命名空间

当工具还可来自 MCP、动态 dispatch、插件或未来注册项时，一份静态 builtin 清单不是真正的
allowlist。只过滤熟悉的名字，会让清单之外的工具继续被展示和执行。

- **正确做法：** 把精确的允许名称集合带到最终组装后的工具目录，在模型看到定义之前过滤，
  并在实际调用时再次失败关闭，以覆盖过期或伪造的调用。
- **发现位置：** CLI `--allowedTools` 根据硬编码 builtin 名单生成 deny 规则，遗漏了 MCP 与
  动态合成的 dispatch 工具。

## 143. 作为注册表键的名称必须校验并拒绝冲突

Map 赋值不等于安全注册：重复名称会悄悄替换旧 handler，而目录、权限或 trace 仍可能描述
两者。规范化也可能让两个不同外部名称制造同类冲突。

- **正确做法：** 在注册边界校验名称，构建前拒绝重复，并对外部名称的展示与调用使用同一套
  确定、抗冲突的映射。
- **发现位置：** 工具注册表曾静默覆盖重复名称；MCP 的歧义或非法 server/tool 名称需要使用
  有长度上限的哈希回退名。

## 144. 扩展审批必须绑定内容、来源与激活状态

发现仓库内的扩展文件并不等于同意执行。若已安装内容随后变化，单纯布尔审批也会立即过期。

- **正确做法：** 分离发现与安装；安装到用户所有的存储并默认禁用；审批绑定全部有界普通
  文件的摘要；拒绝链接；摘要变化后停止所有贡献，直到显式重新批准。
- **发现位置：** `packages/core/src/plugins` 的一等插件生命周期需要支持项目发现，同时不能
  让仓库自行取得 hook/MCP 权限。

## 145. 恢复执行必须重建全部任务级 prompt 贡献

复用对话 trace 并不表示依赖任务的 system context 对新用户轮次仍然有效。

- **正确做法：** 在新建和恢复请求前都重建 mode、plan、memory、skills 及其他当前任务
  prompt 输入；持久化历史与这些输入分开处理。
- **发现位置：** `packages/core/src/agent/loop.ts` 只在新会话分支选择技能，导致后续
  Auto-Loop 迭代静默丢失流程指引。

## 146. 本次请求声明的工具目录就是执行能力边界

一个已注册工具可能因策略或上下文预算选择而没有出现在某次 provider 请求中。仅凭注册表
成员身份不能批准过期或伪造调用。

- **正确做法：** 除全局 allowlist 和 dispatcher 权限检查外，还要把执行绑定到该次请求
  过滤后实际发送的工具名集合。
- **发现位置：** 上下文裁剪可能省略大型 MCP 工具，但 dispatcher 仍会执行模型提供的
  已知工具名。

## 147. 可变扩展存储需要物理身份与事务

只在加载时校验还不够：enable/import/remove 可能跟随链接组件、与 Agent 竞争，或暴露
多文件安装的一半状态。

- **正确做法：** 把每个父目录和叶文件校验为物理对象，跨进程串行化，取得工作区变更
  guard，并通过带回滚的原子 rename 发布多文件更新；元数据 id 必须绑定目录名。
- **发现位置：** `packages/core/src/skills` 生命周期操作直接写文件，可能竞争或跟随不安全
  的技能存储路径。

## 148. 尽力而为的遥测必须有界、非阻塞且不决定业务结果

观测目标可能是 FIFO、链接、超大文件或并发写入者；它们都不能阻塞或破坏被观测的前台操作。

- **正确做法：** 使用 no-follow/non-blocking 的普通文件检查、限制记录和存储大小、串行化
  写入并轮转，同时在领域结果之外捕获所有失败。
- **发现位置：** 技能选择用量日志没有大小限制或物理文件校验，可能无限增长或写向特殊文件。

## 149. 进展指纹必须显式表示“不确定”

同步摘要无界工作区会冻结 Agent；把不完整摘要当作相等又可能提前停止有效工作。

- **正确做法：** 使用文件数、字节数和时间上限异步生成指纹；样本不完整时返回 `null`，
  只有两个完整样本才能用于 no-progress 比较。
- **发现位置：** Auto-Loop 收敛判断会同步读取 dirty 工作区内容，且没有总预算。

## 150. 学习得到的排序信号必须有界且不具备授权性

成功遥测具有相关性、稀疏性，也可能过期。把原始成功率当成权威，会让少量幸运运行支配选择
甚至安全决策。

- **正确做法：** 要求最小样本量，按置信度收缩，限制分数调整幅度，并让它完全不参与权限
  和风险判断。
- **发现位置：** `packages/core/src/skills` 的自适应技能效果需要改善排序，同时不能把遥测
  变成执行授权。

## 151. 文件系统信号缓存必须校验完整扫描边界

在已有嵌套目录中新增文件不会改变根目录时间戳，因此只用根目录作缓存键会静默过期。

- **正确做法：** 保存并校验每个已扫描目录的物理身份和修改时间，并单独校验读取的清单；
  同时限制缓存条目数。
- **发现位置：** 技能工作区语言/路径缓存否则可能永远看不到新加入的嵌套源文件。

## 152. 依赖选择必须作为一次有界图操作完成

先选择流程、再发现依赖缺失、循环、高风险或冲突，会注入不可执行的半套计划或突破 prompt 上限。

- **正确做法：** 提交候选前解析依赖，把整个组合计入同一个预算，拒绝无效组合，并用稳定
  决胜规则对最终集合做拓扑排序。
- **发现位置：** `packages/core/src/skills/select.ts` 中的技能 `dependsOn`/`conflictsWith` 编排。

## 153. 新增观测文件必须从进展信号中排除

即使遥测有界，它仍是工作区变更。若收敛摘要包含它，每次无实际工作的迭代都会被误判为产品
进展，循环防护永远不会触发。

- **正确做法：** 在进展边界对每个新增的 Agent 生成状态文件分类，并添加只修改该文件的回归。
- **发现位置：** `.seekforge/skills-usage.jsonl` 的技能终态记录阻止了 Auto-Loop 的
  `no_progress` 检测。

## 154. 编排器必须显式消费子任务终态事件

异步事件流在报告 `session.failed` 后仍可能正常结束。把“流结束”当作成功，会让失败工作继续
进入后续门禁，并丢失原始错误分类。

- **正确做法：** 显式记录 completed/failed 终态，只对有界的瞬时错误分类重试，并把原始错误
  保留在编排结果中。
- **发现位置：** Auto-Loop 忽略编辑 Agent 的 `session.failed` 后仍运行校验。

## 155. 进展持久化不能把遥测频率变成写盘频率

累计用量可能每个模型回合更新一次。每次都原子重写完整状态快照会放大前台文件系统延迟。

- **正确做法：** 在短而有界的 checkpoint 窗口内合并高频快照，并在迭代、取消、错误和终态
  边界强制同步刷新。
- **发现位置：** Auto-Loop 曾在每个 `usage.updated` 事件上重写状态文件。

## 156. 可观测回调不具备生命周期控制权

渲染或嵌入层回调可能抛错。让异常逃逸会放弃运行，而持久状态仍显示 `running`。

- **正确做法：** 隔离观察者异常，禁用坏回调，记录有界告警，并让权威操作继续。
- **发现位置：** Auto-Loop 的 `onEvent` 异常可能中断循环并释放租约。

## 157. 有界事件数还需要字节预算和保留策略

当单个事件携带大载荷时，事件数上限并不能限制存储；只追加文件跨迭代和恢复后仍会无界增长。

- **正确做法：** 限制载荷字节，批量写入，按总字节轮转，只保留固定分段，并在生命周期边界刷新。
- **发现位置：** verifier 输出每次校验可向无限 Loop 日志追加约 1.6 MiB。

## 158. 结构化计划必须在每个公开入口完整校验

只检查计划是数组，会让非法 id、重复阶段、空命令和无效超时在类型断言下进入深层执行器。

- **正确做法：** 在构造类型化请求前校验形状、数量、唯一安全 id、可选布尔值和正数超时。
- **发现位置：** REST 后台 Loop 曾接受未经校验的 `verificationPlan` 条目，而 WebSocket
  路径会拒绝同样的数据。

## 159. 交付产物必须覆盖完整分支差异

只对 dirty worktree 做 diff 会漏掉已经提交的工作，也无法表示未跟踪文件，因此看似成功的
补丁可能为空或不完整。

- **正确做法：** 先对保留 worktree 做 checkpoint，再生成相对基础检出的完整二进制分支补丁。
- **发现位置：** Loop `--deliver patch` 最初只对 worktree `HEAD` 做 diff。

## 160. 并行图节点需要不同的物理工作区和分配后的预算

提供回调不等于隔离：两个节点仍可能解析到同一检出；同时把全部剩余预算交给每个并发节点，
还会成倍放大预期上限。

- **正确做法：** 每批运行前解析并比较物理工作区身份，并在同时调度的节点之间分配共享成本
  与 Token 容量。
- **发现位置：** Loop DAG 并发最初信任 `workspaceForNode` 的返回值，且为每个节点重复了全部
  剩余共享预算。

## 161. 回放游标必须跨保留轮转与 writer 重启保持稳定

若序号只按当前保留行重新计算，最旧分段轮转后索引会整体移动，已经发出的游标可能跳过全部
新事件。

- **正确做法：** 每行持久化单调序号，writer 重开时恢复最后序号，并为旧格式行保留有界兜底。
- **发现位置：** Loop 历史最初只给当前保留的 JSONL 行临时编号。

## 162. 编排迭代数不等于会话轮次

重试、分析会话与恢复运行都会让编排计数偏离 checkpoint 和 trace 截断所使用的 user-message
索引。

- **正确做法：** 操作开始前记录真实的会话 user-turn 边界，并用同一边界执行文件回退和 trace
  截断。
- **发现位置：** Loop 退化回滚最初从 Loop 迭代号推导会话轮次。

## 163. 每个非终态持久状态都需要孤儿恢复

只恢复 `running` 会遗留在写入 `paused` 后崩溃的进程：已经没有 owner 可以继续，启动恢复却
不会处理它。

- **正确做法：** 检测孤儿工作时枚举所有由租约持有的非终态。
- **发现位置：** Loop 恢复最初遗漏了持久化的 `paused` 记录。

## 164. 局部超时与全局时长预算是不同的停止原因

用单次操作超时代替不存在的全局截止时间，会把普通超时误报为预算耗尽。

- **正确做法：** 只有确实配置了全局时长限制时，才把 abort 映射为 `budget`；否则保留操作自身
  的超时/错误分类。
- **发现位置：** 未配置 `maxDurationMs` 时，Auto-Loop 曾把 verifier 的普通超时归类为
  `budget: duration`。

## 165. 回滚必须恢复派生编排状态，而不只是文件

诊断、连续通过次数、快照与续跑提示都对应特定工作区版本。回退文件却保留被拒绝版本的派生
状态，会让下一次决策针对一个已经不存在的工作区。

- **正确做法：** 回滚后重新运行权威验证，替换收敛基线，并在下一轮前持久化恢复后的结果。
- **发现位置：** Loop 退化回滚恢复旧 worktree 内容后，仍保留退化后的诊断与快照基线。

## 166. 写入端必须遵守读取端的持久化字节上限

分别限制嵌套元素大小和元素数量，并不能限制两者乘积。writer 可能生成合法的多 MiB 快照，
随后却被自己的有界 reader 拒绝。

- **正确做法：** 从历史快照移除重复载荷，在原子替换前检查总字节预算，超限时保留最后一份
  可读取文件。
- **发现位置：** 100 个 Loop 快照可重复保存 16 组 verifier 命令与输出尾部，超过 1 MiB
  状态读取上限。
- **同类问题：** Loop 验证智能限制了条目数与单条命令，却没有在 512 KiB 写入前按 UTF-8
  总字节淘汰旧条目。
- **同类问题：** Graph 调度历史限制了观测数量，却仍可能写出超过自身 128 KiB 读取上限的文件。

## 167. 证据存在不等于证据相关

仓库路径存在只能证明路径存在。把它直接当作验收标准的证明，会允许 evaluator 引用任意无关文件。

- **正确做法：** 要求内容锚点，并在有界、非符号链接的普通文件中核对引用的符号/文本或行区间。
- **发现位置：** Loop 验收最初把没有内容锚点的现有路径视为充分证据。

## 168. 持久控制命令必须绑定生命周期代次

控制命令可能刚通过“仍活跃”检查，owner 就完成退出。若持久邮箱只标识逻辑任务，这条迟到的
暂停或引导会在之后恢复时被重放，错误影响另一次运行。

- **正确做法：** 为每段存活的所有权周期生成并持久化代次 id；命令必须绑定该 id，消费端忽略
  其它代次的条目。入队后再次检查存活性，向调用方给出准确反馈。
- **发现位置：** 跨进程 Loop 控制原本可能在完成/恢复竞态中泄漏到下一次运行。

## 169. 终态后的副作用仍属于实体生命周期

任务到达 `passed` 并不意味着其通过后交付具有原子性。并发删除或第二次交付可能在第一次交付
仍进行时移除状态，或重复执行不可逆的 Git/PR 操作。

- **正确做法：** 在状态迁移和完整外部副作用期间持有同一实体租约，并持久化失败尝试以供显式重试。
- **发现位置：** Loop 交付原本在释放 Loop 租约后执行，也没有持久化失败状态。

## 170. 目录后缀不能唯一标识记录类型

同一目录可能包含状态快照、邮箱、日志和临时文件，而它们会共享宽泛后缀。把每个 `*.json`
文件名都传给严格 id 解析器，会让相邻记录类型破坏列表与恢复。

- **正确做法：** 在调用 reader 前，先按当前记录的精确 id/文件名语法过滤目录项。
- **发现位置：** Loop 状态枚举曾把 `<id>.control.json` 当成含点号的状态 id，导致列表直接抛错。

## 171. 空闲检查必须在首个异步间隙前完成占位

如果先检查进程内队列，经过一次 `await` 后才占位，前台操作就可能在观察与后台启动之间进入。
同样，仅检查进程内状态也无法证明另一进程没有活跃会话。

- **正确做法：** 解析物理仓库身份后同步安装本地占位，再取得跨进程协调租约与工作区 guard；
  任一层繁忙都直接跳过，而不是让空闲任务排队。
- **发现位置：** 后台 Loop 恢复最初没有覆盖服务器仓库队列与跨进程会话的原子空闲启动门禁。

## 172. Owner 关闭与用户取消是不同的持久结果

同一 AbortSignal 机制既可能表示用户显式决定，也可能表示后台工作 owner 的进程正在关闭。
把两者都持久化为终态取消，会让生命周期托管的任务无法恢复。

- **正确做法：** 把中止意图传入操作；owner 关闭应持久化为可恢复中断，并避免把基础设施中止
  记录成负向质量结果。
- **发现位置：** 关闭空闲 Loop 恢复曾把状态改为 `cancelled` 并记录失败的 skill 结果，导致
  下一台服务器跳过该任务。

## 173. 不可逆副作用成功后再持久化成功，并幂等完成收尾

如果在 Git、文件或远程副作用之前写入持久化 `delivered`，进程崩溃后成功标记可能仍在，
但对外宣称的产物从未生成。

- **正确做法：** 先持久化进行中尝试，执行主要副作用，再写入成功并幂等发布最终元数据；
  重试返回既有成功记录前必须验证或修复它。
- **发现位置：** Loop 的 checkpoint、merge 与 patch 交付曾在动作前写入 `delivered`，留下
  崩溃后假成功窗口。

## 174. 所有竞争状态迁移必须取得同一把生命周期锁

只检查另一把锁一次，无法阻止其 owner 在检查后立即启动。运行锁与交付锁分离时仍可能重叠。

- **正确做法：** 定义一把外层生命周期租约，让运行、恢复、交付和删除按一致顺序先取得它，
  再申请更窄的锁。
- **发现位置：** Loop 交付只采样一次运行租约，而恢复可在采样后仅取得运行租约并与 Git/状态
  修改竞态。

## 175. 空闲 guard 必须覆盖完整工作，并只授权其拥有的子会话

在等待后台操作前释放空闲 guard，会把原子空闲启动检查降级为过期快照；直接一直持有又可能
挡住后台操作自己的 Agent 与嵌套 Agent 会话租约。

- **正确做法：** 持有 guard 直到操作完成，并仅向该操作拥有的子会话传递经过验证的进程内
  guard 凭证。
- **发现位置：** Server Loop 恢复曾在 resume 前释放工作区 guard，外部 CLI 会话因而可能与
  后台编辑重叠。
- **同时发现：** Loop 与 Graph 的恢复记账在申请子生命周期租约时没有传递已持有的 guard
  capability，导致 guard 拒绝自身的退避写入或成功清理。
- **同时发现：** Graph runner 把空闲 guard 传给了子工作，却没有传给自己的主生命周期租约，
  导致真实空闲恢复拒绝自身。

## 176. 可恢复状态不代表 owner 已退出

记录可能已经是 `interrupted`，但 owner 仍在退出收尾或继续运行。仅凭状态返回它会启动第二个恢复。

- **正确做法：** 对所有可恢复状态（包括已有的 `interrupted`）应用存活 owner 过滤，并在加入
  恢复候选前执行检查。
- **发现位置：** Loop 恢复会为 `running` 与 `paused` 检查存活租约，却无条件返回所有持久化
  `interrupted` 记录。

## 177. 空闲所有权需要显式抢占握手

前台操作若只等待空闲维护 guard，可能被长时间后台工作饿死；直接删除 guard 又会破坏 owner
的互斥保证。

- **正确做法：** 只把空闲 guard 标记为可抢占，创建绑定 owner 的请求，让 owner 在协作边界中止，
  再通过有界、可中止的等待按正常流程重新获取。
- **发现位置：** 自动恢复正确地全程持有 guard 后，前台 Loop / 会话无法让它及时让出工作区。

## 178. 增量验证不能证明全局成功

按变更路径选择验证器只是基于不完整依赖信息的优化。把所选子集通过当作最终成功，会漏掉未映射的
跨包退化。

- **正确做法：** 只在子集仍失败时利用路径选择；一旦有阶段被跳过且子集通过，必须执行完整流水线，
  才能增加连续通过计数或返回成功。
- **发现位置：** 最初的增量 Loop 设计可能在未证明未选阶段仍为绿色时接受局部通过。

## 179. 保留策略必须重新核验可恢复性与副作用状态

仅凭年龄和数量不能认定编排记录可删除。中断任务或交付未完成的通过任务仍包含未来工作，且其状态
可能在列举与删除之间变化。

- **正确做法：** 排除活跃/可恢复状态及未最终完成的交付阶段；删除前立即重读记录并取得生命周期锁。
- **发现位置：** 自动 Loop 清理需要一个不会抹掉恢复或交付工作的终态谓词。

## 180. 显式发布产物时必须考虑忽略规则

把持久状态写入被忽略的目录后再执行普通 `git add`，并不会真正发布它。外围交付可能成功，
但审计记录仍只存在于可清理的 worktree 中。

- **正确做法：** 校验精确的仓库相对路径，只强制加入调用方明确选择的产物后再 merge 或 push；
  其他被忽略文件仍保持排除。
- **发现位置：** 被 `.gitignore` 排除的 `.seekforge/` 下最终 Loop 交付状态未进入 checkpoint、
  merge、patch 状态或拉取请求提交。

## 181. 祖先证据不能授权持续移动的分支或工作区

已验证 revision 仍在分支历史中，并不能说明之后的提交或未提交工作区变更也经过验证。发布其中
任何一类内容都可能带入验证器从未见过的修改。

- **正确做法：** 比较证据树与发布 tip、索引、已跟踪工作区和未跟踪路径；证据 revision 之后
  只允许精确且明确预期的元数据路径。
- **发现位置：** Loop merge 与 PR 重试曾接受记录 revision 的任意后代，可能发布之后加入的
  未验证提交或本地修改。

## 182. 容器清理必须加入所有内部生命周期

只检查 worker 锁无法覆盖交付或其他暂时不持有窄锁的生命周期阶段。

- **正确做法：** 删除 checkout 前取得工作区 guard，重新检查内部 owner，并持有到破坏性删除完成。
- **发现位置：** 保留的 Loop worktree 在交付生命周期租约活跃时仍可被删除。

## 183. 持久图身份包含执行位置

即使任务和验证命令文本相同，同一节点在另一个物理工作区执行也不是同一个已完成操作。

- **正确做法：** 只解析一次节点工作区，并把物理身份写入恢复所用的检查点指纹。
- **发现位置：** `workspaceForNode` 把节点改映射到另一个 checkout 后，Loop DAG 恢复仍复用旧完成结果。

## 184. 整体清理不能破坏自己的前置条件

在检查 worktree 是否干净之前删除已跟踪的子记录，会自行制造脏 checkout 并导致清理失败。

- **正确做法：** 在 guard 下重新核验完整容器并整体删除；只有保留容器时才逐条清理记录。
- **发现位置：** `loop-prune --worktrees` 曾先删除已跟踪的 Loop 状态，再拒绝由此变脏的 worktree。

## 185. 缺少证据的旧成功状态仍是未完成状态

旧格式没有支撑证据时，迁移后的成功标签不能证明旧版不可逆动作确实发生。

- **正确做法：** 把无证据的旧成功状态规范化为受保护的中间阶段，显式修复，并让元数据修改与
  生命周期串行化。
- **发现位置：** 旧 Loop `delivered` 记录曾被清理视为最终完成；并发优先级写入也可能被 owner 覆盖。

## 186. 派生更窄的整数预算前先验证输入

正的有限小数时长在下游舍入单次尝试预算时可能变成零，导致通过外层验证后又违反被调用方契约。

- **正确做法：** 在减去已用时间和向下取整派生预算之前，就在外层边界要求正安全整数。
- **发现位置：** Loop DAG 曾接受小数 `maxDurationMs`，可能生成无效的零毫秒节点预算。

## 187. 交付证据必须源自 verifier，而不只是 Git

先前验证通过后再 checkpoint 当前树，会把验证到交付之间产生的修改合法化，却没有测试这些内容。

- **正确做法：** 创建或最终确认交付证据前，针对精确的 checkpoint 发布树重新运行完整持久验证契约。
- **发现位置：** Loop 首次交付曾提交 pass 后新增的文件，并把所得 revision 视为已验证。

## 188. 元数据提交后再次验证，并发布不可变对象

提交前的范围检查无法覆盖 commit hook 创建的文件或提交，也无法覆盖 merge/push 前移动的分支引用。

- **正确做法：** 最终元数据提交后再次检查范围，通过已检查的对象 id 而不是可变分支名进行
  merge/push，并禁止该发布路径自动提交脏内容。
- **发现位置：** finalized 状态的 post-commit hook 可新增文件，随后被 `mergeWorktree` checkpoint 并合入。

## 189. 干净 checkout 仍可能拥有未合并提交

工作区干净并不能说明删除它的分支不会丢失已提交历史。

- **正确做法：** 非 force 清理前要求保留分支可从基线 checkout 到达，并在删除引用前保守地再次检查。
- **发现位置：** Loop 自动 worktree 清理曾删除 finalized merge 交付后新增提交的唯一引用。

## 190. 持久身份必须覆盖注入的可执行行为

JSON 序列化会忽略函数，因此对 options 对象做哈希无法发现注入 verifier 实现或捕获配置的变化。

- **正确做法：** 持久节点含自定义可执行行为时要求调用方提供稳定 verifier 身份，并把它纳入恢复指纹。
- **发现位置：** `options.verify` 改变后，Loop DAG 恢复仍复用了已通过节点。

## 191. finalized 标签不是完整交付证据

显式阶段标签可能来自部分写入、迁移或畸形状态；单独标签无法证明不可逆副作用已经完成。

- **正确做法：** 在保留策略判断前，把缺少对应模式完整证据的 finalized 交付规范化回受保护中间阶段。
- **发现位置：** 显式 `finalized` 但无证据的 Loop 记录仍可被清理。

## 192. 重新打开的持久任务必须清除旧完成标记

已完成检查点可能因重跑或失效而重新变为活跃状态。如果可选的完成时间仍被保留，读取方会把暂停中
或仅完成部分重跑的图误判为已结束。

- **正确做法：** 持久操作重新打开时显式清除终态元数据，只有新的全部终态条件成立后才再次写入。
- **发现位置：** Loop DAG 使用 `rerunFrom` 后在新的审批门暂停，仍保留了旧 `completedAt`。

## 193. 发现标记必须是所选根目录内的物理文件

存在性检查会跟随符号链接。链接的清单或锁文件可能让自动发现路径依据工作区外状态选择命令。

- **正确做法：** 检查根目录条目本身，只接受非符号链接的普通文件，并让清单读取保持有界且不跟随链接。
- **发现位置：** Loop 自动验证曾把符号链接的 Cargo 与包管理器标记当作项目自身的发现证据。

## 194. 副作用后的必需策略必须跨进程与重试持久存在

如果必需闭环只存在于回调或 CLI 参数中，中断后它会消失，重试便可能直接最终完成已经发布的副作用。

- **正确做法：** 把冻结策略与进度和副作用证据一起持久化；持久闭环未通过时拒绝最终完成。
- **发现位置：** PR 交付重试曾可绕过最初的 `--wait-ci` 门禁。

## 195. 长时间外部监听必须异步且由取消信号管理

同步子进程等待会阻塞协作式取消与生命周期清理，即使外层编排已经接受 AbortSignal。

- **正确做法：** 异步启动进程，限制输出与时长，通过 `onAbortOnce` 订阅取消，并在取消时终止完整进程树。
- **发现位置：** `gh pr checks --watch` 曾可能在全部超时时间内阻塞 Ctrl-C。

## 196. 并发调度器必须响应单个任务完成

等待整批启动任务会形成隐式屏障：快速任务无法解锁下游，直到无关的慢任务结束。

- **正确做法：** 为每个运行节点保留资源与预算预留，竞争单个完成事件，只释放该节点预留并立即重新调度。
- **发现位置：** Loop DAG 每批吞吐曾被最慢节点限制。

## 197. 声明产物必须验证物理包含关系

看似相对的输出路径在执行后可能是符号链接，或解析到节点工作区之外。

- **正确做法：** 校验可移植相对路径语法，拒绝符号链接和非文件，解析物理目标并证明其位于物理工作区根目录下。
- **发现位置：** Loop DAG 的依赖输出原先没有经过验证的文件产物契约。

## 198. 缓存的验证证据必须绑定被验证状态

阶段 id 与迭代号只标识调用位置，并不标识当时通过的工作区内容。若其他 verifier 或回滚已改变文件，
复用旧结果会绕过权威完整门禁。

- **正确做法：** 只允许在一次增量到完整验证的转换内复用，把结果绑定完整工作区指纹；指纹不确定
  或已变化时禁止复用。
- **发现位置：** Auto-Loop 验证曾只按迭代与阶段 id 缓存，回滚后可能复用被拒绝工作区的成功结果。

## 199. 启动已授权副作用前先持久化授权

内存审批通过后立即执行存在崩溃窗口：副作用已经开始，而持久状态仍显示等待审批。

- **正确做法：** 先持久化独立的“已审批但未完成”状态；恢复时不重复询问，且只由终态执行结果替换。
- **发现位置：** Loop DAG 在节点执行前未写入审批检查点，而恢复会删除全部等待记录，可能造成重复审批或执行。

## 200. 发现结果必须独立满足消费者契约

一个根检测器未产生命令时，不应压制有效的子检测器；多个分别有界的来源合并后仍可能超过共享上限。

- **正确做法：** 独立运行适用的发现根，为权威全局门禁预留容量，并在合并后再次执行消费者总上限。
- **发现位置：** monorepo 子包测试依赖根脚本被识别；package、Cargo、Go 与 Python 阶段合并后还可能超过
  Loop 的 16 阶段上限。

## 201. 可选修复前置条件必须惰性加载

配置了修复策略并不代表一定需要修复。在观察到失败前加载 provider 凭据、信任提示、MCP 进程或 profile，
会让无需修复的成功路径失败，并产生无关副作用。

- **正确做法：** 先判断外部门禁，只有失败结果满足修复条件后才初始化修复专用依赖。
- **发现位置：** `loop-deliver --wait-ci` 曾在 PR checks 已通过时仍预先初始化 Agent/MCP 配置。

## 202. 每个异步 UI 提交都必须绑定所选资源代次

筛选、轮询、选择与分页可能重叠；请求顺序不等于响应顺序，旧成功、错误或 `finally` 都可能覆盖当前资源。

- **正确做法：** 为每条独立请求流分配 latest-generation token，捕获所选资源 id，并守护成功、失败、追加与 busy 清理。
- **发现位置：** Desktop Loop 管理可能显示旧筛选结果，或把先前所选 Loop 的历史追加到当前列表。
- **还发现：** Desktop Graph 的模板发现与预检曾共用同一个 token，启动预检会丢弃仍有效的模板响应，切换工作区还可能遗留 busy 状态。

## 203. 取消错误跨包装层时仍是控制流

若把 abort 放进通用命令结果封装，下一层可能把它解释为普通非零退出，并持久化领域失败。

- **正确做法：** 在解释命令状态前重新抛出取消，并让可重试持久状态与真实外部检查失败保持区分。
- **发现位置：** 被取消的 `gh` CI 监听曾被记录成 checks 失败或缺少日志。

## 204. 派生工作区必须在取得协调权后再创建

名称确定并不代表 worktree 创建不存在竞态；Git 分支相同也不能证明其 checkout 仍位于编排状态预期的
受管路径。

- **正确做法：** 先以无副作用方式推导调度器身份并取得 lease，再创建资源；恢复时同时绑定分支身份与
  精确物理路径。
- **发现位置：** 托管 Loop DAG worktree 曾在取得 DAG lease 前创建，恢复时也只按分支名复用，可能造成
  并发创建或路径重绑定。

## 205. 派生聚合证据必须随输入一起失效

持久化 fan-in、摘要或聚合验证只对生成它的精确节点结果与编排策略有效。重新运行输入或改变集成策略后，
旧聚合结论已经过期。

- **正确做法：** 把影响行为的策略写入持久指纹，并在任一贡献结果失效时清除聚合证据。
- **发现位置：** Loop DAG 的 `rerunFrom` 曾保留已通过的 fan-in，而依赖集成开关也未进入恢复指纹。

## 206. 失败的聚合工作仍必须消耗共享预算

只有终态成功后才记账会漏掉失败或耗尽的聚合修复成本，使后续工作可能超过声明的共享上限。

- **正确做法：** 有界子任务返回后立即记入用量，无论状态都保存其结果，并把观察回调失败与完成流程隔离。
- **发现位置：** 失败的 Loop DAG fan-in 曾未计入持久化成本与 token 总量，抛错的 `onFanIn` 观察器还会
  丢弃已完成检查点。

## 207. 重叠路径前缀必须按最具体匹配分类

第一个命中的前缀可能只是宽泛父目录，而后面的更窄前缀才携带真实依赖或归属语义。验证仍会执行，
但解释信息与策略分类会出错。

- **正确做法：** 规范化全部候选，选择最长的路径边界匹配，再按这个最具体前缀判定直接或依赖关系。
- **发现位置：** 当宽泛直接前缀排在嵌套依赖前缀之前时，Loop 验证曾把依赖变更误标为直接变更。

## 208. 破坏性资源身份必须带类型化来源

通用产物字符串可能恰好长得像托管分支名。只按前缀推断所有权，可能让归档、合并或清理作用于无关 checkout。

- **正确做法：** 用独立且已验证的字段持久化托管分支，并在每次修改前把物理路径重新绑定到精确托管根目录。
- **发现位置：** Loop DAG 资源清理曾从以 `seekforge/` 开头的用户声明产物路径推断分支。
- **同类问题：** Loop DAG fan-in 曾把任意以 `seekforge/` 开头的字符串视为受管来源；
  解析或提升 worktree 前必须校验完整的受管分支语法。

## 209. 仓库级配额必须使用仓库级协调

即使在操作专用 lease 下检查资源数量，只要另一个不同 id 的操作可在首次操作提交前创建资源，仍然存在竞态。

- **正确做法：** 在计数、预留、创建及延迟派生资源创建的全过程持有统一资源族 lease，清理也使用同一把锁。
- **发现位置：** 两个并发托管 Loop DAG 都可能通过 worktree 上限检查，最终留下超过配置上限的 worktree。

## 210. 持久记录内嵌标识符必须使用各自语法

父记录 id 与内嵌候选/节点 id 往往有意采用不同长度限制。复用父级校验器会让刚写入的合法状态无法读取，
未检查的可选字段也会污染受信类型状态。

- **正确做法：** 按声明语法验证每个内嵌字段，并在类型转换前核验引用关系与状态关系。
- **发现位置：** 57–64 字符的合法推演候选 id 写入后会被重新加载拒绝，winner/error/时间字段也曾未校验。

## 211. 组合后的标识符必须再次核验最终语法

单个安全路径段在加上前缀和分隔符后，仍可能生成过长标识符，或携带目标 schema 禁止的字符。

- **正确做法：** 先规范化组合结果，用确定性 hash 后缀限制长度，并按最终消费者语法校验，而不只校验来源片段。
- **发现位置：** 过长或带点的 workspace 目录名会生成被 Loop 阶段校验器拒绝的自动发现验证阶段 id。

## 212. 衰减证据的成熟度必须看有效质量

历史样本的权重即使已衰减到接近零，若仍按原始数量判定成熟，古老数据仍可能通过平局规则覆盖确定性默认值。

- **正确做法：** 同时要求原始样本下限与最小有效权重，并用有效质量而不是原始数量计算置信度与平局排序。
- **发现位置：** 多年前的 Loop 恢复观察在声明的时间衰减后仍可能选中非默认策略。

## 213. 空的可选资源不得初始化对应后端

当操作没有任何派生资源时，不应初始化只用于枚举或修改这些资源的后端；工作区完全可能合法地不具备该后端。

- **正确做法：** 核验持久状态后先返回空结果，再决定是否打开 Git、数据库、网络或托管根目录资源。
- **发现位置：** 在非 Git 工作区检查或清理已完成的非托管 Loop DAG，仍会调用 `git worktree list` 并失败。

## 214. 创建派生状态前必须完成拓扑校验

字段本身合法的图节点仍可能形成依赖环。如果 lease、checkpoint 或 worktree 已经创建，
到调度器内部才发现环就太晚了。

- **正确做法：** 节点与引用校验完成后、首次取得生命周期锁、持久写入或创建资源之前，
  对完整图执行无环拓扑检查。
- **发现位置：** Loop DAG 曾在运行时初始化及首个 checkpoint 之后才检测依赖环，
  非法图可能留下持久副作用。

## 215. 多入口镜像边界校验器必然发生漂移

两个适配层即使起初遵循同一契约，也会在新增字段与边界条件后悄然分叉。更严格的 CLI 保护不了
Core 或 Server 的直接调用，而被某个 decoder 漏掉的字段还会无报错消失。

- **正确做法：** 传输结构解码保持轻量，随后调用唯一的已导出语义校验器；字段 decoder 与 predicate
  也从同一所有者导出复用。
- **发现位置：** CLI 与 Core 的 Loop DAG 校验对重复依赖和包含 NUL 的产物路径处理不一致，
  CLI 还会静默丢弃 `verifierId`。
- **同时发现：** Loop 与 Graph 分别解码同一个自动恢复子记录，但只有 Graph 会拒绝未知字段和
  前后倒置的重试时间戳。

## 216. 嵌套授权必须拥有带限定范围的持久状态

父级与嵌套作用域复用同一个叶子 id 时，原本针对一个节点的批准可能误授权同名的另一个节点。

- **正确做法：** 外部批准必须限定范围，在子作用域产生副作用前独立持久化，并在父级恢复子图时要求存在匹配的子检查点。
- **发现位置：** 工程图嵌套审批门可能继承父级同名批准，或在恢复时迫使已完成的子作用域副作用再次执行。

## 217. 超时不等于资源已经收敛

超时竞速获胜不代表落败的异步操作已经停止。立即重试会让多次尝试重叠，并可能在调度器记为失败后继续修改共享状态。

- **正确做法：** 中止超时操作，等待它真正结束，再重试或释放 owner 租约。
- **发现位置：** 工程图函数节点超时后仍可能保持活跃，同时下一次重试已经启动。

## 218. 恢复指纹必须包含递归派生位置

只对嵌套定义做 hash、却不绑定其已解析子位置，会让父图在物理工作区映射变化后仍复用已完成子图。

- **正确做法：** 在生命周期副作用前递归解析并校验每个嵌套物理工作区，并把限定路径加入父图指纹。
- **发现位置：** 工程图父级指纹最初只绑定了顶层节点工作区。

## 219. 暂停 owner 不得遗留在途子任务

调度器不能在已启动子任务仍在修改状态时持久化 `paused` 并释放自己的租约。

- **正确做法：** 停止启动新工作，等待全部在途子任务结束，写入这些结果，之后才能暴露暂停状态或释放所有权。
- **发现位置：** 工程图审批门原本会立即返回，而独立节点仍在没有图 owner 的情况下继续运行。

## 220. 单项有界不代表聚合后仍有界

每个输出、事件、任务或列表项各自合法，乘以最大数量后仍可能超过外层检查点或响应上限。

- **正确做法：** 限制序列化定义及保留输出/事件总量；列表接口省略重量级详情字段。
- **发现位置：** 单项有界的工程图节点输出与事件仍可能突破 1 MiB 检查点，或生成很大的 REST 列表。

## 221. 工作流产生副作用前必须解析全部扩展注册项

直到节点就绪才发现命名处理器缺失，会让无效图在失败前先由早期节点修改工作区。

- **正确做法：** 只通过对象自身的数据属性解析每个扩展引用，拒绝 getter 与原型回退，并在租约或节点副作用前完成。
- **发现位置：** 未注册的工程图函数处理器最初只会在节点实际执行时失败。

## 222. 稀疏数组与定时器溢出会绕过普通范围检查

JavaScript 的数组迭代可能跳过空洞；Node 还会把过大的定时器延迟压成近乎立即超时，即使该数字仍是安全整数。

- **正确做法：** 要求数组每个索引都是自身属性，并把延迟限制在运行时支持的工作范围内。
- **发现位置：** 稀疏工程图依赖/路由与 Loop DAG 重跑选择器可能逃过元素校验，过大的节点超时则表现为立即超时。

## 223. 展示边界不能重放已完成的副作用

序列化、输出大小或展示整形失败可能发生在有副作用操作已经成功完成之后。把这类失败当成可重试错误，会仅仅因为遥测数据不便保存而重复执行副作用。

- **正确做法：** 把已完成输出转换成有界、可序列化的摘要且不改变执行结果；同时单独拒绝从未产生终态事件的流。
- **发现位置：** 已成功的工程图 Agent 或函数可能因为返回输出超过检查点限制而被重试。

## 224. 并发预留需要重叠检查与串行结算

只检查键值不相等，阻止不了祖先路径与后代路径重叠；各自完成的 Promise 也不能基于同一个旧快照安全执行共享聚合上限。

- **正确做法：** 成对拒绝祖先/后代资源作用域，并在唯一 owner 控制的完成点结算共享额度。
- **发现位置：** 并发工程图或 Loop DAG 节点可能修改嵌套工作区，且工程图节点可能共同突破保留输出总预算。

## 225. 审批回调必须返回精确的肯定值

真值不等于授权契约。未受 TypeScript 约束的嵌入方可能误返回字符串、对象或数字状态，而这些值不应跨过显式审批边界。

- **正确做法：** 只有布尔值 `true` 才视为回调批准，并在产生副作用前校验全部序列化审批选择器。
- **发现位置：** 工程图审批回调返回非布尔真值时也可能通过审批门。

## 226. 已收敛的工作仍需要持久结算

中止并等待在途工作可以阻止孤儿修改，但如果 owner 在释放租约前没有记录其完成或取消结果，恢复过程仍无法复用这些结果。

- **正确做法：** 让紧急清理结果经过同一个串行结果与检查点通道；若持久化本身失败，则仍保留原始调度错误。
- **发现位置：** 异常停止的工程图虽然等待了子 Promise，却可能因未记录最终结果而在恢复时重复其副作用。

## 227. 取消需要结算后的再次检查

最后一个在途项完成时，待处理与活跃集合可能同时变空，调度器因此不会再进入下一轮循环头的取消检查。

- **正确做法：** 在调度循环结束后、推导成功或失败终态之前，再次检查 owner 的取消信号。
- **发现位置：** 取消工程图最后一个节点时，循环会在结算后立即退出，导致结果被报告为 `failed` 而不是 `cancelled`。

## 228. 可选选择器解码必须拒绝“存在但格式错误”

如果把类型错误的已传值当成可选选择器未传，会把审批、重跑或恢复请求静默变成另一种操作。

- **正确做法：** 区分缺省与格式错误，拒绝有歧义的别名组合，再把选中的数组交给共享语义校验器。
- **发现位置：** Graph REST 适配器最初会把字符串形式的审批或重跑选择器当成未提供选择器。

## 229. 并发保护需要考虑依赖可达性

调度器的并发配置表达的是上限，并不能证明任意两个节点都可能重叠执行。如果不考虑传递依赖顺序就拒绝共享资源，会阻断安全的串行工作流。

- **正确做法：** 仅对彼此都不存在传递依赖关系的有副作用节点对执行重叠排除。
- **发现位置：** `maxConcurrency > 1` 的 Graph 即使两个节点必须前后执行，也会因为共享工作区而被错误拒绝。

## 230. 新 owner 不能接管陈旧的派生检查点

确定性的子 id 能支持崩溃恢复，但也可能发现来自更早、已删除或中断 owner 的孤儿记录。新父级在碰撞后自动重试时，不能把该陈旧子记录转成可信进度。

- **正确做法：** 仅允许显式父级恢复，或当前节点尝试序列自己创建的子检查点被复用；预先存在的碰撞应不可自动重试，直到调用方显式重启。
- **发现位置：** 新 Graph 的子图首次尝试可能因已有子检查点失败，却在自动重试时错误接管它。

## 231. 恢复中的子图用量属于在途预留

恢复前删除父级等待结果，会暂时从父检查点移除成本与令牌，但持久子图仍然拥有这些用量。

- **正确做法：** 调度前预留持久子图用量，把它计入并发预算计算，并在父级结果结算时原子替换该预留。
- **发现位置：** 恢复的子图可能获得一份全新的完整预算，使并发父节点共同超出 Graph 预算。

## 232. 运行期上限不属于持久身份

即使子工作流定义没有变化，父级每次重试计算出的本次剩余预算也可能不同。

- **正确做法：** 把运行期上限排除在持久定义指纹之外，并单独校验。
- **发现位置：** 恢复中的 Graph 子图曾因父级新计算的预算份额改变指纹而拒绝自己的检查点。

## 233. 中间检查点也必须满足加载器不变量

如果在终态元数据或最终验证落盘前就发布终态，会产生一个加载器必然拒绝的崩溃窗口。

- **正确做法：** fan-in 期间持久化显式 running 阶段，并把状态、证据、用量和完成元数据一起转入终态。
- **发现位置：** Graph fan-in 曾在 `completedAt` 之前发出 `passed`，导致 fan-in 开始时崩溃后无法恢复。

## 234. 资源归档只属于一个运行世代

如果归档标记只按可复用工作流 id 建索引，它可能授权清理后来重启所创建的资源。

- **正确做法：** 把归档标记绑定到不可变运行世代，清理前要求精确匹配。
- **发现位置：** 已清理并重启的托管 Graph 会继承上一轮运行的 archived 状态。

## 235. 内部资源 id 必须使用不相交命名空间

用 `integration` 这类普通用户节点 id 标识内部 worktree，会让合法定义与 fan-in 资源发生别名冲突。

- **正确做法：** 使用用户 id 语法无法表达的内部标识，并通过同一 helper 推导所有预期分支。
- **发现位置：** 名为 `integration` 的 Graph 节点可能与 fan-in 共用托管 worktree。

## 236. 透明编排节点必须保留产物祖先关系

审批门与路由器携带控制状态但没有分支。只查看直接依赖会让下游工作与最近的有副作用祖先断开。

- **正确做法：** 穿过已通过的无副作用依赖，直到找到有类型的托管来源，并且每个来源只合并一次。
- **发现位置：** 托管 Graph 中位于审批门后的 consumer 无法收到 producer 已提交的修改。

## 237. 模板替换必须失败关闭

把未声明占位符替换成 JavaScript `undefined`、接受额外值或遍历稀疏模板数组，都可能静默生成另一张工作流。

- **正确做法：** 校验自身参数声明与传入键，保留完整占位符的类型，拒绝未解析名称，并在替换后继续执行稠密数组检查。
- **发现位置：** Graph 模板插值最初缺少显式的未知占位符边界。

## 238. 聚合后的提示上下文还需要总量上限

即使分别限制每段日志、错误或历史尝试，组合后的恢复上下文仍可能无限增长。

- **正确做法：** 发送给模型前，对最终序列化内容再做一次整体截断。
- **发现位置：** Loop 恢复最初限制了各字段，却没有限制组合后的上下文胶囊。

## 239. 影响遥测必须区分“被选中”和“实际执行”

规划器选中的阶段仍可能因前置失败而阻塞，或因缓存命中而复用结果。

- **正确做法：** 显式报告运行、跳过、复用和阻塞决策，而不是宣称所有被选中的阶段都已运行。
- **发现位置：** Loop 影响报告最初只反映计划，没有反映最终执行结果。

## 240. 每个事件检查点都必须满足持久化状态不变量

即使最终检查点有效，调度器在补齐跳过或等待结果期间，终态或暂停态仍可能暂时无效。

- **正确做法：** 准备性节点事件使用非终态写盘；等待结果落盘前先切换为 `paused`；只有所需结果和时间戳全部存在后才发布终态。
- **发现位置：** Graph 取消与嵌套审批事件曾短暂写出重启校验无法接受的检查点。

## 241. 在兄弟节点产生副作用前校验派生恢复状态

父级指纹可能匹配，但单独持久化的子检查点仍可能带有过期来源、身份或解析位置。直到子节点启动才发现不匹配，会让独立兄弟节点先发生变更。

- **正确做法：** 发布恢复事件或调度任何节点前，按预期父级来源和独立派生指纹预检每个保留的子检查点。
- **发现位置：** 恢复 Graph 曾在证明子检查点属于当前父定义和工作区映射前，就预留其用量。

## 242. 加载器必须重新执行展示预算

只在写入侧截断，无法保护恢复、列表或详情路径免受旧版本、嵌入方或本地篡改写出的“语法有效”检查点影响。

- **正确做法：** 解码持久化状态时，同时执行单项和聚合序列化输出上限。
- **发现位置：** Graph 加载器曾接受实时调度器本应截断的节点输出，从而绕过保留输出契约。

## 243. 合成事件必须到达所有事件接收端

观察器失败可能在原事件已发送到历史之后生成 warning。若只把它加入内存检查点，持久化轨迹就会与权威的近期事件窗口不一致。

- **正确做法：** 把合成 warning 写入每个持久化事件接收端，同时隔离二次可观测性失败。
- **发现位置：** Graph 观察器 warning 曾写入检查点，却没有进入轮转 JSONL 历史。

## 244. 取消必须规范化结算期间新出现的等待工作

取消后等待在途工作结算时，仍可能新产生 `waiting_approval` 结果。只要等待结果仍存在就发布 `cancelled`，会违反持久化状态/结果不变量。

- **正确做法：** 先结算在途工作，在始终有效的中间状态下把所有等待结果转换为保留用量的取消跳过态，再补齐未启动节点并发布终态检查点。
- **发现位置：** 子图可能在父图排空取消期间进入暂停，最终留下无法加载的取消检查点。

## 245. 并行验证必须显式声明互斥资源

验证器即使被描述为只读门禁，也可能格式化文件、生成代码、更新快照或预热共享缓存。拓扑独立并不代表两个命令可以安全重叠。

- **正确做法：** 默认保持顺序执行；并行必须显式选择并声明不重叠的逻辑资源，已启动波次全部结算后再继续，必需阶段失败后不再启动新波次。
- **发现位置：** 把所有无依赖 Loop 验证阶段并发化会改变遇错停止语义，并让修改工作区的验证器互相破坏缓存。

## 246. 崩溃日志必须包围副作用与结算

`started` 事件只是可观测性，不是持久重试契约。进程退出后，owner 必须区分尚未开始的工作与结果尚未发布的副作用。

- **正确做法：** 副作用前持久化稳定 attempt/幂等身份，原子发布终态结果与日志移除，只在崩溃恢复时复用键而不在显式重跑时复用，并明确报告中断尝试。
- **发现位置：** Engineering Graph 恢复原先只有节点开始事件，函数副作用可能在没有稳定去重键的情况下重复。

## 247. 暂停状态需要持久化原因

审批暂停与操作员暂停具有不同加载不变量和恢复策略。只根据等待节点推断会让合法控制暂停无法加载，或让空闲恢复越过审批边界。

- **正确做法：** 持久化封闭的暂停原因枚举，仅审批暂停要求等待结果，并且只自动恢复明确可恢复的暂停类别。
- **发现位置：** 安全边界 Graph 暂停无法复用原有“paused 必须存在 waiting_approval”不变量。

## 248. 嵌套资源仍归父级生命周期所有

子工作流可能创建分支或 worktree，而其检查点位于父级之下。只检查直接结果分支会让父级归档、清理、重启和删除遗漏这些资源。

- **正确做法：** 通过同一 owner helper 递归推导子级身份，从父级统计中排除单独计量的后代，按物理路径先清理后代，并保留脏后代的所有祖先。
- **发现位置：** 启用嵌套 Graph 托管 worktree 时，子分支最初不在父级资源生命周期内。

## 249. 失败的并行批次必须等待所有已启动同伴结算

快速失败聚合会在一个操作拒绝后立即返回，而兄弟副作用仍在运行，使重试、清理或结果发布与孤立工作重叠。

- **正确做法：** 对已启动副作用批次使用全量结算聚合，所有同伴结算后才发布首个有界失败。
- **发现位置：** Graph map 元素失败后，同批其他处理器副作用仍可能继续运行。

## 250. 持久控制必须绑定 owner 存活状态，而非进程内注册表

合法工作流 owner 可能位于另一进程，或由空闲恢复启动，不会出现在接收服务器的内存运行表中。

- **正确做法：** 按已校验运行身份和共享存活租约授权持久控制；本地注册表只用于本进程拥有的取消句柄。
- **发现位置：** Graph 暂停/指导曾拒绝存活的跨进程与空闲恢复 owner。

## 251. 子检查点保留策略跟随可恢复父级

当父级仍可恢复，并依赖子检查点恢复用量与副作用时，终态子图不能独立删除。

- **正确做法：** 只对根工作流应用终态保留策略，保留可恢复父级的后代，并随终态 owner 删除同根后代。
- **发现位置：** 年龄/数量清理可能删除暂停 Engineering Graph 下已经通过的子图。

## 252. 遍历前必须校验完整 Pointer 语法

只检查起始斜杠会接受格式错误的转义序列，不同 JSON Pointer 实现可能对其产生不同解释。

- **正确做法：** 校验完整有界 Pointer 语法，只解码 `~0` 与 `~1`，并阻止原型键和访问器。
- **发现位置：** Graph 输入绑定曾接受解析器未定义的 `~2` 转义。

## 253. `allSettled` 无法捕获构造输入数组时发生的同步异常

在 `items.map(...)` 中直接调用副作用，会在 `Promise.allSettled` 收到数组之前执行它。同步异常会中断映射，先前已经返回的 Promise 既不会被等待，也不会写入检查点。

- **正确做法：** 通过 `Promise.resolve().then(() => effect())` 进入每个可能同步执行的副作用，再把这些 Promise 交给 `allSettled`。
- **发现位置：** Engineering Graph 的同步 map handler 失败曾绕过成功同伴的结算和项级检查点。

## 254. 持久邮箱 claim 必须在检查点之后确认

在工作流结果持久化前删除已 claim 事件，会在崩溃时丢失事件；永不删除则会最终耗尽有界邮箱。

- **正确做法：** 在权威工作流检查点完成前保留 claim，随后在邮箱租约内确认并删除。
- **发现位置：** 已完成的 Graph 等待信号会永久累积，而提前清理又会形成丢失窗口。

## 255. 动态 fan-out 必须拆分父级剩余预算

把完整父级预算交给并发批次中的每个子项，会按 fan-out 宽度放大对外声明的额度。

- **正确做法：** 每批启动前扣除已提交子项用量，并只在即将启动的子项之间拆分剩余额度。
- **发现位置：** Engineering Graph 的每个 map 元素都曾收到完整节点成本/token 预算。

## 256. 文件校验必须在读取描述符后重新绑定路径

已打开描述符在 rename 后仍然稳定，但流式哈希期间，对外发布的路径可能已重新绑定到另一 inode。

- **正确做法：** 流式读取描述符前后都比较设备/inode 与物理路径；两次绑定一致时才发布证据。
- **发现位置：** 已验证 Graph artifact 证据可能描述初次身份检查后已经变化的路径。

## 257. 数字转换前必须先处理取消哨兵值

UI prompt 取消通常返回 `null`，而 `Number(null)` 会静默变成零。

- **正确做法：** 解析或截断数值前，先分别处理取消与空输入。
- **发现位置：** 取消 Desktop Graph 优先级 prompt 曾会提交优先级 `0`。

## 258. 内部调度键不能复用面向用户的层级语法

把原始文件系统路径嵌入逻辑资源 id，会让普通路径标点意外获得调度语义。

- **正确做法：** 用带域前缀的哈希编码精确内部身份；层级分隔符只留给声明式逻辑资源。
- **发现位置：** Loop DAG 工作区 `pkg` 与 `pkg.child` 曾被误判为父子资源冲突。

## 259. 数值契约必须能经受 JSON 规范化

`NaN`、无穷值和负零等内存数值无法通过 JSON 保持原始语义往返。若持久化 schema 接受它们，恢复后的指纹或校验行为可能发生变化。

- **正确做法：** 拒绝契约中的非有限数值，并在计算指纹或持久化前规范化有符号零。
- **发现位置：** Graph schema enum 曾接受恢复后语义与原始定义不同的数值。

## 260. 终态实时订阅需要明确释放点

重连注册表的生命周期长于单次请求。若已完成后台运行仍留在注册表中，后续每次重连都会重新订阅不可变历史，并在长期 UI 会话中持续泄漏条目。

- **正确做法：** 非终态帧推进 cursor，收到终态帧后立即移除订阅。
- **发现位置：** Desktop 曾将已完成的 Graph Run Ledger 订阅保留到所属标签页关闭。

## 261. 累计时长预算必须持久化活跃耗时

只使用本次调用计时器，会让每次持久恢复都重置工作流时长额度；使用创建到完成的墙钟时间又会产生相反问题，把审批、信号等待和离线暂停计入执行时间。

- **正确做法：** 在检查点中累计活跃耗时，只增加当前 owner 的运行时间，并让调度、嵌套预算、摘要和运行对比统一使用该值。
- **发现位置：** Loop DAG 与 Engineering Graph 的时长预算曾在恢复时重置，反复暂停可以绕过配置上限。

## 262. 持久事件既需要唤醒发现，也需要检查点后对账

正确的 claim 顺序可以避免事件丢失，但它本身不会让暂停工作流进入恢复候选，也无法关闭工作流检查点完成后、邮箱确认前的崩溃窗口。

- **正确做法：** 让恢复扫描检查持久事件是否就绪，并在继续或替换运行前，对已经体现在已提交工作流结果中的 claim 做确认回收。
- **发现位置：** 已入队的 Graph 信号曾无法唤醒空闲恢复；等待节点通过结果写入检查点后若进程崩溃，其已 claim 信号还会永久保留。

## 263. 持久人工暂停不是失去 owner 的运行

进程退出后两种状态都没有活跃 owner，但意图不同：失去 owner 的运行中检查点请求恢复，显式暂停则请求保持静止。

- **正确做法：** 根据持久生命周期原因判断恢复；恢复失去 owner 的运行工作与已就绪等待，但用户/控制暂停和审批暂停必须收到显式继续操作。
- **发现位置：** 空闲恢复曾自动继续用户显式暂停的 Loop 与 control 暂停的 Engineering Graph。

## 264. 恢复记账只能接受已知的相邻运行代次

自动尝试既可能在发布新运行身份前失败，也可能在发布后失败。只绑定一个身份会漏记早期失败；直接更新当前身份又会让迟到失败污染后续运行。

- **正确做法：** 捕获尝试前身份，提前分配本次尝试身份，并且仅当检查点仍匹配这两个已知相邻代次之一时写入失败元数据。
- **发现位置：** Graph 恢复退避可能漏掉 provider 初始化失败，或与较新的前台恢复发生竞态。
- **同时发现：** Loop 恢复失败记账没有尝试代次，迟到失败可能覆盖较新的前台结果。

## 265. 新身份校验必须保留旧版哨兵值

持久化迁移可能使用当前身份校验器会拒绝的哨兵值，表示旧版本中缺失的身份。若恢复边界直接复用新校验器，原本有效的旧状态可能永久无法恢复。

- **正确做法：** 比较旧状态时仅对已记录的迁移哨兵值做窄范围兼容，同时要求新分配的身份继续满足当前校验器。
- **发现位置：** schema-v1 Graph 检查点使用空的控制运行身份，导致这些检查点自动恢复失败后无法持久化退避信息。

## 266. 重试元数据属于一次尝试，而不是工作流历史

退避是临时调度状态。若人工恢复或正常完成后仍保留它，会错误呈现当前健康状态，并可能延迟之后真正需要恢复的中断。

- **正确做法：** 前台取得 owner 时清除旧重试状态；自动尝试正常完成时清理尝试身份与退避。持久失败历史应保存在事件日志中。
- **发现位置：** 已成功恢复的 Loop 会无限期保留旧恢复错误和下次尝试时间。

## 267. 次要失败记账不能中断恢复批次

记录主失败时，可能因为租约或检查点已变化而再次失败。若让这个次要错误逃逸，会掩盖本次运行的原始失败，并阻止后续独立候选或保留清理继续执行。

- **正确做法：** 为记账提供独立错误通道，保留主错误；只要 owner 未被取消，就继续执行有界批次。
- **发现位置：** 单个 Loop 退避写入失败可能中断整个工作区维护 tick，并跳过其余 Loop 与清理。

## 268. 清理必须使用发起操作的代次，不能使用重新读取的身份

清理前刚读到的最新检查点，并不能证明它仍属于刚完成的操作。若用这次读取出的身份授权清理，迟到的完成可能删除相邻 owner 新发布的元数据。

- **正确做法：** 在整个操作中携带尝试前身份与提前分配的尝试身份，并只允许清理这两个已知相邻代次。
- **发现位置：** Server Loop 恢复的成功清理使用了最新持久化的 control-run id，而不是已完成尝试捕获的身份。

## 269. 缓存文件不能改变它所索引的身份

把建议性缓存写在工作区内，可能在计算缓存 key 后立刻改变工作区指纹，使新条目从创建起就已经过期，并让原本可复用的进程内结果失效。

- **正确做法：** 仅从权威工作区身份中排除精确命名的内部缓存文件，同时继续把条目绑定到命令、内容指纹、大小、期限与完整门禁规则。
- **发现位置：** Loop 持久验证缓存因自身写入改变被缓存指纹，导致完整阶段额外执行一次。

## 270. 重试延迟是持久工作流状态

只在进程内 sleep 会在崩溃后丢失延迟，使外部副作用早于声明策略再次执行。

- **正确做法：** 在可取消等待前写入已结算尝试、有界错误与绝对下次尝试时间；恢复时区分执行中断与已结算的重试等待。
- **发现位置：** Engineering Graph 节点重试原先立即执行，也没有可恢复的等待代次。

## 271. 调度过程中产生失败后必须重新应用停止策略

调度器可能先检查 `failurePolicy`，随后在处理截止时间、Gate 或等待时新建一个零次尝试失败。若继续同一轮，就可能在停止策略已经触发后仍启动独立工作。

- **正确做法：** 任何调度器内部转换产生失败后，都要在选择或启动就绪工作前重新检查停止策略。
- **发现位置：** Graph 启动截止时间到期时，一个节点会失败，但其独立兄弟节点仍可能在同一调度轮启动。

## 272. 时间推导的优先级需要同时限制上下界

时钟偏差或未来的持久时间戳会让计算出的等待时长为负。只限制上界，会把防饥饿机制变成无界的优先级惩罚。

- **正确做法：** 把时间推导的老化值限制在声明的上下界内，再加入调度分数。
- **发现位置：** Graph 优先级老化把奖励上限设为 20，却允许负值。

## 273. 结构相等不能依赖对象键的插入顺序

`JSON.stringify` 会保留对象插入顺序，因此由不同适配器构造的语义相同类型对象可能被误判为已变化。

- **正确做法：** 迁移与缓存身份判断应使用结构相等或共享的规范化表示。
- **发现位置：** Graph 迁移计划可能仅因属性插入顺序不同而让未变化节点失效。

## 274. 建议性缓存命中不能授权验收

跨运行缓存即使 key 正确，其权威性仍低于新执行的发布门禁。若没有其他未受影响阶段恰好触发完整回退，把命中视为成功的增量运行并不安全。

- **正确做法：** 显式跟踪持久缓存来源，并在接受成功前强制执行完整权威流水线。
- **发现位置：** 全部阶段均可缓存的 Loop 验证计划可能完全依靠持久提示通过。

## 275. 建议性持久化仍是反序列化边界

只有在复用前校验未知字段、稠密数组、运行时身份、字节上限和嵌套结果形状，忽略损坏缓存文件才是安全的。

- **正确做法：** 使用稠密数组、精确字段、有界字节、严格哈希/时间戳以及与生产契约一致的嵌套不变量解析缓存信封和条目。
- **发现位置：** Loop 验证缓存条目曾接受额外结果字段和宽松形状的指纹。

## 276. 终态化已恢复工作时必须清除其活动标记

当停止策略、取消或控制转换已经决定结果时，已恢复尝试可能不再进入执行路径就直接被跳过。若清理只存在于正常完成处理器中，它将永远不会执行。

- **正确做法：** 每个终态化 owner 都必须在发布结果前，原子移除已恢复尝试查找项和持久活动尝试标记。
- **发现位置：** 已有停止策略失败跳过持久 Graph 重试等待时，活动标记可能与终态结果同时残留。

## 277. 嵌套持久工作流需要稳定的父尝试身份

若恢复后的父工作流会创建新的随机子 id，仅持久化子工作流仍然不够。子流程完成后、父检查点写入前发生崩溃，可能重复编辑并留下孤立历史。

- **正确做法：** 从父流程的持久 attempt 幂等键与 item 身份派生子工作流 id；父流程恢复时继续这个精确子流程，只有真正的新父尝试才分配新子流程。
- **发现位置：** 恢复后的 Graph Loop 节点和动态 Loop map item 会启动无关 Loop 记录，而不是继续其已持久化子流程。

## 278. 检查点缺失与检查点无效是两种不同状态

加载器为了方便列表处理，可能同时对缺失和损坏返回 `null`；但确定性恢复 owner 不能把损坏解释为创建替代状态的许可。

- **正确做法：** 在恢复边界把校验加载与物理存在探测配对；只有确实缺失时才创建，文件存在但无法校验时必须失败关闭。
- **发现位置：** 损坏的确定性 Graph 子 Loop 检查点原本可能退化为一次新的、未持久化子流程执行。

## 279. 新增隐式默认值必须保持旧持久身份

即使运行行为不变，新增一个规范化默认属性也可能改变序列化定义，导致升级后的旧检查点无法通过指纹校验。

- **正确做法：** 当旧规范状态省略某个字段时，新默认值也应保持隐式，或提供明确的指纹迁移。
- **发现位置：** 解析旧 handler `map` 时插入 `mapKind: "handler"`，导致本来兼容的 Graph 检查点无法恢复。

## 280. 聚合能力判断必须覆盖嵌套变体

运行能力可能由某个子类型请求，而不只由顶层 kind 请求。只检查直接 kind，会让派生执行绕过预检要求。

- **正确做法：** 在共享判断函数中枚举所有可能调用该能力的变体，并递归检查嵌套定义。
- **发现位置：** 动态 Agent/Loop map 节点绕过了服务端强制 Graph 成本预算检查。

## 281. 迁移失效范围必须包含 Graph 级策略

当调度、失败、预算、工作区或 fan-in 策略位于定义外层时，只比较节点并不充分。此类变化后仍报告所有节点均可保留，会给出不安全的迁移建议。

- **正确做法：** 对 Graph 级外层执行结构比较；行为相关策略变化时，让所有保留节点失效。
- **发现位置：** Graph 迁移规划忽略了 `failurePolicy`、并发、预算、托管 worktree 与 fan-in 的变化。

## 282. 活动尝试元数据受所属节点契约约束

全局合法的尝试次数，对重试次数更少的节点仍可能不可能出现。接受这种状态，会让损坏的恢复记录伪造定义从未允许的尝试或重试等待。

- **正确做法：** 对所属节点校验：运行中尝试不得超过 `maxRetries + 1`，重试等待不得超过 `maxRetries`。
- **发现位置：** Graph 状态曾允许未配置重试的节点出现第六次尝试乃至重试等待。

## 283. 持久指纹必须认证持久载荷

只把检查点声明的指纹与请求定义比较，相当于信任声明本身，却没有证明已加载定义确实生成了该指纹。被修改的载荷可以保留旧摘要并绕过恢复比较。

- **正确做法：** 从已加载定义重新计算规范摘要或明确支持的旧摘要，再要求这个经过认证的定义与请求的规范身份一致。
- **发现位置：** Graph 恢复曾接受匹配的指纹字符串，却没有把它重新绑定到检查点自身的定义。

## 284. 每一个完成门禁都必须进入收敛身份

验证器可能始终为绿，但验收或独立审查发现仍在变化。只比较验证诊断和工作区内容，会在剩余完成义务已经变化时误报无进展。

- **正确做法：** 把所有持久完成门禁纳入有界收敛指纹，同时不要把不可信自由文本放进身份。
- **发现位置：** Loop 的独立代码审查发现最初没有进入卡住/循环检测。

## 285. 恢复的工作记忆必须仍与工作区匹配

任务级记忆写入时可能有效，但外部编辑或从变化后的 checkout 恢复后就会过期。未经复验直接注入，会把旧观察变成当前指导。

- **正确做法：** 把工作记忆绑定到权威工作区指纹；构造提示前若当前指纹不同就丢弃。
- **发现位置：** Loop 曾可能在两次调用之间工作区已变化后，仍注入持久化的审查/失败记忆。

## 286. 有界诊断窗口必须是最新窗口

读取轮转历史的前 N 条记录不能证明最新持久结果。把该前缀当成尾部，会在后续代次存在时错误报告检查点不匹配。

- **正确做法：** 对完整有界日志保持严格解析，但当诊断依赖时序新旧时，只保留最后 N 条合法记录。
- **发现位置：** Loop 与 Graph diagnose 最初把最旧的 2,000 条保留事件拿来与检查点比较。

## 287. 类型强制转换不等于运行时类型校验

在校验语法前先转换未知字段，可能让错误运行时类型看起来合法，而后续类型断言仍会保留原始非法值。

- **正确做法：** 先证明精确的运行时类型，再在不强制转换的前提下执行语法与唯一性检查。
- **发现位置：** Loop 代码评审 finding id 因先校验 `String(id)` 而接受了数字，随后却存回原始数字值。

## 288. 异步完成门禁必须重新检查取消与硬预算

中止请求可能与提供方最终响应竞态，同一个响应的用量记账也可能越过硬限制。结构合法的结果本身不足以授权成功。

- **正确做法：** 每个异步完成门禁结束后，在接受完成前重新检查权威中止信号与累计预算。
- **发现位置：** Loop 评审可能在取消或评审成本超预算已经赢得竞态后仍报告成功。

## 289. 持久化建议性结论受工作区身份约束

评审或摘要写入时可能有效，但外部编辑后会过期。只清除派生摘要，仍会让旧源结论进入后续提示词。

- **正确做法：** 工作区指纹不再匹配时，同时失效所有建议性结论及其可恢复身份。
- **发现位置：** Loop 清除了过期工作记忆，却仍可能把旧代码评审 finding 交给下一轮编辑。

## 290. 诊断应使用最佳的已验证保留历史

旧检查点可能没有新的追加式历史文件，但检查点本身仍内嵌有界事件轨迹。把这种情况当作无历史会丢失有效证据。

- **正确做法：** 优先使用专用事件日志；缺失时回退到具有相同序列语义的已验证内嵌轨迹。
- **发现位置：** Graph diagnose 在 JSONL 历史尚未创建时忽略了 `state.events`。

## 291. 诊断代码必须防御宽松解码的历史

可观测性读取器可能只识别事件判别字段，而未完整校验所有嵌套载荷。用于报告损坏的诊断自身不应因该损坏而崩溃。

- **正确做法：** 解引用前校验每个嵌套字段，并为非法载荷输出有界损坏 finding。
- **发现位置：** 非法保留 `loop.done` 记录可能在 Loop diagnose 读取 `result.status` 时抛错。

## 292. 建议性状态生产者必须满足自身解析器

当单项值、允许枚举、唯一性和精确键也是持久化契约的一部分时，只限制数组数量并不足够。产生非法建议记录可能导致整个父检查点无法加载。

- **正确做法：** 通过与反序列化相同的字段规则规范化建议数据，并用解析器测试生产者输出。
- **发现位置：** Loop 工作记忆创建可能保留不安全路径或未知类别，随后被状态加载器拒绝。
- **同类问题：** 公共 Loop 验证智能记录函数把阶段/命令及 flaky-attempt 一致性校验推迟到获取租约之后。

## 293. 变更计划在获取租约前就会过期

只读预览与变更锁之间，另一个 owner 可能替换检查点。直接应用旧失效集合可能保留与权威定义已不兼容的结果。

- **正确做法：** 在副作用前完成校验，获取变更租约后重新读取检查点，并基于该 generation 重新计算完整计划。
- **发现位置：** Graph 迁移落地最初存在把预检迁移计划当成状态重写授权的风险。

## 294. 部分检查点迁移必须重建聚合不变量

仅过滤结果行不够：总量还包含未完成 map item 与 fan-in 用量，而暂停原因、完成标记、活动 attempt、fingerprint 和资源 generation 又共同约束同一记录。

- **正确做法：** 按目标契约重新构造迁移检查点，从保留组件重算全部聚合值，清除不兼容生命周期字段，并通过普通 loader 验证。
- **发现位置：** Graph 迁移需要阻止过期用量、终态标记、fan-in 证据或活动 generation 在节点失效后继续存在。

## 295. 预测是观察结果，不是执行授权

仿真无法提前知道未来路由、审批、外部信号、失败或远程延迟。把预测复用为运行时资格决定会静默绕过权威调度器。

- **正确做法：** 保持仿真无副作用，显式报告不确定性，并让真实执行重新判断全部依赖、资源、预算、deadline 与外部事件。
- **发现位置：** Graph 调度预测需要与实时节点资格和检查点变更使用独立契约。

## 296. 嵌套持久 generation 不能独立迁移

子检查点由父级保存的定义与 attempt 身份认证。只重写任一侧都会让两者不一致，而让父级 subgraph 节点失效还可能误恢复旧子 generation。

- **正确做法：** 在协调协议下原子迁移父子身份；该协议存在前，应拒绝子检查点迁移和会让既有 subgraph 失效的迁移。
- **发现位置：** Graph 迁移最初允许嵌套子检查点或既有 subgraph 定义被独立修改。

## 297. 预算预测必须使用预算所属的时间域

工作流 makespan 可能包含持久化离线等待，而运行时会明确把这段时间排除在累计活跃时长之外。比较不同计时口径会产生错误的预算耗尽告警。

- **正确做法：** 分开报告墙钟与活跃运行估算，并只用预算定义的活跃时间口径比较时长预算。
- **发现位置：** Graph 仿真最初把离线 `notBefore` 间隔计入 `maxDurationMs`。

## 298. 备选就绪条件使用 OR 语义

同时声明 timer 与 signal 的 wait 在任一输入满足时即可就绪。把每个未满足输入都报告为独立阻塞，会让已经可运行的节点看起来仍被阻塞。

- **正确做法：** 先计算声明的就绪表达式，只在没有任何备选项满足时报告阻塞。
- **发现位置：** Graph 节点解释最初在 wait timer 已就绪时仍报告 signal pending，反之亦然。

## 299. 持久 wait 是调度屏障，而不是零耗时工作

未解决的持久 wait 会排空在途工作，并在其他就绪节点启动前暂停工作流。把它建模为普通零耗时节点会允许不可能的重叠，并低估墙钟完成时间。

- **正确做法：** 预测与回放模型必须先遵循运行时的暂停并排空转换，再推进持久 timer。
- **发现位置：** Graph 仿真最初会在 `notBefore` wait 恢复前启动独立兄弟节点。

## 300. 可观测文件不能扰动其描述的身份

真实阶段执行后写入验证器历史，可能在收敛采样前改变工作区指纹；即使产品文件未变化，
也会制造虚假进展或让缓存失效。

- **正确做法：** 只从权威内容身份中排除精确命名且有界的内部可观测文件；其解析器、
  租约、运行时 key、期限和数量限制仍应独立保持。
- **发现位置：** Loop 验证智能最初写在工作区内，却没有显式加入工作区指纹排除项。
- **同类问题：** Graph 调度智能是另一个未加入同一内容身份排除项的精确可观测文件。

## 301. 读改写状态必须在取得所有权后再读取

两个记录者可能先读到同一份聚合，再通过租约串行写入；第二个记录者仍会提交其租约前读取的
旧快照。只把写操作串行化并不能避免更新丢失。

- **正确做法：** 先获取共享变更租约，再在持有所有权期间读取、合并并原子替换状态。
- **发现位置：** Loop 验证智能最初在获取跨进程租约前读取聚合记录。
- **同类问题：** Graph 调度观测采用无租约的读改写路径，可能用旧快照覆盖更新的并发结果。

## 302. 新的历史消费者需要覆盖每一代生产者

当路由或收敛逻辑也会读取首次预检查快照时，只给后续迭代快照增加字段并不够。
第零代缺失元数据会悄悄重置连续历史计算。

- **正确做法：** 每当新的持久字段开始驱动历史决策，都要枚举并测试首次、恢复、重试、
  回滚与普通生产路径。
- **发现位置：** Loop 自适应模型路由最初遗漏预检查失败类别，使升级延后一次迭代。

## 303. 诊断形状不能证明失败结果

验证器成功时仍可能识别出所属框架，而另一道验收门禁会让工作流继续编辑。若只按框架形状分类，
就会报告一个从未发生的测试失败。

- **正确做法：** 先从权威退出结果判断成功或失败；只有真实失败才进入诊断类别分类。
- **发现位置：** Loop 模型路由最初把“验证器为绿但验收未满足”错误归类为 `test`，而不是 `none`。

## 304. 有界操作数在聚合时仍可能溢出

两个安全整数并不保证其乘积或加权和仍是安全整数。极大但合法的耗时乘以样本数，
可能破坏平均值或调度分数。

- **正确做法：** 优先使用数值稳定的增量平均；仅用于启发式排序的分数应先限制在声明的
  数值域内再参与排序。
- **发现位置：** Loop 验证智能最初把一个安全耗时乘以最多 10,000 个保留样本。

## 305. 观察历史不等于行动历史

预检查可以把失败归为与后续编辑迭代相同的类别，但它尚未尝试任何恢复。把该分类当成已执行策略，
会跳过首次类别专用修复并过早切换方案。

- **正确做法：** 行动多样化只能依据确实可能执行过该行动的 generation，不能只看输入类别相同的快照。
- **发现位置：** 自适应 Loop 路由为第零轮快照加入类别后，首次 SARIF 恢复跳过了
  `repair_review`，错误选择 `replan`。

## 306. 历史建议必须绑定其测量的契约 generation

稳定的 Graph 与节点 id 可能跨越处理器、工作区、依赖或调度策略变化。只按 id 复用结果，
会让新定义继承它从未执行过的耗时与失败证据。

- **正确做法：** 在每条观测 key 中包含权威的“定义 + 物理工作区”指纹；只有精确匹配时，
  历史才可影响调度。
- **发现位置：** Graph 自适应调度最初只按 Graph 和节点 id 关联观测，因此定义变化后仍会
  消费过期调度证据。

## 307. 替换事务必须保留即将被遮蔽的旧状态

如果先写入新的权威检查点、再归档旧终态，进程在两次写入之间退出时，源状态会永久丢失。
只记录指纹的 journal 可以证明发生过什么，却无法重建丢失的快照。

- **正确做法：** 先持久化 prepared journal，再执行幂等的源归档，然后原子替换检查点，
  最后把 journal 标记为 committed。由于归档身份稳定，恢复时可安全重试。
- **发现位置：** Graph 迁移最初在归档源运行前提交替换检查点，崩溃窗口会丢失对比历史。

## 308. 建议性预测不能变成运行资格

即使历史耗时和失败估计按正确 key 隔离，它们仍可能过期、稀疏或有偏差。让预测跳过必需
验证器或绕过依赖，会把可观测误差升级成正确性错误。

- **正确做法：** 学习值只能用于有界排序、重试建议和纯仿真；依赖、资源、预算、权限与
  必需验证门禁继续保持权威。
- **发现位置：** Graph 健康报告与 Loop 验证可靠性需要明确隔离预测报告和运行资格。

## 309. 恢复身份必须包含资源代次

资源重建后可能再次出现同一个定义指纹。如果仅凭该指纹就认定 prepared 替换已经提交，旧
journal 可能会被绑定到新的物理资源代次，并错误授权后续清理。

- **正确做法：** 替换恢复必须同时绑定逻辑目标指纹和不可伪造的资源代次；开始下一次替换
  前先完成精确匹配的事务，并拒绝既不匹配源状态、也不匹配精确目标状态的 prepared journal。
- **发现位置：** Graph 迁移 journal 已记录资源代次，但最初的恢复逻辑只比较目标指纹。

## 310. 版本排序必须包含预发布优先级

如果只比较语义版本的数字核心，就会把 `1.0.0-beta` 误判为 `1.0.0` 之后的版本，也无法正确
排列预发布标识符，导致内容变化实际降级时升级门禁仍报告兼容。

- **正确做法：** 先按数值比较 major、minor、patch，再应用正式版与预发布版以及点分标识符
  的优先级规则；内容是否相同与版本是否前进应分开判断。
- **发现位置：** Graph 模板兼容性最初只检查三个数字段来判断变化后的候选版本是否前进。

## 311. 内容替换必须保留独立生命周期元数据

替换同一个逻辑 key 下的内容，并不代表有权重置由另一条生命周期管理的元数据。通用 upsert
若重建整条记录，可能会把已显式弃用或归档的对象静默恢复为活跃状态。

- **正确做法：** 识别不属于本次替换操作的元数据，在同一读改写租约内继续保留；只有独立、
  显式的操作才能撤销该生命周期状态。
- **发现位置：** Graph 模板精确版本被重新注册时，最初会丢失其 `deprecatedAt` 标记。

## 312. 预测误差必须使用结果产生前捕获的预测

把待评估结果加入样本后再计算基线，会把答案泄漏进预测。只有一个样本时，更新后的分位数
必然等于结果本身，无论原预测是什么都会显示零漂移。

- **正确做法：** 在任务派发时持久化预测，并把它与精确的完成观测关联；如果不存在结果产生
  前的预测，就省略漂移，而不是用事后估计替代。
- **发现位置：** Graph 健康最初用已经包含当前完成节点的 P50 与该节点耗时比较。

## 313. 容量预测必须保留硬上限的比较语义

如果运行时在 `usage >= limit` 时停止，就不能把 `remaining / forecast` 的整数步数全部称为
可承受容量：恰好落在上限上的那一步已经会被拒绝。缺少预测样本也不能让当前用量已耗尽的硬
上限重新获得容量。

- **正确做法：** 容量计算必须使用与权威预算门禁相同的严格比较；剩余容量为零时立即报告零。
- **发现位置：** Loop 健康最初会在预测恰好触及 `maxVerifyRuns` 时报告仍可承受一次验证迭代，
  也会在没有样本但成本预算已耗尽后继续报告编辑容量。

## 314. 配置建议必须满足被建议配置的契约

纯仿真器可能接受公共解析器或工作区校验器会拒绝的假设对象。把这种结果作为建议返回，会让
建议无法被安全应用。

- **正确做法：** 每条建议都要受权威配置常量约束；如果无法从保留状态证明物理前提，就应
  抑制该建议。真正应用时仍必须经过正常校验。
- **发现位置：** Graph 健康最初可能建议让共享同一工作区的有副作用节点并发，或新增第 65 个
  资源容量 key。

## 315. 乐观版本必须单调递增

两个状态转换可能发生在同一个时钟毫秒内。直接把墙钟时间戳当作乐观版本，可能让 `updatedAt`
保持不变，使过期 reviewer 覆盖更新后的决策。

- **正确做法：** 分配 `max(now, previous + 1ms)`，或使用独立的单调 generation；在持有修改
  lease 时比较保留状态中的精确版本。
- **发现位置：** 编排提案批准最初直接使用 `new Date()`，紧接着的第二次复核可能复用原版本。

## 316. 归档证据必须使用与在线证据相同的校验器

把产物元数据移入运行归档，并不会让其中的路径或摘要自动变安全。宽松的历史解析器可能把之前
被拒绝的元数据变成未来的复用候选。

- **正确做法：** 写入与读取归档时都复用权威的相对路径、摘要、大小、生产者与验证状态校验；序列化前
  省略不完整证据，复用规划前还必须要求契约代次精确匹配。
- **发现位置：** Graph 运行快照开始保留已验证产物证据时，需要补上在线状态已有的安全相对路径不变量；
  它还可能序列化不完整的“已验证”证据，导致严格归档读取器拒绝整个运行。

## 317. 新历史消费者必须保留权威回退语义

持久 JSONL 文件可能尚不存在，但有效检查点仍保留有界事件尾部。新报告如果只读取 JSONL，就会把
一个已存在的终态运行描述为空重放，与 history 和 diagnose API 不一致。

- **正确做法：** 重放前集中复用或严格保持从持久历史回退到检查点事件的既定规则，并使用相同序号语义。
- **发现位置：** workspace 编排报告最初遗漏了 REST history 与诊断路径已经使用的 Graph 检查点事件回退。

## 318. 动作结果必须归因到选择该动作时的状态

结果通常保存动作后的状态，但 router 是根据前一状态选择动作的。当动作改变了分类时，按结果状态分组
会学习出相反关系。

- **正确做法：** 保留或定位精确的动作前 generation，把模型、重试或策略结果归因给该 generation；
  回滚尝试也必须保留其已选策略证据。
- **发现位置：** Loop 策略学习最初按编辑后的失败分类汇总模型，并在回滚快照中丢失模型元数据。

## 319. 比率聚合必须按证据加权，而不是按实体平均

逐节点比率的算术平均会让只有一个样本的节点与数百样本节点拥有相同权重。同样，只测得一个 stage
也不代表多 stage pipeline 已有完整预测覆盖率。

- **正确做法：** 按样本数加权比率，报告已测量/可测量覆盖率，并用实测样本而不是预测计算百分位 SLO。
- **发现位置：** 编排 SLO 最初等权平均 Graph 节点失败率，并把任意 Loop 验证智能视为 100% 覆盖。

## 320. 子级记账需要持久来源

稳定派生 id 可以避免重复执行，却不能向后续报告代码证明所有权。同时统计父级总量与独立保存的子级，
会放大 workspace 用量与预算。

- **正确做法：** 在子检查点持久化并校验父级身份，恢复时核对，在摘要中保留；只有父级已包含该用量时
  才从汇总中排除子级。
- **发现位置：** 组合汇总已经排除子 Graph，却最初重复计算了由 Graph 持有的持久子 Loop。

## 321. 决策存储必须故障关闭，且不能淘汰决策

宽容的只读视图可以隐藏损坏的可选状态，但修改不能把这种“缺失”当成覆盖文件的授权。容量淘汰也必须
区分已复核决策与可重新生成的草案。

- **正确做法：** 在修改 lease 内使用严格解析器，优先保留已复核记录，并只返回实际保留的记录。
- **发现位置：** 编排提案刷新最初可能覆盖损坏状态，或用新生成草案淘汰较旧的批准记录。

## 322. 数字传输语法必须明确

JavaScript `Number` 会接受空白、十六进制与指数形式，而这些形式可能不属于公共十进制配置契约。

- **正确做法：** 数值转换前先按预期语法校验完整传输字符串，再检查有限性与范围。
- **发现位置：** 编排 CLI 与 REST 的 SLO 解析器最初会接受 `0x10` 等值。

## 323. 预览状态必须绑定到其源 generation

通过确定性 id 找到检查点，并不能证明它代表当前预览的定义或父边。从无关检查点推导建议，可能错误地
暗示协调迁移是安全的。

- **正确做法：** 在迁移树预览使用检查点前，比较完整标准化源定义与精确父级来源。
- **发现位置：** Graph 树迁移规划最初把任意同 id 状态标记为可用，没有核对其定义或父级。

## 324. 乐观版本也必须覆盖内容刷新

记录可以保持相同身份与复核状态，但证据、理由或其他被复核内容已经改变。如果版本不变，复核者就可能
批准与其读取内容不同的记录。

- **正确做法：** 刷新时比较完整复核载荷；任意字段变化都要单调推进乐观版本。
- **发现位置：** 同一提案 id 获得新证据时，编排提案刷新最初仍保留原 `updatedAt`。

## 325. 嵌套状态发现必须沿物理工作区进行

子检查点身份与子检查点位置是两个不同问题。只列出根工作区会遗漏带 workspace override 的嵌套节点，
使迁移预览与实际 apply 不一致。

- **正确做法：** 解析每个定义 generation 的物理工作区树，逐层加载检查点，以 runtime id 与规范工作区
  共同绑定所有权，并同时检查源树和目标树中的孤儿冲突。
- **发现位置：** Graph 迁移树 REST/CLI 预览最初只提供根工作区内找到的状态。

## 326. 传输变体必须保留已证明字段

用一个宽松 DTO 同时表示生成草案、持久决策与已验证证据，会让消费者依赖的生命周期版本或密码学证明
看起来是可选的。

- **正确做法：** 分开建模草案与持久变体，并收窄已验证输出，使经过校验证明的字段在公共契约中必填。
- **发现位置：** 编排传输最初因为草案复用了同一 DTO，而把持久提案版本与已验证产物摘要设成可选。

## 327. 相对预警区间需要零目标规则

“距离上限 10%”这类百分比区间在上限为零时会坍缩。直接使用通用乘法公式，可能把精确满足要求的零观测
错误归为预警而非成功。

- **正确做法：** 应先显式定义零目标的相等语义，再应用比例预警区间。
- **发现位置：** `maxFailureRate: 0` 的编排 SLO 最初把观测到的零失败率报告为 `at_risk`。

## 328. 子级所有权会改变恢复与记账语义

只持久化父 id 还不够：如果通用恢复仍可独立运行子级，或父检查点消失后报告仍排除子级，所有权语义就会
失效。

- **正确做法：** 子级恢复必须经过父编排路径；通用恢复与直接删除应排除子级；只有同一记账范围内存在
  所属父级时才去重子级用量。受守护的终态保留仍可删除过期子记录。
- **发现位置：** Graph 持有的 Loop 最初可被直接恢复，而孤儿子 Loop 仍会被组合总计排除。

## 329. 排序或截断前必须完成校验

保留选择不是输入校验边界。如果先截断低排名的无效项，一个畸形生成批次就可能看似有效，并隐藏上游
不变量破坏。

- **正确做法：** 在去重、排序、获取 lease 或持久化前校验完整稠密批次；之后才能应用保留策略。
- **发现位置：** 编排提案记录最初只校验排名前 128 个草案。

## 330. Busy 状态必须从头到尾使用同一操作所有者

相邻异步功能通常有名称相似的加载标志。如果设置一个所有者的标志，却清除另一个所有者的标志，UI 会
永久保持忙碌，并禁用无关控制。

- **正确做法：** 每个操作的设置/清除路径都必须绑定同一 coordinator 与状态所有者，包括过期结果清理
  和工作区切换。
- **发现位置：** Desktop 编排刷新与 DAG 检查路径曾短暂交叉使用 `resourceBusy` 和
  `orchestrationBusy` setter。

## 331. 多检查点激活需要一个可见提交点

即使每个文件写入都是原子的，独立写入相关子检查点与根检查点仍可能在崩溃后暴露混合 generation。

- **正确做法：** 按规范顺序租用参与者，持久化 prepared 状态与恢复 journal，先提交不可独立访问的
  子级、最后激活根；恢复必须确定性前滚。
- **发现位置：** 协调式 Engineering Graph 树迁移最初只有预览，无法安全应用使 subgraph 失效的变更。

## 332. 批准版本与部署版本是两个边界

把批准当作执行会让过期证据修改更新后的 runtime generation，且效应提交与记录提交之间没有可恢复状态。

- **正确做法：** 把部署绑定到精确提案版本与源指纹；效应前持久化 `applying`；重试时识别已提交目标；
  保留精确回滚证据。
- **发现位置：** 编排建议最初止于批准，缺少安全的 apply/observe/rollback 生命周期。

## 333. 内容寻址元数据不是 blob 权威

已记录摘要仍可能指向被替换文件、符号链接，或从未进入不可变存储的字节。

- **正确做法：** 使用 no-follow 语义重新打开物理文件，流式校验大小和摘要，在 lease 协调下复制到 CAS，
  原子物化前再次哈希，并把公开恢复限制为权威复用候选。
- **发现位置：** Graph 产物复用最初只返回元数据计划。

## 334. 容量预留在畸形返回时也必须释放

远端预留完成后的校验已经位于效应之后。因元数据畸形而直接拒绝会泄漏执行器容量。

- **正确做法：** 只要存在可调用 release hook，就在校验拒绝、取消、处理器失败和成功等所有路径尽力调用；
  同时只向精确 attempt 传递有界 fencing token。
- **发现位置：** Graph 远端预留校验最初会在释放前抛错。

## 335. 当前页不是全局评估窗口

只聚合可见分页详情却把结果标为 workspace 级，会在遗漏记录越界时误报健康 SLO。

- **正确做法：** 显式标记分页派生摘要，把完整组合总计分开，并用覆盖全部检查点的物化索引提供有界全局摘要。
- **发现位置：** 编排报告的新错误预算摘要最初没有 scope 标记。

## 336. 有界索引必须对被省略记录做指纹

只哈希保留摘要项，会让展示上限之外的变化无法推进缓存 generation。

- **正确做法：** 先校验并指纹化完整权威源集合，在截断前计算总计，最后只保留有界展示投影。
- **发现位置：** 编排物化索引最初只从最新 512 项生成 generation。

## 337. 引用感知 GC 仍需要发布屏障

生产者可能先提交 CAS blob，随后才发布引用它的检查点。夹在两个效应之间的 GC 会把有效 blob 看成孤儿并删除。

- **正确做法：** 协调 CAS 写入者与回收者；复用已验证 blob 时刷新发布时间；即使为了满足配额，也绝不回收
  有界发布宽限期内的未引用 blob。
- **发现位置：** Graph 产物 GC 最初只信任当前检查点引用扫描，留下 store-to-state 发布竞争窗口。

## 338. 多 lease 部分获取失败时必须回收

规范获取顺序能避免死锁，却不能阻止后续参与者在前序 lease 已获取后处于 busy。

- **正确做法：** 逐个获取；任意一步失败时按逆序释放全部前序 lease，并用 busy 参与者测试覆盖部分获取路径。
- **发现位置：** Graph 树迁移最初用 `map` 构造 lease 数组，后续获取抛错时会泄漏更早参与者的 lease。

## 339. 状态目录上限必须在归属过滤之后应用

先截断、后识别文件名，会让 journal、control 或攻击者创建的辅助文件把权威记录挤出发现范围。

- **正确做法：** 截断前校验精确 owner 文件名语法；显式删除 owner 时也清除其有界 journal 与 prepared 文件。
- **发现位置：** Graph 状态枚举曾把所有 `.json` 都计入上限，Graph 删除也会遗留树事务文件。

## 340. 替换安全要求在 rename 前完成校验

先原子替换目标、再校验新物化文件，会在新字节损坏时同时破坏原本有效的旧目标。

- **正确做法：** 先 fsync 并哈希精确的同目录临时文件，再把已验证 inode rename 到目标，最后 fsync 父目录。
- **发现位置：** CAS 物化最初会在 rename 后校验失败时删除已经替换的目标。

## 341. 批准只属于精确提案内容

标识符不变时，理由、证据、风险或动作仍可能变化。跨这种刷新继承批准会授权从未被复核的内容。

- **正确做法：** 只有完整生成草案完全相等时才保留批准；任一字段变化都推进版本并重置为 `proposed`。
- **发现位置：** 提案刷新最初无论草案是否变化都会复制旧状态。

## 342. 部署串行化必须覆盖修改目标

只按 proposal id 加 lease，仍允许两个不同提案并发修改同一 Loop 路由或 Graph，旧回滚也可能擦除新工作。

- **正确做法：** 使用 scope 与 source 的有界哈希串行化 apply/rollback；拒绝冲突的活跃目标部署；回滚前核对
  当前路由或 Graph 指纹。
- **发现位置：** 编排部署最初只协调单个提案的重试，没有协调同一 source 上相互竞争的提案。

## 343. 运行时与建议资格必须只有一个 owner

若预检和优化分别判断执行器，畸形负载元数据可能产生非有限排名，而运行时仍接受不健康或满载执行器。

- **正确做法：** 共用一个故障关闭资格分类器，覆盖契约形状、信任、协议、取消、健康、容量、队列和局部性。
- **发现位置：** Graph 预检与 placement 报告曾维护重叠但不一致的执行器检查。

## 344. 时长上限与 deadline 是不同事件

`maxDurationMs` 限制累计活跃运行时间；节点 deadline 限制该节点可开始的时间。把两者都报为 deadline 越界会误述契约。

- **正确做法：** 从同一仿真调度分别计算并公开活跃时长预算与节点/wait deadline 越界概率。
- **发现位置：** Monte Carlo Graph 预测最初在活跃时长超过 `maxDurationMs` 时增加
  `deadlineBreachProbability`。

## 345. 加锁前读取的 journal 只能作为提示

另一个 owner 可能在 journal 发现与参与者 lease 获取之间完成或替换事务；继续操作旧对象会覆盖更新的
prepared 事务。

- **正确做法：** 获取全部参与者 lease 后重新读取并比较精确 journal generation；准备新事务前，拒绝规划期间
  新出现的任何未解决 journal。
- **发现位置：** Graph 树恢复最初会直接提交加 lease 前读取的 journal 对象，不会重新校验其 transaction id
  与内容。

## 346. 授权候选必须持续有效直到效应发生

精确 generation 的产物候选若在加锁前检查，Graph 可能在物化开始前推进，使授权变成过期状态。

- **正确做法：** 获取权威 Graph lease，重新加载检查点与运行快照，重新计算候选成员关系，随后再通过物化
  owner 获取 CAS lease。
- **发现位置：** Graph 产物 REST 路由最初在进入任何协调边界前检查候选范围。

## 347. 效应完成与生命周期记录可能分别失败

原子目标修改可能已成功，而随后的部署记录写入失败。把重试当作全新修改，要么重复效应，要么因 source
已变化而拒绝。

- **正确做法：** 先持久化意图；重试时识别已经 applied 或 restored 的目标指纹/路由；多步路由恢复必须由
  owner 在一次原子写入中完成。
- **发现位置：** Graph apply 以及 Graph/Loop rollback 最初在目标已提交、部署状态未提交时没有恢复路径。

## 348. 持久生命周期解析器必须执行跨字段状态约束

逐字段校验部署记录仍会接受不可能的组合，例如没有目标指纹的 `applied`，或没有错误的 `failed`。

- **正确做法：** 把状态专属的必需/禁止字段、时间戳顺序、scope/action 兼容性与回滚证据来源作为一个整体
  invariant 校验。
- **发现位置：** 第一版部署解析器只检查字段形状，没有检查生命周期组合。

## 349. 共享命令选项仍需按 operation 限定

同时使用 operation 参数与共享 option parser 的命令，可能接受语法有效但对当前 operation 无意义的 flag。

- **正确做法：** dispatch 前校验最终 operation/id/option 组合，拒绝会被忽略的修改、并发控制或回收选项。
- **发现位置：** orchestration `show`/`list` 与 artifact-store `inspect` 最初会接受只供相邻修改 operation
  使用的选项。

## 350. 有界发现列表不是穷尽式安全扫描

状态列表可以有意限制展示或恢复工作量，但复用 GC、保留策略与 workspace 总计不能静默遗漏上限之外的
有效 owner 文件。

- **正确做法：** 在确定性展示上限前过滤精确 owner 名称；为删除、GC、保留与全局聚合 owner 提供故障关闭的
完整扫描模式。
- **发现位置：** Graph 产物 GC 最初复用了 256 项 UI 列表，可能把只被遗漏检查点引用的 blob 判为未引用。

## 351. Workspace 状态拓扑可能跨越目录边界

只列出根 `.seekforge/graphs` 目录会遗漏节点解析到其他物理 workspace 的可达子 Graph 检查点，使组合与
索引总计不完整。

- **正确做法：** 从完整直接根开始，通过共享物理 workspace resolver 遍历每个已验证定义，合并精确 runtime
  identity，并拒绝冲突或过大的总树。
- **发现位置：** 物化编排索引最初只使用根目录中的直接 Graph 状态发现。

## 352. 观察型读-算-写需要与修改相同的生命周期租约

观察者读取活跃记录、计算指标并稍后回写时，可能覆盖期间已经完成的回滚或恢复。

- **正确做法：** 在整个观察过程持有部署 identity lease，获取目标 lease 后重新读取，并通过已经加锁的内部
  owner 执行回滚。
- **发现位置：** 编排部署观察最初只保护最终文件写入，没有保护该写入所依据的生命周期转换。

## 353. 定义指纹不等于检查点 generation

Graph 定义指纹不变时，执行进度仍可能推进。prepared 树事务若只比较定义 identity，崩溃恢复时就可能覆盖
更新的结果。

- **正确做法：** 用完整的已验证检查点哈希绑定 source 与 prepared participant，要求规范化的物理 workspace
  identity，并在任一精确 generation 变化时拒绝恢复。
- **发现位置：** Graph 树迁移 journal 最初只记录 participant 的定义指纹，没有记录完整检查点 generation。

## 354. 跨 workspace 发现必须保留 owner identity

从另一个物理 workspace 解析到子检查点后若只返回状态，就会丢失读取其历史、调度证据、运行快照和内容寻址
产物所需的位置。

- **正确做法：** 在完成所有 owner 专属读取前，让每个发现状态始终携带规范化物理 workspace；对于必须通过
  根树事务修改的嵌套检查点，不要生成独立修改提案。
- **发现位置：** workspace 编排报告虽然找到了外部子 Graph，最初却从根 workspace 读取其辅助数据。

## 355. 意图恢复必须先于提案 supersession

部署效应已提交、`applying` 记录尚未推进时，提案证据可能刷新。若先按新提案版本将记录标为 superseded，
就会丢失活跃目标唯一的持久恢复与回滚血缘。

- **正确做法：** 比较提案版本前，先按 `applying` 记录自身的持久 action 与精确目标进行协调；若已恢复，
  新版本必须先回滚旧部署才能应用。
- **发现位置：** 编排观察最初会直接把版本滞后的 `applying` 记录分类为 superseded，而不检查已提交目标。

## 356. 回滚目标指纹不能认证回滚材料

source generation 指纹能证明修改了哪个 Graph，却不能证明单独持久化的回滚定义仍包含精确 source 内容。

- **正确做法：** 对已验证回滚定义计算哈希，在应用效应前把哈希写入部署意图，并在崩溃协调与回滚时都
  重新验证。
- **发现位置：** Graph 部署回滚最初会信任预期回滚路径中的任意合法定义。

## 357. 持久容量校验应位于事务准备之前

若 participant 数量或字节上限只在读取恢复状态时执行，writer 可能创建恢复路径永远拒绝的 prepared
检查点或 journal。

- **正确做法：** 先在内存中构建并验证全部 prepared payload 与 journal，执行相同 participant/字节上限，
  在任何 participant 文件前持久化 `preparing` 意图，并让恢复清理未完成的准备过程。
- **发现位置：** Graph 树迁移最初限制 journal 恢复读取，却没有限制对应的准备写入。

## 358. 定义 generation 不等于证据 generation

Graph 的状态、结果、用量与控制状态可以在定义指纹不变时推进。只绑定该指纹的提案可能把旧检查点证据
应用到后来执行状态。

- **正确做法：** 用完整已验证检查点的规范哈希绑定决策 identity 与 apply-time 复核，并把定义指纹作为
  独立回滚元数据保留。
- **发现位置：** Graph 优化提案最初把定义/workspace 指纹当作其精确 source generation。

## 359. 回滚安全需要精确的效应后检查点

只检查已部署定义，无法判断 Graph 后来是否在同一定义下恢复运行、累积结果或修改控制状态。

- **正确做法：** 记录完整迁移后检查点的规范哈希，只恢复迁移 journal 能证明的静止检查点，并在回滚前
  要求该哈希仍完全一致。
- **发现位置：** Graph 部署回滚最初只比较目标定义指纹。

## 360. 创建派生历史时必须保留检查点 fallback 事件

读取路径可能只在追加日志为空时回退到检查点事件。若写入首个迁移事件时不补齐更早的检查点事件，合法
生命周期历史会从公共视图消失。

- **正确做法：** 在 Graph lease 内，按 sequence 顺序追加所有比日志尾部更新的保留检查点事件，并在正常
提交与恢复中使用同一修复路径。
- **发现位置：** 第一次由部署触发的 Graph 迁移曾使更早的 `graph.completed` 事件从 REST 历史中消失。

## 361. applying 协调有三种状态，而不是两种

崩溃后，目标可能等于精确 source、等于精确已提交效应，或已被其他生命周期改成第三个 generation。把所有
非目标状态都当作“未应用”，可能覆盖或 supersede 活跃工作。

- **正确做法：** 把精确 source 判为可重试、精确 target 判为可恢复，其余 generation 判为 diverged；保留
  diverged 意图并要求人工恢复。
- **发现位置：** 编排 apply 重试最初会把已推进但定义相同的 Graph 当作部署效应从未提交。

## 362. 持久策略读取应位于纯选项校验之后

持久策略读取可以影响 provider 选择；但若在校验调用方显式选项前读取，就会让畸形请求检查工作区状态，
并可能改变最终暴露的错误。

- **正确做法：** 先校验显式请求结构，再加载精确作用域内的策略，按文档优先级合并，最后才初始化合并
  配置选中的 provider。
- **发现位置：** Auto-Loop 最初会在校验 task、验证、恢复与路由选项前加载已应用路由。

## 363. 原子 rename 不等于原子禁止覆盖

先检查目标不存在，再把临时文件 rename 过去，会留下无关写入方创建目标的窗口；在 POSIX 上，该目标会被
静默覆盖。

- **正确做法：** 禁止覆盖时，使用同文件系统内、遇到 `EEXIST` 即失败的原子硬链接发布；只有显式允许
  覆盖时才使用替换式 rename。
- **发现位置：** CAS 物化默认承诺禁止覆盖，却最初使用“存在性检查后 rename”。

## 364. 观测与判定是一个持久状态

分别校验 observation 与 verdict，会允许“不可能”的记录，例如终态观测仍为 `pending`，或从未观测的部署
却标记为 `improved`。

- **正确做法：** 按生命周期联合校验：未观测或非终态的 applied 记录必须 pending；终态观测必须有终态
  判定；rolled-back 记录只保留 stable/regressed 结果。
- **发现位置：** 编排部署解码最初会独立接受任意合法 metric 与 verdict 组合。

## 365. 无操作事务仍必须返回完整结果

根定义未变化只能说明无需写入；若公共结果描述整棵可达树，就不能仅用根状态构造计划。

- **正确做法：** 在构造 no-op 结果前，仍获取与变更事务相同、包含物理 owner 的完整快照；只跳过 lease
  与写入。
- **发现位置：** 幂等 Graph 树迁移最初会把实际存在的子检查点报告为 missing。

## 366. “精确 generation”哈希不能删减持久证据

若在哈希前把证据字段替换成占位值，两个不同的持久检查点会共享同一决策 generation；即使正常写入通常会
推进时间戳，也不能依赖这个旁路假设。

- **正确做法：** 用规范键顺序哈希完整、已校验的持久值；摘要本身不会保留或暴露底层证据文本。
- **发现位置：** Loop 编排指纹最初会先清空 verifier 命令与输出尾，再声称标识精确 generation。

## 367. 物化刷新 lease 必须覆盖源扫描

若两个刷新器都在发布 lease 外计算，较旧快照可能先等待较新写入释放 lease，随后反而覆盖新结果。

- **正确做法：** 用同一刷新 owner 串行化源枚举、聚合与发布，并把每个已加载 generation 纳入物化摘要。
- **发现位置：** 编排索引刷新最初只在最终文件写入阶段获取 lease。

## 368. 策略键必须使用消费者的封闭分类

通用安全标识符在结构上可能无害，却仍可能是不可能出现的路由分类。若持久化后再于显式选项校验之后合并，
就会绕过运行时的封闭 union。

- **正确做法：** 使用与提案及运行时路由相同的领域谓词校验持久策略键，不能使用更宽泛的路径/id 正则。
- **发现位置：** 已应用 Loop 路由最初会把任意安全标识符当作 failure category。

## 369. CAS 摘要不能授权外部源路径

调用方提供的字节与摘要匹配，只能证明内容完整性，不能证明调用方有权把该文件读入工作区级产物存储。

- **正确做法：** 打开和哈希前，把源解析为精确工作区内、无符号链接的物理路径；摘要/大小校验仍作为
  独立不变量保留。
- **发现位置：** 公共 Graph CAS 存储原语最初会接受任意可读主机文件作为源。

## 370. 精确 Loop generation 校验需要 Loop 生命周期 owner

独立部署目标 lease 只能让多个部署彼此串行，无法阻止运行中的 Loop 在源校验与策略激活之间写入新检查点。

- **正确做法：** 在基线采集、精确 generation 复核、apply 与 rollback 外层获取 Loop 的权威生命周期
  lease；同时保留 target lease 来串行不同提案。
- **发现位置：** Loop 路由部署最初只使用编排 target lease；Graph 部署则还会进入 Graph migration owner。

## 371. 幂等检查点恢复也必须修复派生历史

事务参与者可能已经与目标提交状态完全一致，因为进程恰好在发布检查点后、追加历史前崩溃。若把该参与者
直接当作完整 no-op，会让权威检查点与派生审计历史不一致。

- **正确做法：** 恢复流程识别到精确目标代际时，也要先幂等修复每个派生历史或索引效应，再推进事务。
- **发现位置：** Graph 树恢复在注入的崩溃边界上遇到已提交 child 检查点时，曾跳过历史修复。

## 372. 文本分类器的每个备选项都需要词法边界

某个带边界的备选项不能保护同一正则里的无边界短语。例如 `go test` 会匹配 `cargo test` 的尾部，
从而把 Rust 工作区误判为混合语言。

- **正确做法：** 把所有工具链关键词放进同一个显式单词边界分组，并测试相互重叠的前后缀。
- **发现位置：** 上下文 Loop 路由最初会把 `cargo test` 同时分类为 Rust 和 Go。

## 373. 一次容量决策必须基于同一个持久快照

在一次持有 lease 的决策中重复读取 reservation 文档会产生无谓 I/O；如果读操作不受同一 owner 约束，
还可能比较不同代际的值。

- **正确做法：** 获取 owner 后只读取一次，从该不可变快照推导有效/过期项，并只发布一次替换结果。
- **发现位置：** 工作区级 Graph 执行器容量最初在判断是否需要发布过期清理时重复读取文档。

## 374. 有界历史淘汰必须保留活跃生命周期

直接按时间倒序截断会把终态审计记录与活跃状态机等同处理。足够多的新终态记录可能淘汰仍在运行的灰度，
使已部署效果失去管理入口。

- **正确做法：** 先保留所有活跃生命周期，对不可能的活跃溢出报错，再用终态历史填满剩余额度。
- **发现位置：** 编排灰度保留最初会把 shadow、canary 和终态记录一起截断。

## 375. 跨树关联需要完整代际身份

逻辑 ID 可能在另一个物理工作区或代际中复用。仅按 ID 把优化报告关联到检查点，可能把实际结果附到错误预测。

- **正确做法：** 按 Graph ID 与精确 fingerprint 关联持久证据；物理 owner 可用时也应纳入。
- **发现位置：** 编排预测维护最初只用 Graph ID 索引已发现的 Graph 状态。

## 376. 依赖型选项必须在任何副作用前校验

某个选项单独看可能合法，但缺少启用它的选项时没有意义或不安全。若直到构造后台调度器才发现依赖错误，
更早启动的服务和定时器可能已经残留。

- **正确做法：** 在公共入口创建 registry、server 或 scheduler 之前校验选项蕴含关系与定时器范围。
- **发现位置：** 空闲编排自动回滚最初没有在服务预检时要求同时启用空闲编排维护。

## 377. 血缘去重键必须包含每个不同来源

内容摘要只能标识字节，不能标识产生这些字节的路径或生产者声明。两个输出可能有意包含相同字节，
却拥有不同血缘。

- **正确做法：** 证明身份应包含精确代际、生产者、源路径与摘要；只有 blob 存储可单独使用摘要。
- **发现位置：** Graph 产物证明最初会把同一生产者的两个同内容路径折叠成一条记录。

## 378. 观测身份必须包含生命周期代次与尝试编号

一个动作可以重试，提案也可以在不改变逻辑 ID 或最终指标值的情况下修订。若只按 ID 与结果去重，
就会静默丢失真实的控制面样本。

- **正确做法：** 在持久化观测身份中包含精确提案修订版本和部署尝试编号；执行预测还要包含运行代次。
- **发现位置：** 部署证据最初会折叠不同尝试的相同结果，Graph 预测最初也会折叠重新运行。

## 379. 容量报告与执行必须读取同一个所有者状态

适配器本地的活跃计数无法描述其他进程持有的预留。执行使用工作区预留存储、报告却使用本地计数，
会产生矛盾的可用量与发布决策。

- **正确做法：** 工作区容量遥测应从准入控制所使用的同一份持久化预留快照派生；没有工作区限制的
  适配器仍使用自身本地计数。
- **发现位置：** 第一版执行器容量报告忽略了跨进程 Graph 预留。

## 380. 派生生命周期必须同步权威的人工转换

自动化记录可能显示已提升，而底层部署已经从另一个入口被人工回滚。若把终态自动化记录视为不可变，
管理视图就会失真。

- **正确做法：** 根据权威部署状态同步派生发布状态，包括发布入口之外触发的转换。
- **发现位置：** 已提升发布最初在直接回滚后仍显示为已提升。

## 381. 学习建议必须保持可选，并覆盖自动生成的身份

历史路由可能指向已经移除的 provider，新运行也可能还没有调用方提供的 ID。这两种情况都不应停用或破坏
工作区学习。

- **正确做法：** 对每个持久化的自动生成或显式运行选择建议，安全探测建议 provider，并在不削弱显式
  策略的前提下回退。
- **发现位置：** 上下文 Loop 路由最初要求显式 Loop ID，还可能把已退役的历史 provider 变成运行前提。

## 382. 单键容量上限不能约束共享集合

多个执行器可以分别低于自身限制，但合计 reservation 仍会溢出持久化文档的最大值。

- **正确做法：** 追加前同时执行单执行器容量与存储总准入上限；公开容量最大值必须与该上限兼容。
- **发现位置：** Graph 工作区 reservation 最初允许多个执行器写入超过解析器可接受数量的记录。

## 383. 派生遥测必须保留物理 owner

嵌套 Graph 可以把制品与 reservation 持久化到外部或托管工作区。只聚合根存储会丢失它们的证据，
或把另一工作区的同内容证据错误归属给它们。

- **正确做法：** 每个已发现物理 owner 只读取一次，并按 owner 加领域身份组成派生关联键。
- **发现位置：** 编排制品证明计数最初只读取根工作区，并且只按摘要关联。

## 384. 幂等证据必须保留原始时间戳

重试时再次记录同一声明不是新的观测。用新时间戳替换它会篡改审计历史，并可能推迟有界淘汰。

- **正确做法：** 对完整身份相同的记录原样返回；仅在完整血缘身份变化时创建新记录。
- **发现位置：** 重复 Graph 制品证明最初会刷新 `createdAt`。

## 385. 时间分析必须排除未来样本与无身份样本

时钟偏移产生的未来记录会污染当前校准窗口，而没有运行代次的旧执行无法安全去重。

- **正确做法：** 每个当前窗口指标都以 `now` 为上界；缺少观测键所需身份的旧样本应跳过。
- **发现位置：** 预测校准最初会接纳未来时间戳，维护任务也会在 control-run ID 为空的旧 Graph 检查点上失败。

## 386. 有界生命周期存储需要按字节淘汰终态记录

终态错误包含长度有界但可变的文本，因此仅限制记录数仍不够。接近容量的合法文件可能拒绝之后的每次转换。

- **正确做法：** 保留所有活跃记录，再淘汰最旧的终态记录，直到数量与序列化字节上限都满足。
- **发现位置：** 灰度持久化最初只在按数量截断后检查字节数。

## 387. 过期容量租约必须隔离迟到结果

只在 `finally` 中释放租约，无法保护运行时间超过 lease 的远程操作。旧结果仍可能在替代 owner 已启动后被接受。

- **正确做法：** 使用独立于可选远程 heartbeat 的定时器，在到期前提前续租，并把续租绑定到精确 fencing token；一旦丢失该代次，就取消并拒绝当前 attempt。
- **发现位置：** 工作区级 Graph 执行器 reservation 在长时间远程节点中会过期，却不会阻止迟到结果提交。

## 388. 分阶段灰度证据必须限定 cohort 且只能使用一次

进入更大 cohort 后复用同一观测，会把重复轮询伪装成独立证据，并可能在没有新执行的情况下完成提升。

- **正确做法：** 同时保留全局去重集合和当前阶段样本集合；阶段切换或人工恢复时只清空阶段集合。
- **发现位置：** 同一个精确代次 canary 观测原本可能在下一灰度比例中再次计数。

## 389. 零保留配额不等于负向切片

JavaScript 会把 `slice(-0)` 当作 `slice(0)`。因此，本意是“不保留任何终态记录”的代码，可能恰好在
受保护记录占满上限时错误保留整个集合。

- **正确做法：** 使用负向尾部切片前显式处理剩余槽位为零的分支，并测试精确占满窗口的边界。
- **发现位置：** 未完成 Graph 预检占满 512 个受保护槽位时，决策保留逻辑最初仍会保留全部终态决策。

## 390. 转换审计必须绑定被评估的快照

分阶段转换通常会为下一个 cohort 清空证据窗口。若记录的是转换后的状态，而不是通过门禁的状态，审计记录
就会缺少其所声称决策对应的证据。

- **正确做法：** 先提交权威状态转换，但使用不可变的转换前证据快照构建观测性决策记录。
- **发现位置：** 5% 和 25% 灰度门禁决策最初会对刚清空的下一阶段观测窗口计算指纹。

## 391. 动态安全状态必须在每个约定边界重新采样

若只捕获控制器启动时的状态，临时冻结会变成整次运行的固定策略，即使调度器声称会在安全边界协调状态。

- **正确做法：** 可以缓存不可变的历史与配置，但必须在每个会双向改变行为的边界重新读取可变安全状态。
- **发现位置：** Graph 在自适应控制器冻结时启动后，即使控制器在运行期间恢复，也无法重新启用学习调度。

## 392. 执行分段上限不等于任务终态上限

有界 provider/工具分段结束时，用户任务仍可能有有效进展和剩余预算。把该边界直接变成失败会卡住大型
交互任务；另起一次运行又会伪造用户轮次并丢失运行内状态。

- **正确做法：** 只在显式、有限的分段预算内续跑，并保持同一次运行、lease、上下文、用量计数与取消域；
  harness 引导不写入持久用户轮次 trace，同时发出非终态进度事件。
- **发现位置：** 桌面对话原本把内部 50 轮循环上限当成了整项用户任务的终态
  `max_turns_exceeded`。

## 393. 启动用文件系统根不是用户项目

桌面壳在用户选择项目之前可能需要一个安全 cwd。若这个运行目录进入普通工作区选择或空闲维护，它就会
变成一个意外可编辑的项目，并可能积累领域状态。

- **正确做法：** 在服务器边界标记启动根，将其排除在项目 UI 与项目维护目标之外；仅为兼容服务器默认
  路由保留其默认工作区角色。
- **发现位置：** 去掉启动目录弹窗时，否则只能把 app-data 目录暴露为桌面端活动工作区。

## 394. 保留回滚状态也是原子升级的一部分

若先替换活动目录、再轮换旧回滚目录，系统可能在新版本已经生效后才报告失败，导致状态记录与文件系统事实不一致。

- **正确做法：** 活动版本交换前先移走上一份回滚；任何 rename 失败都恢复活动与回滚两个代次；只有完整交换成功后才淘汰更旧副本。
- **发现位置：** 插件强制更新最初会在回滚目录轮换失败仍可能发生时先装入新摘要。

## 395. 注册表记录不是其中嵌套的领域载荷

列表接口常在领域操作所接收的对象外包裹生命周期元数据。把包装对象继续传递可能因其类型是 `unknown`
而通过类型检查，却在之后的语义校验中失败；重复的包装身份还会在带键 UI 集合中冲突。

- **正确做法：** 统一解码一次包装，保留身份与生命周期状态，拒绝重复身份，并把有明确名称的嵌套载荷传给领域操作；测试真实列表响应形状。
- **发现位置：** 桌面端 Graph 模板选择器曾把 `{template, registeredAt, deprecatedAt?}` 当成模板本身。

## 396. 引用安全编辑必须枚举每个承载契约的字段

依赖不一定只存在于显式依赖数组中。若只保护直接边，编辑器可能删除仍被条件、绑定、路由、补偿目标或其他领域字段引用的值。

- **正确做法：** 从权威契约导出完整引用清单，区分嵌套作用域，并在允许移除依赖或删除节点前覆盖测试每种承载引用的变体。
- **发现位置：** 桌面端 Graph 编辑最初遗漏了 router `routes[].when` 条件中的引用保护。

## 397. 去抖持久化必须有意刷新或取消

去抖定时器属于持久化生命周期的一部分。若导航或卸载时只清除定时器而不先结算其捕获值，用户恰好离开界面时会丢失最新编辑。

- **正确做法：** 连同精确 owner 身份保留有界待保存载荷；在正常生命周期边界刷新，在重置时显式取消，并把配额或存储不可用故障与当前编辑器隔离。
- **发现位置：** 桌面端按工作区保存 Graph 草稿的初版会在切换工作区或卸载时取消最后 300ms 窗口中的编辑。

## 398. 应用必须消费预览时的精确控件与 owner

即使权威状态会在应用时重新计算，dry-run 结果也只描述一个控件快照。应用时重新读取可变控件可能执行用户从未审阅的策略；界面复用时，迟到结果还可能跨越资源边界。

- **正确做法：** 把已校验选项保存在预览旁，任何输入编辑都使预览失效，捕获资源代次，并守护成功、错误、副作用后续与 busy 清理。
- **发现位置：** 桌面端记忆整理曾以一个归档阈值预览、却应用输入框当前值，而且回调未绑定工作区代次。
